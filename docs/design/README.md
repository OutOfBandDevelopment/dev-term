# Design Documents

Living design docs for dev-term, written during the pre-implementation design phase. Each doc covers one concern and cross-links to the others; "Open questions" sections track decisions not yet made.

- [Architecture overview](architecture.md) — core abstractions (session, transport, presenter, pipeline, plugin host, front ends) and how data flows between them.
- [Transport layer](transports.md) — the `ITransport` contract and the initial transports: serial, TCP (client + listener), UDP (target + listener), USB HID (HidSharp), BLE (cross-platform via a pluggable per-OS adapter seam, "BLE Serial"/Nordic UART Service as the common device pattern). Also covers why USBTMC and GPIB aren't in that list — USBTMC needs its own raw-USB transport; most GPIB-via-cheap-adapter hardware needs no new transport at all (Prologix protocol over existing serial/TCP), except NI-protocol clones, which do and aren't recommended.
- [RFC 2217](rfc2217.md) — client (connect to a remote serial port, e.g. `ser2net`) and server (expose a local serial connection to the network) support for the Telnet Com Port Control Option; not yet built. Flags that "RFC2217" in a vendor's marketing copy isn't proof of standard compliance — confirmed against a real target device.
- [USBTMC transport](usbtmc-transport.md) — a raw-USB transport (WinUSB or LibUsbDotNet) for the USB Test & Measurement Class most local-USB bench equipment (Rigol/Keysight/etc.) actually uses; not HID, not a virtual COM port. Explicitly rules out IVI.NET/VISA (Windows/.NET-Framework-oriented, plus a separate proprietary native runtime install) in favor of implementing the protocol directly, matching how Serial/HID already avoid a vendor-driver dependency. Not yet built.
- [Presenters & encodings](presenters.md) — text/numeric-base views; protocol decoders (device and network protocols) that always produce a human-readable text baseline; rendering presenters (HPGL/PostScript/PCL, telemetry plots) with export to SVG/PNG/JPG; composite/channelized decoders for interlaced telemetry; and mappable presenters (external name/label/unit maps, e.g. Modbus register maps) so one decoder plugin serves many devices.
- [Plugin model](plugin-model.md) — how transports and presenters are packaged, discovered, versioned, loaded, and registered into the DI container.
- [Device control modules](device-control-modules.md) — plugins that bundle an outbound control surface (commands/parameters, e.g. for driving test equipment) with telemetry decode/present/plot for the response, composed from the existing transport/presenter contracts.
- [UI definitions](ui-definitions.md) — a framework-agnostic, JSON/XML-serializable model (`DevTerm.UiDefinitions`) for declaring a control panel's layout once so every front end renders it generically. Rendered generically by both front ends' control panels against a live `IControlSurface` (K8055, Busylight, SCPI, device manifests); includes a serializable `ValueConstraint` (data type/bounds, independent of the widget) checked by one shared `ValueValidator`, and display-only bar graph, strip chart, and vector/coordinate controls fed by live decoder values.
- [Device manifests](device-manifests.md) — a no-code way to fully configure dev-term for a device: one JSON file (or a folder/zip of one, when a binary Kaitai `.ksy` reference is needed) bundling the declarative command/response schema from [device-control-modules.md](device-control-modules.md) together with a [UI definition](ui-definitions.md). Loadable and live: **Device > Device Manifest...** opens a text-protocol manifest as a working panel on the current session (templated commands, reply correlation, regex response patterns feeding indicators/charts); binary `.ksy` decoding is not built.
- [Connection profiles](connection-profiles.md) — named, saved connection configurations (the same fields as `CliOptions`, plus an optional reference to a [device manifest](device-manifests.md)), pickable from a menu in either front end at any time, not just at startup. Also covers the startup flow: valid config from args goes straight to the execution model, an incomplete one shows a Configure screen instead of hard-failing. Design only so far.
- [Session logging and playback](session-logging.md) — logger mode's versioned JSON Lines session-log format (header plus one lossless record per sent/received chunk and connect/disconnect event, with sequence numbers and monotonic timestamps), the passive `Session.AddObserver` tap that records it, and the injectable-clock playback engine (speeds, step, seek, fast-forward, presenter change, trim, notes) shared by the CLI, TUI and WPF. Implemented 2026-09-25; not yet verified against real hardware.
- [Front ends](frontends.md) — the console app (CLI + TUI modes) and the WPF GUI app, and how they share the core engine.
- [Platform, hosting & configuration](platform.md) — .NET 10+, dependency injection/Generic Host as the composition root, and the Options pattern for settings.
- [Testing](testing.md) — the `Unit`/`Integration` test categories (a hardware-backed `Integration` test preflights device presence and reports `Assert.Inconclusive` rather than needing its own category), the `.runsettings`-based opt-in for real-hardware tests, the WPF in-process automation approach (with two real gotchas found building it: a missing `DispatcherSynchronizationContext`, and double-connecting a session by both showing a window and calling its connect method directly), and the TUI in-process automation approach via Terminal.Gui's own official testing API (with its own two real gotchas: key injection and cross-thread `Application.Invoke` don't work at the same time, so headless and looped runs are two separate modes).

These documents describe intent and direction, not a finished spec — update them as design decisions are made or revisited, rather than letting the code and the docs drift apart.

## Features

[`features/`](features/) holds proposals/task docs that have actually been completed and verified —
moved out of `proposals/` once done, so that directory stays a list of what's still ahead. Each
still carries its own "Status" section with what was built and what was actually verified against
real hardware vs. assumed.

- [SCPI bench instrument control module](features/scpi-instrument-control.md) — **implemented** (2026-09-23) as `DevTerm.Devices.Scpi`, a data-driven profile mechanism (JSON command sets, no rebuild to add an instrument) for SCPI-compatible bench test equipment, sourced from a planning-stage project in `mwwhited-notes/shared`. The first real instance of the declarative command/response schema discussed in [device-control-modules.md](device-control-modules.md). Verified against one real instrument so far (HP/Agilent/Keysight 34401A over RS-232); the other five curated profiles remain unverified.
- [USBTMC bulk-IN reassembly fix](features/usbtmc-bulk-in-reassembly-fix.md) — **implemented** (2026-09-24): fixed the bug where a multi-transfer bulk-IN reply re-decoded a continuation transfer's raw bytes as a bogus header and hung forever, plus two compounding hardening gaps (unbounded reply size, no header integrity check). Verified against real DM3058E/DS1102E/DG1022 hardware; also fixed a DS1102E-specific "phantom empty reply right after connect" quirk found during that verification. The DG1022's separate bulk-IN stall was later root-caused and fixed by the protocol-conformance rework below.
- [USBTMC protocol-conformance rework](features/usbtmc-protocol-conformance.md) — **implemented** (2026-09-25):
  - EOM-driven multi-transfer reads with short-packet detection and packet-multiple buffers.
  - INITIATE_ABORT/CLEAR recovery on timeouts.
  - REN_CONTROL wValue fixed.
  - Leak-free device matching and serialized I/O.
  - A per-VID:PID `UsbtmcDeviceQuirks` table. Rigol 0x1AB1:0x0588 gets a 20 ms query→read-request delay and no REN. This was the DG1022's real root cause, verified on hardware.

  Verified on all four bench Rigols (DG1022, DS1102E, DG1062Z, DM3058E). It also found and fixed a data-toggle desync from clearing endpoint halts on open (the DG1062Z's "2-byte first read").
- [Tektronix 2230 protocol](features/tektronix-2230-protocol.md) — **implemented** (2026-09-23) as a minimal one-command (`ID?`) SCPI profile reusing `DevTerm.Devices.Scpi` as-is, since the pre-SCPI "codes" protocol needed no bespoke plumbing for just that command. Confirmed against the project's own two owned units; full command enumeration beyond `ID?` remains future work, and auto-detect doesn't apply (no `*IDN?`-equivalent).
- [Kuando Busylight protocol](features/kuando-busylight-protocol.md) — **implemented** (2026-09-22) as `DevTerm.Devices.Busylight`, a USB HID RGB status light module built against the generic `UiDefinition`/`IControlSurface` renderer. Confirmed live: the read path returns a real device identification report, and the light changes color (green/blue/red) via the single-command report format, including a custom RGB/HSV color-picker modal. The separate 64-byte batch-program format sends without error but has no visible effect and was removed from the UI as a confirmed no-op.
- [Velleman K8055 protocol](features/velleman-k8055-protocol.md) — **implemented** (2026-09-22) as `DevTerm.Devices.K8055`, the first concrete device module built against the generic `UiDefinition`/`IControlSurface` renderer. Verified live: Analog In/Digital In indicators matched an independent CLI hex reading exactly, and Digital Out/Analog Out/Counter-Reset commands round-tripped without error. Genuinely still open: the digital-in bit mapping, the trailing duration/debounce bytes, what command `0x06` does, and the TUI side.

## Proposals

[`proposals/`](proposals/) holds concrete feature proposals for specific transports, decoders, or
device control modules — narrower and more actionable than the docs above, which describe the
general contracts these proposals build on, and each grounded in an actual piece of target
hardware rather than a hypothetical. Each proposal notes where it came from at the top.

- [DER EE DE-5000 LCR meter protocol](proposals/de5000-lcr-meter-protocol.md) — a fully-specified, checksum-free 17-byte binary decoder (Cyrustek ES51919 chipset) reverse-engineered by the hobbyist community. Physically unusual: the meter's own optical/IR UART output is bridged to BLE via a custom-built adapter, so this is gated on the not-yet-built BLE Serial transport rather than a decoder gap — but that transport already has real target hardware pushing for it. A second real `ICompositeDecoder`/bitfield candidate now that Favero is shelved.
- [Radex One geiger counter protocol](proposals/radex-one-protocol.md) — a fully-specified binary protocol (framing, checksum, four command types; decoder + control surface) for a USB geiger counter, sourced from a finished reverse-engineering writeup in `mwwhited-notes/shared`. The device turned out to enumerate as USB HID, not a virtual COM port as the source doc assumed — so this is now gated on the not-yet-built USB HID transport, not just decoder work.
- [EByte E810-DTU(RS485) config protocol](proposals/ebyte-e810-dtu-config-protocol.md) — a UDP broadcast-based discovery/configuration protocol (port 1901) for an Ethernet-to-RS485 bridge, conceptually similar to the USR-TCP232-302 already in dev-term but from a different vendor with its own protocol. Sourced from local reverse-engineering notes (`dotex/Incoming/BinaryDecoders`), not yet a finished spec — a byte-count check already found a discrepancy worth resolving before implementing. Needs the not-yet-built UDP transport.
- [Zoom H4n remote control protocol](proposals/zoom-h4n-remote-protocol.md) — a consumer audio recorder's remote-control port, accessed via a custom-built serial adapter (`h4n2rs485`) that already exists. Plain serial, 2400-8-N-1, needs no new transport — cross-referenced against two independent public reverse-engineering writeups, plus a real initialization-handshake quirk worth preserving.
- [BYTECC BT-UP01 USB-over-network bridge](proposals/bytecc-bt-up01-usb-network-bridge.md) — a research starting point, not a spec: no reverse-engineering exists yet for this device, and none was found publicly either. Fundamentally different in kind from every other proposal here — tunneling USB itself over a network (device enumeration, control/bulk/interrupt transfers) rather than decoding one device's byte protocol over an existing transport. Recommends checking two things before any real work: whether the vendor's own client software just makes the remote device look local (no dev-term work needed at all if so), and whether the box happens to already speak the open USB/IP protocol before assuming anything proprietary.
- [Stream content detection & rendering window](proposals/stream-content-detection.md) — an optional front-end window that watches a live session for HPGL/PostScript/PCL/binary-image replies (via a declared per-command response-format hint, e.g. on a SCPI command, or by sniffing known signatures) and captures/exports them, phased so the TUI's auto-save-only behavior and WPF's native-image-format preview both ship before the harder HPGL/PostScript/PCL rendering-presenter work from [presenters.md](presenters.md) §3 is built. **Phase 1 built 2026-09-25** as the Stream Monitor (Device > Stream Monitor... in TUI/WPF; `DevTerm.Core.StreamContent` + `DevTerm.Configuration.StreamMonitor`; see [docs/specs/stream-monitor.md](../specs/stream-monitor.md)); unit-tested only, not yet verified against real hardware. Phase 2 (HPGL/PostScript/PCL preview/rasterize) not started.

## Diagrams

Diagrams are embedded directly in the markdown as fenced ` ```plantuml ` code blocks. Structural/architecture diagrams (system context, containers, components) follow the [C4 model](https://c4model.com) using the standard [C4-PlantUML](https://github.com/plantuml-stdlib/C4-PlantUML) macros, pulled in via `!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/...` — rendering these requires a PlantUML setup that allows remote `!include`s (the public PlantUML server does; a fully offline renderer needs a local copy of the C4-PlantUML stdlib instead). Sequence diagrams use plain `@startuml`/`@enduml`, and UI wireframes use `@startsalt`/`@endsalt` — neither needs the C4 include.
