# Design Documents

Living design docs for dev-term, written during the pre-implementation design phase. Each doc covers one concern and cross-links to the others; "Open questions" sections track decisions not yet made.

- [Architecture overview](architecture.md) — core abstractions (session, transport, presenter, pipeline, plugin host, front ends) and how data flows between them.
- [Transport layer](transports.md) — the `ITransport` contract and the initial transports: serial, TCP (client + listener), UDP (target + listener), USB HID (HidSharp), BLE (cross-platform via a pluggable per-OS adapter seam, "BLE Serial"/Nordic UART Service as the common device pattern). Also covers why USBTMC isn't in that list — it needs its own raw-USB transport; GPIB is out of scope (decided 2026-10-03).
- [RFC 2217](rfc2217.md) — client mode (connect to a remote serial port, e.g. `ser2net`) is built and selectable as `--transport rfc2217`, and verified against a real ser2net server in `containers/` (automated as `Ser2NetIntegrationTests`; not yet against real hardware behind one); server mode (expose a local serial connection to the network) is still design-only. Flags that "RFC2217" in a vendor's marketing copy isn't proof of standard compliance — confirmed against a real target device.
- [VXI-11 transport](vxi11-transport.md) — **implemented** (2026-10-03): `--transport vxi11 --host <ip>`, an ONC-RPC core-channel client for LXI instruments with no raw SCPI port; verified against the Rigol DG1062Z.
- [USBTMC transport](usbtmc-transport.md) — a raw-USB transport (WinUSB or LibUsbDotNet) for the USB Test & Measurement Class most local-USB bench equipment (Rigol/Keysight/etc.) actually uses; not HID, not a virtual COM port. Explicitly rules out IVI.NET/VISA (Windows/.NET-Framework-oriented, plus a separate proprietary native runtime install) in favor of implementing the protocol directly, matching how Serial/HID already avoid a vendor-driver dependency. **Implemented** and verified against all four bench Rigol instruments (DM3058E, DS1102E, DG1062Z, DG1022) — see the [USBTMC protocol-conformance rework](features/usbtmc-protocol-conformance.md) feature entry below.
- [Presenters & encodings](presenters.md) — text/numeric-base views; protocol decoders (device and network protocols) that always produce a human-readable text baseline; rendering presenters (HPGL/PostScript/PCL, telemetry plots) with export to SVG/PNG/JPG; composite/channelized decoders for interlaced telemetry; and mappable presenters (external name/label/unit maps, e.g. Modbus register maps) so one decoder plugin serves many devices.
- [Plugin model](plugin-model.md) — how transports and presenters are packaged, discovered, versioned, loaded, and registered into the DI container.
- [Device control modules](device-control-modules.md) — plugins that bundle an outbound control surface (commands/parameters, e.g. for driving test equipment) with telemetry decode/present/plot for the response, composed from the existing transport/presenter contracts.
- [UI definitions](ui-definitions.md) — a framework-agnostic, JSON/XML-serializable model (`DevTerm.UiDefinitions`) for declaring a control panel's layout once so every front end renders it generically. Rendered generically by both front ends' control panels against a live `IControlSurface` (K8055, Busylight, SCPI, device manifests); includes a serializable `ValueConstraint` (data type/bounds, independent of the widget) checked by one shared `ValueValidator`, display-only bar graph, strip chart, and vector/coordinate controls fed by live decoder values, and the forms engine: attributes on any model plus a reflection-based generator produce a `UiDefinition` that both front ends' form renderers draw two-way bound to the model (the Connection Editor's fields, the manifest editor's forms), with visibility conditions on sections and controls.
- [Device manifests](device-manifests.md) — a no-code way to fully configure dev-term for a device: one JSON file (or a folder/zip of one, when a binary Kaitai `.ksy` reference is needed) bundling the declarative command/response schema from [device-control-modules.md](device-control-modules.md) together with a [UI definition](ui-definitions.md). Loadable and live: **Device > Device Manifest...** opens a text-protocol manifest as a working panel on the current session (templated commands, reply correlation, regex response patterns feeding indicators/charts); validated on every load (the same checks the manifest editor runs before saving), and editable with a live panel preview via **Device > Edit Device Manifest...**; binary `.ksy` decoding is not built.
- [Connection profiles](connection-profiles.md) — named, saved connection configurations (the same fields as `CliOptions`, plus an optional reference to a [device manifest](device-manifests.md)), pickable from a menu in either front end at any time, not just at startup. Also covers the startup flow: valid config from args goes straight to the execution model, an incomplete one shows a Configure screen instead of hard-failing. **Implemented** (2026-09-15 through 2026-09-18): Device Profiles menu in both front ends, live mid-session profile switching, Connect/Disconnect toggle, import/export (including zip), shared view-model logic between TUI/WPF.
- [Observability](observability.md) — opt-in (`--otlp`) OpenTelemetry export of dev-term's own session traces and byte/connection metrics over OTLP; core always records, `DevTerm.Observability` exports.
- [Session logging and playback](session-logging.md) — logger mode's versioned JSON Lines session-log format (header plus one lossless record per sent/received chunk and connect/disconnect event, with sequence numbers and monotonic timestamps), the passive `Session.AddObserver` tap that records it, and the injectable-clock playback engine (speeds, step, seek, fast-forward, presenter change, trim, notes) shared by the CLI, TUI and WPF. Implemented 2026-09-25; not yet verified against real hardware.
- [Theming](theming.md) — light/dark/system plus user-defined JSON themes for both front ends: semantic color roles in `DevTerm.Configuration`, the selection kept as an app preference (`~/.dev-term/preferences.json`, never in a profile), WPF via per-window role brushes plus dark-capable replacement templates, the TUI via Terminal.Gui scheme overrides. Records why .NET's Fluent `ThemeMode` (still experimental, re-templates with bigger metrics, transparent dark background) and Terminal.Gui's own Dark/Light themes (terminal-default backgrounds) weren't used. Implemented 2026-09-25.
- [Front ends](frontends.md) — the console app (CLI + TUI modes) and the WPF GUI app, and how they share the core engine.
- [Multiple sessions per window](multi-session-ui.md) — extracting today's window-level `Session`/`PresenterCatalog`/output/send-history state into a per-tab `SessionTab` unit, so both front ends' main windows can hold more than one open connection at once. Reuses `DevTermSessionBuilder` unchanged. **Implemented** (2026-09-30, all four steps): `SessionTab` extracted; both WPF's `MainWindow` (`TabControl`) and the TUI's `TuiMode` (`Terminal.Gui.Views.Tabs`) wire File > New Session/Close Session; session logging and the Stream Monitor are per-tab; closing the last tab reaches a zero-tab state instead of exiting; Ctrl+T/Ctrl+W/Ctrl+Tab/Ctrl+Shift+Tab shortcuts. `docs/specs/tui-main-screen.md`/`docs/specs/wpf-main-window.md`/`docs/user-guide/multiple-sessions.md` document it in full.
- [Platform, hosting & configuration](platform.md) — .NET 10+, dependency injection/Generic Host as the composition root, and the Options pattern for settings.
- [Testing](testing.md) — the `Unit`/`Integration` test categories (a hardware-backed `Integration` test preflights device presence and reports `Assert.Inconclusive` rather than needing its own category), the `.runsettings`-based opt-in for real-hardware tests, the WPF in-process automation approach (with two real gotchas found building it: a missing `DispatcherSynchronizationContext`, and double-connecting a session by both showing a window and calling its connect method directly), and the TUI in-process automation approach via Terminal.Gui's own official testing API (with its own two real gotchas: key injection and cross-thread `Application.Invoke` don't work at the same time, so headless and looped runs are two separate modes).

These documents describe intent and direction, not a finished spec — update them as design decisions are made or revisited, rather than letting the code and the docs drift apart.

## Features

[`features/`](features/) holds proposals/task docs that have actually been completed and verified —
moved out of `proposals/` once done, so that directory stays a list of what's still ahead. Each
still carries its own "Status" section with what was built and what was actually verified against
real hardware vs. assumed.

- [LXI support](features/lxi-support.md) — **implemented** (2026-10-03): network-connected bench-instrument support. The common raw-socket-SCPI case needs no new code (the existing TCP transport + SCPI module already cover it); the actual new work is LXI discovery (Phase 1, built: a VXI-11 portmapper broadcast plus an `*IDN?` probe, since mDNS got no reply from the real instrument) and an ONC-RPC VXI-11 client for instruments that need it (Phase 2, gated on a confirmed real instrument). Complete for now: Phase 1 built, VXI-11 (Phase 2) deliberately deferred until an instrument needs it (Rigol DG1062Z, raw SCPI on 5555, VXI-11 portmapper open).
- [`.ksy` importer and binary frames](features/ksy-importer.md) — a fixed-layout binary frame declared in a manifest (`Inbound.Frame`: sync bytes, typed fields, scale/offset, magic constants), decoded by `ManifestFramePresenter` into live values the picker, charts and indicators read like a regex capture; `KsyImporter` generates one from a Kaitai Struct file. **Built 2026-10-02 (model, decoder, presenter, catalog paths, validator, importer, and the Binary frame / Import entries in both manifest editors); checked live against a real Radex One only.**
- [Schema files for custom formats](features/format-schema-files.md) — a generated JSON Schema per hand-authored format (device manifest, UI definition, connection profile, and the planned binary-frame schema from the `.ksy` importer), exported from the C# model with `JsonSchemaExporter` regenerated by a Debug build and checked by a drift test, so editors and the importer can validate files without loading dev-term. **Implemented 2026-10-02** for manifest, UI definition and connection profile; the `.ksy` frame schema is not built.
- [Stream content detection & rendering window](features/stream-content-detection.md) — **implemented** (Phase 1 2026-09-25, conversion 2026-10-01/02): the Stream Monitor (Device > Stream Monitor... in TUI/WPF) watches a live session for HPGL/PostScript/PCL/binary-image replies, by a declared per-command response-format hint or by sniffing signatures, and captures and exports them; "Convert..." turns a capture into SVG/PNG with the internal HP-GL converter or an external tool, and WPF previews images and SVG. Verified on a real DG1062Z and TDS2024 (BMP) and a Tektronix 2230 (HP-GL). Not built, now in `BACKLOG.md`: live PostScript/PCL rendering, SVG drawing in the TUI, CLI export, export-folder cleanup. See [docs/specs/stream-monitor.md](../specs/stream-monitor.md).
- [Several converter tools for the Stream Monitor](features/stream-converter-tools.md) — **implemented** (2026-10-02): an app-wide list of named external converters (Ghostscript, GhostPCL...), edited from Device > Converter Tools... in both front ends and stored in `~/.dev-term/converter-tools.json`, each declaring the formats it handles; Convert... runs the chosen one, or "Auto" picks by capture format. Verified with real Ghostscript and GhostPCL runs.
- [Theme builder](features/theme-builder.md) — **implemented** (2026-10-01): an in-app UI (color pickers per `ThemeRole`, live preview via the existing `ActiveTheme` mechanism, live contrast feedback) for creating/editing `ThemeFile`s in both the TUI and WPF, built on the [theming.md](theming.md) storage/loading model. Unit-tested, and reviewed by hand in both front ends 2026-10-02.
- [SCPI bench instrument control module](features/scpi-instrument-control.md) — **implemented** (2026-09-23) as `DevTerm.Devices.Scpi`, a data-driven profile mechanism (JSON command sets, no rebuild to add an instrument) for SCPI-compatible bench test equipment, sourced from a planning-stage project in `mwwhited-notes/shared`. The first real instance of the declarative command/response schema discussed in [device-control-modules.md](device-control-modules.md). Verified against one real instrument so far (HP/Agilent/Keysight 34401A over RS-232); the other five curated profiles remain unverified.
- [USBTMC bulk-IN reassembly fix](features/usbtmc-bulk-in-reassembly-fix.md) — **implemented** (2026-09-24): fixed the bug where a multi-transfer bulk-IN reply re-decoded a continuation transfer's raw bytes as a bogus header and hung forever, plus two compounding hardening gaps (unbounded reply size, no header integrity check). Verified against real DM3058E/DS1102E/DG1022 hardware; also fixed a DS1102E-specific "phantom empty reply right after connect" quirk found during that verification. The DG1022's separate bulk-IN stall was later root-caused and fixed by the protocol-conformance rework below.
- [USBTMC protocol-conformance rework](features/usbtmc-protocol-conformance.md) — **implemented** (2026-09-25):
  - EOM-driven multi-transfer reads with short-packet detection and packet-multiple buffers.
  - INITIATE_ABORT/CLEAR recovery on timeouts.
  - REN_CONTROL wValue fixed.
  - Leak-free device matching and serialized I/O.
  - A per-VID:PID `UsbtmcDeviceQuirks` table. Rigol 0x1AB1:0x0588 gets a 20 ms query→read-request delay and no REN. This was the DG1022's real root cause, verified on hardware.

  Verified on all four bench Rigols (DG1022, DS1102E, DG1062Z, DM3058E). It also found and fixed a data-toggle desync from clearing endpoint halts on open (the DG1062Z's "2-byte first read").
- [Tektronix 2230 protocol](features/tektronix-2230-protocol.md) — **implemented** (2026-09-23) as a minimal one-command (`ID?`) SCPI profile reusing `DevTerm.Devices.Scpi` as-is, since the pre-SCPI "codes" protocol needed no bespoke plumbing for just that command. Confirmed against the project's own two owned units; full command enumeration beyond `ID?` remains future work, and auto-detect doesn't apply (no `*IDN?`-equivalent).
- [Kuando Busylight protocol](features/kuando-busylight-protocol.md) — **implemented** (2026-09-22) as `DevTerm.Devices.Busylight`, a USB HID RGB status light module built against the generic `UiDefinition`/`IControlSurface` renderer. Confirmed live: the read path returns a real device identification report, and the light changes color (green/blue/red) via the single-command report format, including a custom RGB/HSV color-picker modal. The separate 64-byte batch-program format sends without error but has no visible effect and was removed from the UI as a confirmed no-op.
- [Velleman K8055 protocol](features/velleman-k8055-protocol.md) — **implemented** (2026-09-22) as `DevTerm.Devices.K8055`, the first concrete device module built against the generic `UiDefinition`/`IControlSurface` renderer. Verified live: Analog In/Digital In indicators matched an independent CLI hex reading exactly, and Digital Out/Analog Out/Counter-Reset commands round-tripped without error. Genuinely still open: the digital-in bit mapping, the trailing duration/debounce bytes, what command `0x06` does, and the TUI side.
- [Radex One geiger counter protocol](features/radex-one-protocol.md) — **implemented and verified against real hardware** (`DevTerm.Devices.RadexOne`: framer, decoder, control surface, `UiDefinition`, wired into both front ends' Device menus) — confirmed 2026-09-26 on COM8 at 9600 8N1, decoding a real reading end-to-end (`RealHardwareRadexOneTests`), after [061](../bugs/resolved/061-radexone-wrong-baud-rate.md) corrected an earlier, unverified "2400 baud" claim, and re-confirmed 2026-09-29 (`docs/test/2026-09-29-11-52-14.md`). Only the `readData` query has been run against real hardware; `readSerialVersion`/`readSettings`/`resetAccumulated`/`writeSettings` remain unverified.
- [NMEA 0183 GPS sentence decoder](features/nmea-gps-protocol.md) — **implemented and verified against real hardware** (`DevTerm.Devices.Nmea`: sentence parser, decoder, a deliberately no-op control surface, `UiDefinition`, wired into both front ends' Device menus as "NMEA 0183..."), a generic protocol decoder (GGA/RMC/GSA/GSV/VTG) not tied to any one receiver — gated on the one confirmed-compatible unit's VID/PID (DeLorme Earthmate GPS BT-20, USB HID). Unit-tested against real, independently-computed-checksum sentences, and confirmed 2026-09-29 against a real Earthmate BT-20 (`docs/test/2026-09-29-14-08-11.md`), decoding a real `$GPRMC` sentence end-to-end.
- [Zoom H4n remote control protocol](features/zoom-h4n-remote-protocol.md) — **implemented and verified against real hardware** (`DevTerm.Devices.ZoomH4n`: decoder, control surface with the init-handshake watcher, `UiDefinition`, wired into both front ends' Device menus). Confirmed 2026-10-01 against a real H4n via the `h4n2rs485` adapter on COM5 (`docs/test/2026-10-01-08-15-06.md`): the init handshake completes and a button command (`mic`) sends without fault or timeout. Only that one path was exercised — the other 11 buttons and the exact status-bitmask semantics against a live unit remain unconfirmed.
- [Loopback sample rate control](features/loopback-sample-rate.md) — **implemented** (2026-10-01): a configurable `SampleIntervalMs` delay between the Loopback transport's scripted streaming responses (`Samples: N`, `Send Events: N`), wired through CLI, configuration and both front ends' connection editors, so streaming UI (strip charts, Stream Monitor captures) can be demoed at a believable cadence. Verified by unit tests and checked live in both front ends (2026-10-02); captured stills and GIFs are in the user guide.
- [Expression picker, value-path catalog and CEL-style language](features/expression-picker-paths-and-cel.md) — enumerate every valid value path from a manifest (patterns, `.ksy` fields, controls, parameters) with type/range/unit, generate realistic sample data for previews, a picker control in both front ends that builds valid expressions, and a CEL-style language (regex `matches()`, strings, lists). **Implemented (2026-10-02)** and unit/screenshot-tested, not driven against a real device (it has no device-side behavior); the CEL-style language extends our own `Expression` rather than using a library. Picker buttons for the newer text/list functions are in `BACKLOG.md`.
- [Manifest editor expression builder](features/manifest-editor-expression-builder.md) — a small, dev-term-owned arithmetic expression grammar letting a device manifest's display controls and button parameters derive a value (unit conversion, scale/offset) from live decoder values instead of only binding to one raw value verbatim. **Built 2026-10-01** (`IndicatorControl.Expression`, `ChartChannel.Expression`, `ButtonControl.ParameterExpressions`); unit- and screenshot-tested in both front ends; no device-side behavior, so no hardware pass applies. Extended 2026-10-02 by the picker, value-path catalog, binary frames and `.ksy` importer.

## Proposals

[`proposals/`](proposals/) holds concrete feature proposals for specific transports, decoders, or
device control modules — narrower and more actionable than the docs above, which describe the
general contracts these proposals build on, and each grounded in an actual piece of target
hardware rather than a hypothetical. Each proposal notes where it came from at the top.

- [DER EE DE-5000 LCR meter protocol](proposals/de5000-lcr-meter-protocol.md) — **implemented** (`DevTerm.Devices.De5000`: framer, decoder, a deliberately no-op control surface, `UiDefinition`, wired into both front ends' Device menus, gated on "any BLE connection"), but not yet verified against real hardware — the custom optical-to-BLE adapter's GATT profile (Nordic UART Service assumed) is still unconfirmed, since no adapter was paired this session.
- [EByte E810-DTU(RS485) config protocol](proposals/ebyte-e810-dtu-config-protocol.md) — a UDP broadcast-based discovery/configuration protocol (port 1901) for an Ethernet-to-RS485 bridge, conceptually similar to the USR-TCP232-302 already in dev-term but from a different vendor with its own protocol. Sourced from local reverse-engineering notes (`dotex/Incoming/BinaryDecoders`), not yet a finished spec — a byte-count check already found a discrepancy worth resolving before implementing. Needs the not-yet-built UDP transport.
- [BYTECC BT-UP01 USB-over-network bridge](proposals/bytecc-bt-up01-usb-network-bridge.md) — a research starting point, not a spec: no reverse-engineering exists yet for this device, and none was found publicly either. Fundamentally different in kind from every other proposal here — tunneling USB itself over a network (device enumeration, control/bulk/interrupt transfers) rather than decoding one device's byte protocol over an existing transport. Recommends checking two things before any real work: whether the vendor's own client software just makes the remote device look local (no dev-term work needed at all if so), and whether the box happens to already speak the open USB/IP protocol before assuming anything proprietary.
- [Web-accessible host service (WebSocket tunnels + Blazor front end)](proposals/web-tunnel-blazor-frontend.md) — a fourth front end reaching a running session from a browser over WebSockets, tunneling the existing `Session`/`Pipeline` output rather than adding a new transport. Implemented 2026-10-02 as `DevTerm.Web`: loopback-only by default, a shared access token, https required off loopback, one shared session over a `/ws` WebSocket and a single static page. A read-only token and a generic `UiDefinition` panel renderer (K8055/Busylight, JSON at `/api/panel`, no Blazor) were added 2026-10-03.
- [Network device discovery](proposals/network-device-discovery.md) - one Detect action for any network device (LXI, serial bridges, mDNS/SSDP) that pre-fills the connection editor. Proposed 2026-10-03, not built.
- [In-app config editors for network bridges](proposals/network-device-config-editors.md) - Device > Configure device for the USR-TCP232-302 and EByte E810-DTU. Proposed 2026-10-03, not built.
- [Cross-process session channel](proposals/cross-process-control-channel.md) - a read-only named pipe per live session (`SessionPipeServer`, built, not yet in a front end) so another process can tail traffic; read-write and a localhost web service are open.
- [Plugin-contributed panels](proposals/plugin-contributed-panels.md) - an `IDevicePanelContribution` so a plugin adds a Device-menu control panel; the prerequisite for moving the built-in device decoders out of the core references. Contract built; TUI and WPF menus use it, web and the decoder move still to do.
- [Out-of-process plugins](proposals/out-of-process-plugins.md) - a presenter run as a child process in any language over stdin/stdout JSON lines (`ExternalProcessPresenter`, built); Python, Java and Go examples tested; loaded from `plugin.json` after user approval, remembered per content hash.
- [MQTT / AMQP / STOMP protocol support](proposals/message-broker-protocols.md) — message-broker transports (one plugin per protocol) for topic-addressed pub/sub, pairing with the existing `IControlSurface`/`UiDefinition` pattern for outbound triggering. Flags the biggest open question as whether topic-addressed messages need a `Pipeline`/`Session` model change for per-topic presenter routing, something nothing built so far has needed. MQTT, AMQP 0-9-1 and STOMP 1.2 are implemented (topic/routing-key-prefixed text, verified against the Mosquitto and RabbitMQ containers). A routing proxy (device lines to a broker and back, rules in the profile) has a Routing window in WPF and the TUI.
- [Z-Wave support](proposals/z-wave-support.md) — controller frame decode/encode and basic single-node control (Binary Switch, Basic Get/Set, Multilevel Switch) for a Z-Stick or Z-Wave Raspberry Pi HAT, both serial-attached (no new transport needed). The project's first real candidate for the Kaitai Struct (`.ksy`) binary-decoding path referenced in [device-manifests.md](device-manifests.md) (the importer and binary-frame decoder have since been built, see [ksy-importer](features/ksy-importer.md)). Not started — design only; no Z-Wave hardware confirmed on hand yet.

## Diagrams

Diagrams are embedded directly in the markdown as fenced ` ```plantuml ` code blocks. Structural/architecture diagrams (system context, containers, components) follow the [C4 model](https://c4model.com) using the standard [C4-PlantUML](https://github.com/plantuml-stdlib/C4-PlantUML) macros, pulled in via `!include https://raw.githubusercontent.com/plantuml-stdlib/C4-PlantUML/master/...` — rendering these requires a PlantUML setup that allows remote `!include`s (the public PlantUML server does; a fully offline renderer needs a local copy of the C4-PlantUML stdlib instead). Sequence diagrams use plain `@startuml`/`@enduml`, and UI wireframes use `@startsalt`/`@endsalt` — neither needs the C4 include.
