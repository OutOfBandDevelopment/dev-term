# RFC 2217 (Telnet Com Port Control Option)

## Purpose

Describes dev-term's planned support for [RFC 2217](https://www.rfc-editor.org/rfc/rfc2217), in both directions:

- **Client mode** — dev-term connects to a remote RFC 2217 server (e.g. `ser2net`, a USB-to-Ethernet serial gateway) and controls that remote serial port — baud rate, parity, DTR/RTS, break — over the network as if it were local.
- **Server mode** — dev-term exposes a serial connection *it* holds to the network, so a remote RFC 2217 client (another dev-term instance, `ser2net`-compatible tooling, pyserial's `rfc2217://` client, etc.) can control it as if it were local to them.

These two roles are architecturally different shapes (see below) and are designed together here so the wire-format logic is shared, but are expected to be *built* client-first, server-second — see `TODO.md`.

## What RFC 2217 actually is

Plain "serial over TCP" (what most naive bridges do, including dev-term's own `DevTerm.Transports.Tcp` today) only carries the raw data bytes. RFC 2217 layers a **control channel** on top of a normal Telnet connection, using Telnet's option-negotiation mechanism (`IAC WILL`/`DO`/`SB ... COM-PORT-OPTION ... SE`) to also carry:

- Baud rate, data size, parity, stop size (`SET-BAUDRATE`, `SET-DATASIZE`, `SET-PARITY`, `SET-STOPSIZE`)
- Flow control and modem control lines — DTR, RTS, break — via `SET-CONTROL`'s many sub-values
- Line state / modem state change notifications pushed from server to client (`NOTIFY-LINESTATE`, `NOTIFY-MODEMSTATE`)
- Buffer purge requests (`PURGE-DATA`)
- Flow-control suspend/resume signaling

One TCP connection carries two logically distinct things: the **data stream** (actual serial bytes, Telnet-escaped — a literal `0xFF` byte in the data must be doubled per Telnet's `IAC IAC` escaping) and the **control stream** (Telnet subnegotiations for `COM-PORT-OPTION`, RFC 2217's option number 44).

## Shared codec

A pure, protocol-only codec — tentatively `Rfc2217Codec` in a new `DevTerm.Transports.Rfc2217` project — used by **both** roles:

- Telnet IAC escaping/unescaping of the data channel (`0xFF` → `0xFF 0xFF` and back).
- Encoding/decoding `COM-PORT-OPTION` subnegotiation frames: both the client→server *requests* (`SET-BAUDRATE`, `SET-CONTROL`, ...) and the server→client *notifications* (`NOTIFY-LINESTATE`, `NOTIFY-MODEMSTATE`, and echoed acknowledgements of a `SET-*` request).

Kept deliberately allocation-conscious and fully unit-testable (no I/O) — encode a command to bytes, decode bytes to a command — verified byte-for-byte against the formats RFC 2217 documents, the same way `NumericBasePresenter` or `LineEnding` are pure/tested today. Both the client transport and the server bridge depend on this codec, using it in opposite directions.

## Client mode

Fits the existing `ITransport` contract exactly, alongside `SerialTransport` and `TcpTransport`:

- `Rfc2217Transport : ITransport` — opens a TCP connection (reusing the same connect/stream patterns as `DevTerm.Transports.Tcp`), performs the Telnet option negotiation (`WILL`/`DO COM-PORT-OPTION`), then sends `SET-BAUDRATE`/`SET-DATASIZE`/`SET-PARITY`/`SET-STOPSIZE`/`SET-CONTROL` to configure the *remote* port. From the caller's side this is the same configuration surface as `SerialTransportOptions` (baud, data bits, parity, stop bits, DTR, RTS) — `Rfc2217TransportOptions` mirrors it, plus `Host`/`Port` like `TcpTransportOptions`, since it's "a serial port, reached over the network."
- The data channel needs de-escaping on read and escaping on write, and has to tolerate control-channel subnegotiations arriving interleaved with data on the same TCP stream without corrupting either — a small Telnet-aware framing layer sits between the raw socket stream and `StreamToPipePump`, rather than handing the socket straight to the pump the way `TcpTransport` does today.
- `OpenAsync`/`CloseAsync` map onto TCP connect + Telnet/COM-PORT-OPTION negotiation, and TCP disconnect, respectively.

## Server mode

Structurally different from every other transport: this isn't "dev-term's own session talking to a device," it's "dev-term *sharing* a device it's already connected to." It composes an existing connection rather than being one itself:

- A new component — tentatively `Rfc2217ServerBridge`, **not** an `ITransport` — takes an already-open `ITransport` (in practice a `SerialTransport`, though nothing rules out bridging a `TcpTransport` connection) and a TCP listen port. For each connecting client it performs the server side of Telnet/`COM-PORT-OPTION` negotiation, forwards data bidirectionally between the local connection and the network client, applies incoming `SET-*` control requests to the real local port (a remote `SET-BAUDRATE` actually changes the physical port's baud rate), and reports the real port's line/modem state back as `NOTIFY-*` subnegotiations.
- CLI surface is a bolt-on to an existing session, not a `--transport` choice of its own — e.g. `dev-term --transport serial --port COM3 ... --rfc2217-listen 2217` — since server mode needs *both* a live local connection and a network listener at once, unlike the client role which only needs the network side.
- v1 policy question (mirrors the TCP listener's existing one-peer-at-a-time v1 policy — see [transports.md](transports.md)): one remote client at a time, since `COM-PORT-OPTION` control is inherently stateful per connection and it's unclear what "two remote clients both issuing `SET-BAUDRATE`" should even mean.

## Testing strategy

Real-protocol verification against an independent implementation, not just unit tests of the codec — the same approach that caught the DTR-default and read-cancellation issues in `SerialTransport` this session:

- **Client role**: verify against pyserial's reference `rfc2217_server.py` example — a real, independent RFC 2217 server — the same way pyserial was used earlier to confirm COM3's actual behavior before trusting dev-term's own implementation.
- **Server role**: verify against pyserial's `serial.rfc2217.Serial(...)` client — dev-term acts as the server, pyserial connects as the client and exercises remote baud-rate/DTR/RTS changes, confirming they actually reach the physical port.

## Vendor-specific variants are common — verify before assuming compatibility

Not every device advertising "RFC2217" actually speaks the IETF standard. Case in point, one of the concrete devices this is meant to support — the [USR-TCP232-302](https://shop.usriot.com/1-port-rs232-to-ethernet-converters-usr-tcp232-302.html) RS232-to-Ethernet converter — documents its own protocol as **"Customized RFC2217"**: *"Users can dynamically modify the baud rate, stop bit, data bits and parity bit of the TCP232-302 by sending PUSR customized protocol over the network."* That's a vendor-specific (PUSR) protocol that borrows RFC 2217's *concepts* (remote line-parameter control) without necessarily matching its wire format — a standards-compliant `Rfc2217Transport` client is not guaranteed (and shouldn't be assumed) to interoperate with it.

Practically, for this device specifically:

- It also supports plain **TCP Server / TCP Client** modes (transparent passthrough — the same shape `DevTerm.Transports.Tcp` already implements today). Configuring the device's serial parameters once via its own AT-command or web interface, then talking to it as a raw TCP byte pipe, **works right now with no new code** — the right near-term path if the attached instrument doesn't need its baud rate/parity changed mid-session from dev-term.
- Genuine, on-the-fly remote reconfiguration (matching what `Rfc2217Transport` gives against a real RFC 2217 server like `ser2net`) would need a **separate, vendor-specific transport** implementing PUSR's actual documented protocol — not an extension of `Rfc2217Codec`, since there's no reason to assume the two are wire-compatible. Not designed here; would need PUSR's own protocol reference before starting.
- **Action before building anything RFC-2217-shaped against a specific device: confirm which protocol it actually implements from the vendor's own docs**, the same way this was just checked here — "RFC2217" in marketing copy is not sufficient confirmation.

## Security note

RFC 2217 itself has no authentication or encryption — it's plain Telnet-over-TCP. Server mode means *anyone who can reach the listening port can control the attached serial device* (change its baud rate, assert/deassert DTR/RTS, send arbitrary bytes to whatever's attached). This is a real exposure once server mode exists, not a hypothetical one. At minimum: default the listener to bind loopback-only (`127.0.0.1`) rather than all interfaces, require an explicit opt-in to bind externally, and call this out clearly in user-facing docs/CLI help — real authentication/encryption (e.g., requiring a tunnel) is out of scope for v1 but should stay an explicit, documented limitation rather than a silent gap.

## Open questions

- Exact project/class layout for the server bridge: inside `DevTerm.Transports.Rfc2217` alongside the client (sharing the codec easily) vs. its own project.
- CLI/config surface for enabling server mode alongside an existing session — is it serial-only, or should bridging a `TcpTransport` connection out via RFC 2217 also be supported?
- Multi-client policy for server mode beyond v1's one-at-a-time (queue additional connections? reject them outright? read-only observers permitted alongside one read/write controller?).
- How `NOTIFY-LINESTATE`/`NOTIFY-MODEMSTATE` (server→client informational pushes) surface to the user in client mode — purely internal state the transport tracks, or something presenter-visible (e.g., a "modem status changed" event a future device control module could react to — see [device-control-modules.md](device-control-modules.md))?
- Whether `Rfc2217Transport` should reuse `DevTerm.Transports.Tcp`'s `ITcpConnectionSource`/`ITcpConnection` abstractions directly (composition) or define its own, given it needs the same dial-out/accept shapes but with the Telnet framing layer in between.
- Whether a dedicated vendor-specific transport for PUSR's "customized RFC2217" protocol (see above) is worth building at all, versus just using `DevTerm.Transports.Tcp`'s existing plain-passthrough mode against devices like the USR-TCP232-302 and configuring their serial parameters out-of-band (AT commands / the device's web UI).
