- Opened the "Other BLE" saved profile from **both** the TUI (`ConfigureMode`) and the WPF

## Findings

- **The new BLE GATT characteristic picker UI (write/notify) is confirmed working against real
  hardware, from both front ends** — this was the one piece of this session's work that had only been
  build/unit-test verified until now (see `docs/changes/2026-09-29.md`'s "Not yet done" note, now
  addressed).
- **Root cause progress on the reconnect failure: the reconnect only fails if the TTL-serial-side
  peripheral hasn't been reset since the first disconnect.** This reframes the failure from "unknown,
  possibly a Windows BLE stack timing quirk" (as left in `TODO.md`) to "likely the peripheral's own
  GATT server doesn't cleanly re-arm for a new central connection after the first central
  disconnects" — a firmware/hardware behavior of the bridge module itself, not necessarily a defect
  in dev-term's own `BleTransport`/`WindowsBleAdapter` code. This is consistent with `TODO.md`'s
  existing note that `WindowsBleAdapter.Cleanup()` already disposes cleanly and unsubscribes both
  event handlers on every close — there was never a clear dev-term-side leak to point to, and this
  finding explains why: the failure isn't on dev-term's side of the link.
  - Not yet isolated further: whether "reset" means power-cycling the module, its physical reset pin,
    or something Windows-side (e.g. forgetting/re-pairing) that happens to coincide with a physical
    reset. Whether the module simply stops advertising after a central disconnects (so
    `ConnectAsync`'s failure is really "no advertisement found", surfacing as a generic cancellation)
    is the leading theory but wasn't directly confirmed here (e.g. by scanning for its advertisement
    with `--listbledevices` in the disconnected-but-not-reset state).

## Summary

No code change this session. This confirms the BLE characteristic picker UI added earlier today

connections" — updating `TODO.md` accordingly rather than leaving it as a cold trail.
