# Rigol DS1102E profile: build and real-hardware verification

Built `src/DevTerm.Devices.Scpi/Profiles/rigol-ds1102e.json` from
`docs/devices/rigol-ds1102e/programming-manual.md` (replacing the wrong-model
`rigol-ds1105e.json`), then tested its commands against the real bench unit over USBTMC — using
the console CLI directly (`--transport usbtmc ... --cli true`), not the profile-aware SCPI
control-panel path (`ScpiReplyPresenter`/`--presenter scpi`), since that path is only wired into
`TuiMode`/`MainWindow`, not `CliMode` (see docs/design/usbtmc-transport.md). Three real bugs were
found and fixed along the way (see Findings); this pass supersedes the "Not attempted" DS1102E row
in `docs/test/2026-09-24-07-16-34.md`.

## Findings

- **Fixed — wrong SCPI abbreviations for two Measure queries.** The profile's first draft used
  `:MEAS:VAVG?` and `:MEAS:RISE?`, guessed from the mnemonics' full names (`VAVerage`, `RISetime`)
  rather than their actual SCPI short forms (the capitalized letters only: `VAV`, `RIS`). The
  DS1102E doesn't reply to an unrecognized query at all — no error text, nothing — so this looked
  identical to a slow device or a transport timeout until the request/reply bytes were traced at
  the USB level and cross-checked against the manual's own abbreviation table
  (docs/devices/rigol-ds1102e/programming-manual.md, "MEASure Commands"). Fixed by correcting both
  templates in `rigol-ds1102e.json`; confirmed against real hardware (instant, correct replies —
  `1.50e-02` and `<3.00e-05` respectively).
- **Fixed — `UsbtmcTransport.IsQuery` only checked the outgoing line's last character.**
  `:MEAS:VPP? CHAN1`-style queries (a `?`-terminated mnemonic followed by a space-separated
  parameter) were sent as fire-and-forget writes with no follow-up `REQUEST_DEV_DEP_MSG_IN`/read —
  the reply was silently never fetched, and stayed queued in the device. Fixed by having `IsQuery`
  find the mnemonic before the first space and check *that* substring's last character
  (`src/DevTerm.Transports.Usbtmc/UsbtmcTransport.cs`). Confirmed against real hardware: every
  `Source`-parameterized query in the table above (14 of the 27) now round-trips correctly.
- **Fixed — LibUsbDotNet's string-descriptor properties come back NUL-padded.**
  `IUsbDevice.Info.SerialNumber`/`Manufacturer`/`Product` returned e.g. `"DS1ET180300759\0"`,
  breaking `--serialnumber`'s exact-match comparison in `SystemUsbtmcDevice.Open()` and showing as
  literal control characters in `--listusbtmcdevices` output. Fixed by trimming trailing NULs in
  both `SystemUsbtmcDevice.TryGetSerialNumber` and `SystemUsbtmcDeviceDiscovery.TryGet`.
- **Fixed — `--readtimeoutms`/`--writetimeoutms` were silently ignored for USBTMC connections.**
  `ServiceCollectionExtensions.AddDevTermFrontEnd`'s USBTMC branch never copied `cliOptions`'
  timeout values into `UsbtmcTransportOptions` (unlike the Serial branch, which does), so the
  transport was always stuck at the hardcoded 1000 ms/5000 ms defaults regardless of the CLI flags.
  This surfaced while chasing the two mnemonic-bug timeouts above, before the mnemonics themselves
  were identified as the real cause — with the wiring fixed, a real `--readtimeoutms 5000` measured
  as ~5007 ms elapsed (confirmed via temporary instrumentation, since removed), proving the flag now
  actually reaches the transport. Fixed by adding the same two lines the Serial branch already has.
- **Confirmed — the DS1102E's USBTMC replies carry no CR/LF terminator at all**; the bulk-IN
  transfer's EOM bit alone marks the message boundary. This is why raw `--presenter ascii` testing
  showed nothing despite the byte-level round trip succeeding (checked directly via temporary
  instrumentation in `SystemUsbtmcDevice`/`UsbtmcTransport`, since removed) — a line-buffered
  presenter never sees a terminator to flush on. Set `rigol-ds1102e.json`'s `Terminator` to `""` so
  `ScpiReplyPresenter` uses its terminator-less mode, exactly mirroring the pre-existing Korad
  KA3005P/KA6003P profiles for the same reason. Not independently re-verified through the TUI's
  `ScpiReplyPresenter` path this session (`CliMode` has no route to it) — the general
  terminator-less mechanism already has real-hardware confirmation via the Korad units, and this
  session independently confirmed the DS1102E's replies have no terminator at the raw-byte level,
  so the profile fix follows a known-good, already-proven pattern rather than an unverified one.
- **Minor, not a bug — the raw `hex` presenter has no line-boundary logic**, so two terminator-less
  replies sent back-to-back fast enough to both land in the pipe before the presenter's next render
  call get displayed as one concatenated chunk (observed once, for `:ACQ:TYPE?`/`:ACQ:MODE?` sent in
  immediate succession). Worth remembering for future raw-CLI USBTMC/terminator-less testing:
  `hex`/`ascii` are for spot-checking individual round trips, not a guaranteed one-reply-per-line
  transcript when firing several terminator-less queries rapidly.
- **Not a bug, real-hardware SCPI behavior** — `:ACQ:MODE?` and `:TRIG:EDGE:SOUR?` echo back a
  canonical/alternate form (`REAL_TIME`, `CH1`) different from the abbreviated set-form the profile
  sends (`RTIM`/`ETIM`, `CHAN1`/`CHAN2`) — common, expected SCPI instrument behavior, not something
  to fix in the profile.
- **Noted, out of scope this session**: no `DevTerm.Transports.Usbtmc.Tests` project exists at all —
  a real coverage gap for the transport code fixed twice in this session (`IsQuery`, the NUL-strip
  helpers). Worth a `BACKLOG.md` entry; not built this session given the narrower scope of the
  original request.

## Summary

`rigol-ds1102e.json` is now verified against real hardware: all 27 profile query commands plus
`:WAV:DATA?` return correct data. Three real bugs were found and fixed in the process — two in
`DevTerm.Transports.Usbtmc` (the `IsQuery` heuristic, NUL-padded string descriptors) that affect
every USBTMC device, not just this one, plus the USBTMC timeout-wiring gap in
`DevTerm.Configuration`; one in the profile itself (wrong SCPI abbreviations for two Measure
queries). Full solution build and `TestCategory=UNIT` suite both pass after all fixes.
