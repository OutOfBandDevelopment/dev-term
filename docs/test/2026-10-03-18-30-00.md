# 2026-10-03 18:30: DG1062Z screen capture (HCOPy:SDUMp:DATA?) over VXI-11

Raw capture of the DG1062Z bitmap reply, for the Stream Monitor's unverified DG1062Z case. The user confirmed the unit is connected over LXI and USB.

## Command

```bash
(sleep 2; echo "HCOPy:SDUMp:DATA?"; sleep 25; echo ":SYST:ERR?"; sleep 3) | dotnet run --project src/DevTerm.Console --no-build -- --transport vxi11 --host 192.168.0.87 --presenter hex --parser ascii --lineending Lf --cli true
```

Hex lines were joined and decoded offline.

## Result

- 230,481 bytes in 155 chunks (1,500 bytes each): an IEEE 488.2 definite-length block header `#9000230456` (`23 39 30 30 30 32 33 30 34 35 36`), the BMP, a `0A`, then the next reply `0,"No error"` for `:SYST:ERR?`.
- Block length 230,456 equals the bytes between the header and the trailing `0A`.
- BMP: `BM`, header file-size field 230,454 (the block carries 2 more bytes than the BMP says, `00 00` padding), 320 x 240, 24 bits per pixel, uncompressed, 230,400 pixel bytes, offset 54.
- Pillow decodes it. The picture is the instrument screen: CH1/CH2 tabs, Sine, Freq 1,000,000,000 kHz field, Ampl 5.000 Vpp, Offset 0, Phase 0, both channel previews, outputs OFF.
- The error queue after the capture: `0,"No error"`.

## Findings

- The capture is read whole in one pass over VXI-11; the reply is a `#9` block, not a bare BMP. The Stream Monitor's end-finder therefore has to handle either a block prefix or find the BMP inside it, and tolerate 2 spare bytes after the BMP's declared size.
- No setting was changed; the output stayed OFF.
- The Stream Monitor itself was not run on this.

## Summary

No code change. Confirms the DG1062Z bitmap reply shape (block header plus a 24-bit BMP) for the Stream Monitor.
