### 2. Raw-wire diagnostic — rules out a framing/checksum bug before touching the baud rate

A temporary `ScratchRadexOneDiagnosticTests` class (removed after this session; not committed) opened
`SerialTransport` directly and dumped raw hex for 5 seconds per case, bypassing `Session`/`RadexOneDecoder`
entirely:

```
dotnet test tests/DevTerm.Devices.RadexOne.Tests --filter "FullyQualifiedName~ScratchRadexOneDiagnosticTests"
```

| Case | Baud | Sent | Bytes received in 5s |
|---|---|---|---|
| Listen only | 2400 | nothing | 0 |
| Send Read Data request | 2400 | `RadexOneFramer.BuildRequest(1, RadexOneExtensionCodec.BuildQuery(RadexOneCommand.ReadData))` | 0 |
| Send Read Data request | 9600 | same request | 34 |
| Send Read Data request | 4800 | same request | 0 |

The 9600 case's raw reply: `7AFF20801600010000004D80000800000C0000000E0000000201000010000000D3F6` —
correct inbound prefix (`7A FF`), correct inbound type marker (`20 80` little-endian = `0x8020`),
`ExtensionLength` `16 00` LE = 22, `PacketNumber` `01 00` LE = 1 (matches the request), and the
extension's first word `00 08` LE = `0x0800` = `RadexOneCommand.ReadData`, matching the request's own
command code — a structurally valid, byte-exact reply. This confirmed the framer/checksum/codec logic
(bugs 021/022's fixes) was already correct; only the baud rate was wrong.

## Findings

- **The Radex One's real, current baud rate is 9600, not the 2400 documented everywhere as
  "real-hardware confirmed 2026-09-25."** That 2026-09-25 pass confirmed the *transport kind* (plain
  serial COM port, not USB HID) against real hardware, but the specific baud rate was taken from the
  source reverse-engineering doc's prose, never itself checked against the real device — a claim later
  copied into `devterm.runsettings`, three source doc comments, and the design proposal as if it had
  been. Filed as [061](../bugs/resolved/061-radexone-wrong-baud-rate.md) and fixed the same session (no
  production logic changes needed — only the baud configuration/documentation).
- At the wrong baud (2400 or 4800), the device doesn't reply at all — not a garbled/misframed reply,
  just silence, even to a pure listen with nothing sent. This is a useful diagnostic signature for any
  future "confirmed baud rate" claim on this or a similar USB-serial-bridge device: a wrong baud on a
  bridge like this (VID `0xABBA`/PID `0xA011`) doesn't misdecode, it silently drops everything both ways.

## Summary

Fixed [061](../bugs/resolved/061-radexone-wrong-baud-rate.md): corrected the Radex One's real-hardware
baud rate from an unverified "2400" to the confirmed 9600 across `RealHardwareRadexOneTests.cs`,
`devterm.runsettings`, `RadexOneControlSurface.cs`, `RadexOneFramer.cs`, `RadexOneDecoder.cs`, and
`docs/design/proposals/radex-one-protocol.md`. The Radex One now produces real decoded readings
end-to-end through the shipped `Session`/`RadexOneDecoder`/`RadexOneControlSurface` pipeline.
