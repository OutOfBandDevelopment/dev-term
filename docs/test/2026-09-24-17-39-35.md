# Lightweight follow-up check: Rigol DM3058E and DG1022 over USBTMC

Quick sanity pass on the DM3058E and DG1022 SCPI profiles, requested as a lightweight follow-up
after Matt manually tested both devices earlier today and reported they "looked fine" — not a full
bench review. Used the console CLI directly (`--transport usbtmc ... --cli true`, raw `ascii`
parser / `hex` presenter), the same pattern as `docs/test/2026-09-24-09-54-39.md`'s DS1102E pass,
since the profile-aware SCPI control-panel path isn't wired into `CliMode`.

## Device configuration

| Device | Profile | Transport / address | Result |
|---|---|---|---|
| Rigol DM3058E | `rigol-dm3058e.json` | USBTMC, VID 0x1AB1 PID 0x09C4, serial `DM3R232301438` | Confirmed working |
| Rigol DG1022 | `rigol-dg1022.json` | USBTMC, VID 0x1AB1 PID 0x0588, serial `DG1D125306284` (shares its PID with a DS1102E also on this bench — `--serialnumber` required) | Failed — known parked issue, see Findings |

`--listusbtmcdevices true` also showed a Rigol DS1000-series unit (serial `DS1ET180300759`,
PID 0x0588) and a DG1000Z (VID/PID 0x1AB1/0x0642, serial `DG1ZA232603118`) on the bench; neither was
in scope for this pass.

## Commands tested and responses

### Rigol DM3058E

| Sent | Received | Notes |
|---|---|---|
| `*IDN?` | `Rigol Technologies,DM3058E,DM3R232301438,01.01.00.02.03.01` | |
| `:MEASure?` | `TRUE` | Unexpected for a query documented as returning the current measurement value — see Findings |
| `:MEASure:VOLTage:DC?` | `-7.190550E-05` | Plausible floating-input DC reading (~-72 µV), leads not connected |
| `:SYSTem:ERRor?` | `-113,"Undefined header; keyword cannot be found"` | Queued error from one of the two commands above — see Findings |

### Rigol DG1022

| Sent | Received | Notes |
|---|---|---|
| `*IDN?` | *(no reply, 3 attempts, ~2s apart)* | Zero bytes back each time — matches the known parked USBTMC bulk-IN issue, not a new bug (see Findings) |

## Findings

- **DG1022 reproduces the already-tracked zero-byte stall** — `BACKLOG.md`'s USBTMC entry already
  documents that after a bench power-cycle, the DG1022 (and, that day, also the DS1102E) enumerate
  fine over USBTMC but return zero bytes for `*IDN?`, no exception or timeout. This pass reproduced
  exactly that against the DG1022 (3/3 attempts, no reply at all — not even a garbled one). Per the
  existing plan, root-causing this needs a USBPcap/Wireshark capture of a working NI-VISA exchange
  to diff against real hardware, not more blind retries — not attempted here, out of scope for a
  lightweight check.
- **`:MEASure?` (bare) on the DM3058E replied `TRUE`, not a value** — the profile documents this as
  a value query (`measureQuery`, `:MEASure?`). The reply looks more like a boolean/state response
  than a measurement. The following `:SYSTem:ERRor?` popped a `-113 "Undefined header"` from the
  queue, which is likely blaming one of these two commands rather than a real profile bug — not
  investigated further here (lightweight pass, and the DC-voltage query right after it worked
  correctly), but worth a closer look if the DM3058E profile ever gets its own dedicated pass like
  the DS1102E did.

## Summary

No dev-term code changes from this pass. The DM3058E round-trips its identify and DC-voltage
queries correctly over USBTMC as already shipped, matching Matt's own manual test today. The
DG1022 reproduced the already-tracked, parked zero-byte USBTMC stall — a known issue, not a new
regression; no action taken beyond confirming it's still present.
