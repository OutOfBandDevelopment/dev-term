# KA3005P/K8055 re-confirmation, new TCP dedicated tests (TDS2024 + both 2230s), MSTest timeout fix

Follow-up to `docs/test/2026-09-25-15-02-44.md`. Two parts: (1) the user re-ran three already-known
devices via VS Test Explorer and pasted the results for the record; (2) added a new
`RealHardwareTcpTests` class (dedicated, output-message-querying tests for the TDS2024 and both
Tektronix 2230s, matching the existing `RealHardwareSerialTests`/`RealHardwareUsbtmcTests` pattern
instead of `RealHardwareCliTests`'s identity-only child-process check) and ran it against real
hardware, which surfaced a real MSTest configuration bug.

### Method

The KA3005P/K8055 runs and the new `RealHardwareTcpTests` runs were driven from **VS Test
Explorer** with `devterm.runsettings` selected as the active settings file (not the `dotnet test`
CLI) — confirmed with the user directly. Command-line equivalents are given below for
reproducibility, but weren't what actually produced these results.

```bash
# Equivalent of the VS Test Explorer runs, for reproducibility:
dotnet test tests/DevTerm.Console.Tests --settings devterm.runsettings \
  --filter "FullyQualifiedName~RealHardwareSerialTests.CliMode_AgainstKoradKa3005p" \
  --logger "console;verbosity=detailed"

dotnet test tests/DevTerm.Devices.K8055.Tests --settings devterm.runsettings \
  --filter "FullyQualifiedName~RealDevice_ResetCounter1_CompletesWithoutFaultOrTimeout" \
  --logger "console;verbosity=detailed"

dotnet test tests/DevTerm.Console.Tests --settings devterm.runsettings \
  --filter "FullyQualifiedName~RealHardwareTcpTests" \
  --logger "console;verbosity=detailed"
```

I (Claude) also ran the last command myself via this session's Bash tool, with the same
`devterm.runsettings` file, several times over the course of this session. Results varied run to
run — not a sandboxing/network-access issue (an earlier theory here, since retracted): **the bench
only has one spare network cable for the two Tektronix 2230s**, so at most one of Host1 (.107)/
Host2 (.108) is ever actually connected at a time; whichever is unplugged correctly reports
Inconclusive ("not reachable"), which is expected bench topology, not a bug. Both 2230s and the
TDS2024 did answer real queries correctly whenever they were actually the cabled unit at the time —
see the matrix below.

### Findings

- **New, real bug: `devterm.runsettings`'s global `<MSTest><TestTimeout>5000</TestTimeout>` silently
  overrides any per-step timeout written into a test body.** The TDS2024 test answered `*IDN?` and
  `CH1?` correctly, then was killed mid-flight on the third query (`TRIGger:MAIn:FREQuency?`) with
  `Test 'CliMode_AgainstTektronixTds2024_AnswersIdentityAndQueriesChannel1' timed out after 5000ms` —
  not a device fault, not the test body's own 15-second `WaitAsync` per step (`RealHardwareTcpTests.cs`'s
  `_timeout`), but the MSTest framework's own 5-second *whole-method* deadline, which had never been
  hit before because no existing real-hardware test happened to chain three real round-trips that
  added up to more than 5 seconds. **Fixed**: raised `<TestTimeout>` to `60000` (60s) in
  `devterm.runsettings`, with a comment explaining why. This means the TDS2024's actual
  `TRIGger:MAIn:FREQuency?` reply is still unconfirmed — the query was sent but no reply was
  received before the test was killed, so it's unknown whether the device would have answered
  correctly given more time. Worth re-running now that the timeout is fixed.
- **New, real bug: every `TRIGger:...?` query tried against this TDS2024 unit hangs (never
  replies), while every other query answers normally.** First seen with `TRIGger:MAIn:FREQuency?`
  (hung the full step timeout twice: once via the user's VS Test Explorer run, once from this
  session's own re-run after the MSTest timeout fix above). Swapped to `TRIGger:STATE?` — a much
  cheaper status query with no measurement/computation — and it **also hung**, ruling out
  "expensive measurement" as the cause. Swapped again to `CH2?` (not `TRIGger`-family, but still the
  3rd command in the sequence) and it answered immediately (651ms for the whole test), ruling out a
  simple "3rd command in the session" positional issue too. Narrows the finding specifically to the
  `TRIGger` command family on this unit — root cause not identified (possibly related to that
  profile's own `Name` field noting this unit is "NOT the TDS2024B", if `TRIGger` queries need that
  variant's firmware, but this is unconfirmed). **Fixed the test** by using `CH1?`/`CH2?` instead of
  any `TRIGger` query — tracked as a `BACKLOG.md` item to investigate the real `TRIGger` hang
  separately, since it's a genuine device/profile gap independent of the test suite.
- Only one Tektronix 2230 is ever cabled to the bench at a time (one spare network cable, swapped
  between Host1/.107 and Host2/.108 by hand) — running both 2230 TCP tests in the same pass will
  always show one Inconclusive, which is expected bench topology, not a bug.
- Both 2230s and the KA3005P/K8055 boards behaved exactly as expected, no regressions.
