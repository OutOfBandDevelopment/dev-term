# 2026-10-03 19:30: Kuando Busylight batch/program-mode write (observed by the user)

The 64-byte batch write had been recorded as "no visible effect" (design doc open question). Retried with three candidate frames while the user watched the lamp. Nothing was timed or filmed.

## Device and command

Kuando Busylight, USB HID VID 0x04D8 / PID 0xF848.

```bash
dotnet run --project src/DevTerm.Console --no-build -- --transport hid --vendorid 1240 --productid 63560 --presenter hex --parser hex --lineending None --cli true
```

Each frame is 65 bytes: report id `00`, 64 bytes of batch report. The batch report is step 0 (8 bytes, `NextStep Repeat R G B On Off Audio`), 48 zero bytes, then the footer `06 04 55 FF FF FF` and a 2-byte big-endian additive checksum of the preceding 62 bytes.

| Variant | Step 0 | Checksum |
|---|---|---|
| V1 | `10 00 00 64 00 01 00 00` (jump opcode `10`, green 0x64) | `03D1` |
| V2 | `10 00 00 FF 00 01 00 00` (jump opcode `10`, green 0xFF) | `046C` |
| V3 | `00 00 00 FF 00 01 00 00` (no opcode, green 0xFF) | `045C` |

## Runs

| Run | What was sent | User observed (user-reported) |
|---|---|---|
| 1 (the first attempt failed to open: "Failed to get info", a one-off; a retry connected) | V1 at 16:11:31, V2 at :39, V3 at :47, then all zeros, 8 s apart | "solid green" |
| 2, isolated, an all-zero frame before each, 16:12:36 to 16:13:24 | off, V1 at 16:12:42, off :52, V2 :58, off 16:13:08, V3 :14, off :24 | green on, off, green on, then off and stayed off (V3 did nothing) |

## Findings

- **The batch write works when step 0 starts with `0x10`.** V1 and V2 turned the lamp green; V3, identical except for `00` in the first byte, did nothing. That matches the idea that the first byte is an opcode (`0x1_` = jump to step `_`, so `10` means start at step 0) and the earlier "set green" frame did not carry one. The meaning of the opcode is inferred from this result, not from documentation.
- Green at 0x64 and at 0xFF looked the same to the user; the proper range (0 to 100 percent versus 0 to 255) is not established.
- Run 1's single observation ("solid green") fits any of the three, which is why run 2 was isolated.
- No code change was made in this session; the one failed open is unexplained and did not recur.
- Not tried: multi-step sequences, the jump target and Repeat bytes, audio, and the footer's `06 04 55` bytes (timeout and sensitivity are unknown).

## Summary

No code change. Answers the main open question (why the batch write did nothing). The "Program Sequence..." button that was removed from the control panel can come back once a multi-step sequence is verified.
