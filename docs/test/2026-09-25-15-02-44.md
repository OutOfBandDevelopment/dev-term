# First real-hardware run of the new automated Integration/Hardware test suite

First `--settings devterm.runsettings` run of the automated real-hardware tests added this session
(`RealHardwareSerialTests`, `RealHardwareUsbtmcTests`, plus the pre-existing
`RealHardwareCliTests`/`RealHardwareMainWindowTests`/`RealHardwareK8055Tests`/
`RealHardwareBusylightTests`), against the bench as currently wired. Purpose: confirm the new tests
correctly drive real hardware (not just report `Inconclusive`), and pick up whatever they find.

### Commands run

```bash
dotnet build

dotnet test --settings devterm.runsettings --filter "TestCategory=Integration"

dotnet test --settings devterm.runsettings --filter "TestCategory=Integration&TestCategory=Hardware" \
  --logger "console;verbosity=detailed" tests/DevTerm.Console.Tests

dotnet test --settings devterm.runsettings --filter "TestCategory=Hardware" \
  --logger "console;verbosity=detailed" tests/DevTerm.Devices.K8055.Tests

dotnet test --settings devterm.runsettings --filter "TestCategory=Hardware" \
  --logger "console;verbosity=detailed" tests/DevTerm.Devices.Busylight.Tests

dotnet test --settings devterm.runsettings --filter "TestCategory=Hardware" \
  --logger "console;verbosity=detailed" tests/DevTerm.Wpf.Tests
```

(`dotnet test` only accepts one project/solution path at a time — the `--logger detailed` passes
above were run per-project rather than as one combined command.)

### Findings

- **New, real bug: the Rigol DG1062Z's `*IDN?` bulk-IN reply fails USBTMC header decoding.**
  `UsbtmcTransport.WriteAsync` → `ReadReply` → `UsbtmcCodec.DecodeHeader` throws
  `InvalidOperationException: USBTMC bulk-IN transfer of 2 byte(s) is shorter than the 12-byte
  header.` immediately after sending `*IDN?` — the very first bulk-IN transfer back from the device
  is only 2 bytes, nowhere near the mandatory 12-byte USBTMC header. This is the DG1062Z's first-ever
  attempt against dev-term (the 2026-09-24 bench session didn't attempt it — no profile existed yet
  and the DM3058E stall was assumed to block it too). Not investigated further this session — same
  category of problem as the DM3058E stall (docs/changes/2026-09-23.md), likely needs a packet
  capture of a known-working NI-VISA/Ultra Sigma `*IDN?` exchange against this specific unit to
  compare framing against what `LibUsbDotNet` actually sent. Tracked as a new `BACKLOG.md` item
  rather than fixed blind.
- **New: `RealHardwareSerialTests`'s HP 34401A test "passes" but the logged replies are wrong —
  a test-harness bug, not a device problem.** The transcript shows `Received: H` for `*IDN?` and
  `Received: ?` for `MEAS:VOLT:DC?`, both single characters, where the real replies are
  `HEWLETT-PACKARD,34401A,...` and a numeric voltage (confirmed via the 2026-09-24 bench session).
  Root cause: `RunAsync` uses the shared `RawPresenter` (no line buffering) and reads exactly one
  item off the `Session.Output` channel per command — but the 34401A's replies arrive over serial in
  multiple small chunks (this device's profile is LF-terminated, unlike the Korads/DS1102E this
  harness pattern was designed around), so each chunk fires `Session.Output` separately and the test
  only consumes the first chunk of each reply, leaving the rest sitting in the channel to be
  misread as the *next* command's reply. The test still satisfies the "non-empty reply, no fault, no
  timeout" bar it was written to, so it passed — but it isn't actually validating what it looks like
  it's validating for this specific device. Needs a harness fix (e.g. drain the channel until a
  short quiet gap before treating a reply as complete, or use `AsciiPresenter` with the profile's own
  LF terminator for devices that have one, reserving `RawPresenter` for genuinely terminatorless
  replies like the Korads). Not fixed this session — flagging for a follow-up before trusting this
  test's pass/fail on devices with a real line terminator.
- **The DM3058E's previously-parked USBTMC bulk-IN stall (docs/changes/2026-09-23.md,
  docs/test/2026-09-24-07-16-34.md) did not reproduce** — `*IDN?`, `SYSTem:VERSion?`, and
  `:MEASure:VOLTage:DC?` all answered correctly and promptly. Whatever fixed it (most likely one of
  the `Session.OpenAsync`/`Task.Run` cancellation-token fixes landed since, per `CLAUDE.md`'s
  constraints list) resolved this as a side effect — worth a deliberate re-test if that's ever
  disputed, but no further action needed now.
- Everything else (both Korads, the HP 34401A's actual round-trip once you look past the harness bug,
  both Tektronix scopes over TCP, the DS1102E, two of the four K8055 boards, and the Busylight)
  behaved exactly as already documented in `docs/test/2026-09-24-07-16-34.md`/`docs/changes/2026-09-23.md`
  — no regressions.
