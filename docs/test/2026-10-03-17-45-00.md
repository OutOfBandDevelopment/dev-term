## Findings

- **Still working as previously verified:** `*IDN?` returns the TDS 2024 identity (firmware v4.12); `CH1?` is 360 mV/div DC and `CH2?` 40 mV/div DC, both 10x probe; `ACQuire?` answers `SAMPLE;16;1;RUNSTOP`.
- **The silent queries in runs 1-3 were the missing write delay, not XY mode.** `HORizontal:MAIn:SCAle?`, `DISplay:FORMat?`, `ACQuire:NUMAVg?`, `MEASUrement:IMMed:TYPe?`, `HORizontal?`, `DISplay?` and `MEASUrement?` got no reply without the delay and each left `363 Input buffer overrun`. With `--writebytedelayms 50` (as the profile Notes already say for this unit) all answered and the error queue was clean. This is wider than the `TRIGger` hang recorded on 2026-09-25: every query is at risk without the delay, not just those.
- With the delay: the main time base is 500 us/div (`5.0E-4`), the display format is XY (vectors, 55 persistence setting as reported), 16 averages, and the immediate measurement type is PERIOD.
- Not run: the `HARDCopy` capture for the Stream Monitor; no scope setting was changed (the user allowed a mode change, not needed).

## Summary

No code change. Always use `--writebytedelayms 50` for this unit. Consider making the delay the default in the TDS2024 profile or a saved connection profile so a bare connection does not overrun it.
