# Radex One: real replies against the shipped `.ksy` layouts (2026-10-02)

A routine check that the binary-frame layouts in `docs/devices/radexone/` match what a real Radex One sends. This is the
"real-device check of a binary frame" item from TODO.md. It used the raw bytes only; the manifest presenter was not run live.

## Bench

Radex One on COM8 (virtual COM port), 9600 8-N-1, DTR and RTS asserted. No other device involved.

## Script

`python scripts/radexone_probe.py COM8` (builds each request with the word-sum checksums, writes it, waits 0.7 s, reads what arrived).

## Findings

- Every request got a reply on the first try, and each reply's length matches its `extension_length` plus 12.
- The Read Data request and reply decode with `radexone-query-request.ksy` and `radexone-read-data-reply.ksy` unchanged:
  `command_code` 2048, `ambient` 9, `accumulated` 855, `cpm` 13. Captured as `DeviceKsyFilesTests.RadexOne_RealCapturedReadDataExchange_DecodesWithTheShippedLayouts`.
- The Read Settings reply is 28 bytes with `alarm_mode` 0 and `threshold` 10 (0x000A), the same shape as the write-settings layout, as the
  doc comment there says.
- No `.ksy` exists yet for the Read Serial/Version reply (the layout is in the decoder, not in a file).
- Checksums are unvalidated (Kaitai can't express them).

## Live run through `ManifestFramePresenter` (same day, later)

`RealHardwareRadexOneTests.RealDevice_ReadData_PublishesFieldsFromTheImportedKsyFrame`
(`dotnet test tests/DevTerm.Devices.RadexOne.Tests --filter "FullyQualifiedName~RealHardware" --settings devterm.runsettings`):
imports `radexone-read-data-reply.ksy`, builds a `ManifestFramePresenter` from it, opens a `Session` on COM8 with that as the
only presenter, sends Read Data through `RadexOneControlSurface`, and waits for `ValuesChanged`. Passed three runs in a row.
One published set: `type_marker=32800, extension_length=22, packet_number=1, envelope_checksum=32845,
extension.command_code=2048, extension.constant_0c=12, extension.ambient=15, extension.accumulated=856, extension.cpm=21,
extension.checksum=62583` (the same reading the `RadexOneDecoder` test printed in that run: `CPM=20 Ambient=13 Accum=856`;
readings move between requests).

Finding: the two hardware tests in that class both opened COM8, and MSTest ran them in parallel, so one failed with
`UnauthorizedAccessException: Access to the path 'COM8' is denied`. The class is now `[DoNotParallelize]`.
