# Real-hardware test: Tektronix TDS2024 `TRIGger` query hang, follow-up investigation

Follow-up to the routine confirm pass in `docs/test/2026-09-30-21-47-20.md`, on the same bench
session with the same unit still online. Scope: dig further into the known
`TRIGger:...?`-queries-never-reply quirk tracked in `BACKLOG.md`'s "Tektronix TDS2024" section and
first confirmed 2026-09-25 (`docs/test/2026-09-25-18-57-22.md`) — specifically, whether the hang
also affects the device's own error/event reporting and the TCP link itself, or is isolated to the
query's own reply.

## Device configuration matrix

| Device | Role | Profile used | Transport + address | Framing | Result |
|---|---|---|---|---|---|
| Tektronix TDS2024 | Oscilloscope | `tektronix-tds2024.json` | TCP (serial-to-Ethernet bridge), `192.168.0.110:23` | `ascii` presenter, `Lf` line ending | Confirmed: `TRIGger` family silently dropped, link otherwise unaffected |

## Commands tested and responses

Connected via:

```bash
dotnet run --project src/DevTerm.Console -- --transport tcp --host 192.168.0.110 --port 23 --presenter ascii --lineending Lf --cli true
```

Each row below is a separate connection/run (process-level timeout used to bound the wait rather
than hang the shell indefinitely):

| Sent | Received | Notes |
|---|---|---|
| `*IDN?` | `TEKTRONIX,TDS 2024,0,CF:91.1CT FV:v4.12 TDS2CM:CMV:v1.04` | Baseline identify, each run |
| `TRIGger:STATE?` | *(no reply within 10s)* | Reconfirms 2026-09-25 finding |
| `TRIGger:MAIn:FREQuency?` | *(no reply within 10s)* | Reconfirms 2026-09-25 finding |
| `TRIGger?` | *(no reply within 10s)* | Query-all-trigger-settings form also silently dropped, not just the narrower subqueries |
| `TRIGger:STATE?` then `CH1?` | *(no reply)*, then `10;1.0E-1;0.0E0;DC;OFF;OFF` | **New**: the TCP link itself is unaffected — `CH1?` sent ~10s after the dropped `TRIGger:STATE?` got a clean, immediate, uncorrupted reply. The device drops the query itself; it does not hang the connection or queue a stale reply that bleeds into the next command. |
| `*CLS` then `TRIGger:STATE?` then `ALLEv?` | `1,"No events to report - new events pending *ESR?"` | **New**: no IEEE 488.2 command-error event (410/420-class) was queued for the dropped query — the device isn't rejecting `TRIGger:...?` as a malformed command, it's silently not answering at all. |

## Findings

- The `TRIGger` query family (including the unqualified `TRIGger?` form, not just
  `TRIGger:STATE?`/`TRIGger:MAIn:FREQuency?` tested previously) gets no reply at all from this unit,
  confirming and extending the 2026-09-25 finding.
- The drop is isolated to that one query/reply: it does **not** hang the TCP link, corrupt framing,
  or delay/queue a reply that later shows up prepended to a subsequent command's response — the very
  next command (`CH1?`) answered normally and promptly.
- The drop raises **no** SCPI/IEEE error-queue event (`ALLEv?` reported the queue empty immediately
  after). A malformed-command rejection would normally post a 410/420-class event; its absence here
  points toward the firmware simply never generating a reply for this command family on this
  specific unit/variant, rather than rejecting the command.
- This is consistent with `tektronix-tds2024.json`'s own `Name` field noting this unit is
  specifically "NOT the TDS2024B" — still an unconfirmed hypothesis, but the no-error-posted
  behavior rules out "device treats it as a syntax error" as an alternative explanation.

## Summary

No dev-term code/doc change needed beyond recording this; `BACKLOG.md`'s existing TDS2024 entry is
updated with this run's added detail (link/event-queue unaffected) in the same change. The
remaining open question — comparing wire-level framing against a known-good `TRIGger` exchange from
a Tek-provided tool — still needs a packet capture, which this session didn't have tooling for.
