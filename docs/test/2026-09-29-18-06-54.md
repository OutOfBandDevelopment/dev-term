### Manual probe: DS1102E long-memory/RAW waveform read (BACKLOG's missing-ZLP edge case)

`BACKLOG.md`'s USBTMC item notes the pyvisa-py-reported missing-ZLP bug needs a reply landing exactly
on a 64-byte packet boundary, and that a normal-mode 600-sample `:WAV:DATA?` (610 bytes) never hits
one. With the scope reachable, tried to force a longer reply via the CLI directly (`--presenter hex`,
manual commands, not a permanent test):

| Sent | Received (decoded) |
|---|---|
| `*IDN?` | `Rigol Technologies,DS1102E,DS1ET180300759,00.04.02.01.00` |
| `:STOP` | (no reply — command, not query) |
| `:ACQ:MEMD LONG` | (no reply) |
| `:WAV:POIN:MODE RAW` | (no reply) |
| `:WAV:DATA? CHAN1` | IEEE block `#8` + `00008192` + 8192 data bytes (8202 bytes total) |
| `*IDN?` | `Rigol Technologies,DS1102E,DS1ET180300759,00.04.02.01.00` (clean, unaffected) |

8202 bytes isn't a multiple of 64 (or 512), so this still didn't land on the boundary the pyvisa-py
report needs — the edge case remains unreproduced. The read itself was clean either way: no hang, no
truncation, and the following `*IDN?` came back uncorrupted, consistent with the fix already in place.
A follow-up `:ACQ:MEMD?` read back `NORMAL` even right after setting `LONG` (before `:WAV:DATA?`, in a
separate attempt) — likely the scope's own state-reporting lag rather than anything on dev-term's
side (the bigger 8192-byte reply is otherwise consistent with long/raw mode having actually taken
effect), but not chased further since it's not a dev-term transport concern.
