# Bench test: Rigol DG1022 over USBTMC (dev/usbtmc-fix)

## Bench

- **Attached:** a single USBTMC device, a Rigol DG1022, with a WinUSB driver bound (Zadig).
  - `--listusbtmcdevices true` → `1AB1:0588  Rigol Technologies DG3000 SERIES   SN:DG1D125306284`.
  - The DS1102E, which shares this VID:PID, was **not** attached, so the blank
    `RealUsbtmcDg1022SerialNumber` in `devterm.runsettings` could not pick the wrong device.
- **Firmware** (from `*IDN?`): `00.02.00.06.00.02.07`.
- **Host:** Windows 11, libusb 1.0.26 via LibUsbDotNet 3.0.224. Bulk-IN wMaxPacketSize = 64.

## Matrix

| Run | Code | Result |
|---|---|---|
| `RealHardwareUsbtmcTests.CliMode_AgainstRigolDg1022...` | branch, before request delay | **Fail**: `*IDN?` OK, `OUTPut?` read timed out (1 s) and was aborted. The failure was masked by a double-dispose `ObjectDisposedException` (fixed). The Debug trace shows GO_TO_LOCAL timing out on close. |
| CLI, 2 s between lines | same | `*IDN?` OK, `OUTPut?` and `FREQuency?` time out. |

| Raw probe, 1 / 5 / 10 / 20 / 50 / 100 ms gap | n/a | Every query answers, 6 of 6 per run. One transfer each, EOM set, bTag echoed correctly. |
| `RealHardwareUsbtmcTests.CliMode_AgainstRigolDg1022...` | with `UsbtmcDeviceQuirks` (20 ms delay, no REN) | **Pass, 3 of 3 runs**, about 200 ms each. |
| CLI, 7 queries piped with no pacing | same | All 7 answered: `*IDN?` ×2, `OUTPut?` ×2, `FREQuency?` ×2, `VOLTage?` → `5.000000e+00`. |

## Raw exchange (probe, 100 ms gap)

```
OUT tag=1 '*IDN?'        REQ tag=2  IN n=75 hdr=0202FD003F00000001000000 'RIGOL TECHNOLOGIES,DG1022 ,DG1D125306284,,00.02.00.06.00.02.07\n'
OUT tag=3 'OUTPut?'      REQ tag=4  IN n=17 hdr=0204FB000500000001000000 'OFF\n\r'
OUT tag=5 'FREQuency?'   REQ tag=6  IN n=25 hdr=0206F9000D00000001000000 '1.000000e+04\n'
```

`--presenter hex --parser ascii` confirms that `OUTPut?`'s reply is `4F46460A0D` (`OFF\n\r`). The trailing `\r`
after the `\n` is why the ASCII presenter shows a blank line. That is device behavior, not framing.

## Findings

1. **Root cause of the DG1022's "intermittent zero-byte reply" (BACKLOG.md):** the device drops a
   `REQUEST_DEV_DEP_MSG_IN` that arrives immediately after the query's `DEV_DEP_MSG_OUT`.
   - It is deterministic, not intermittent. What made it look intermittent was timing: `*IDN?` worked only because the open-time control requests happened to leave a gap before it.
   - Fixed with `UsbtmcDeviceQuirks.RequestDelayMs = 20` for `0x1AB1:0x0588`.
2. **The DG1022 doesn't really support USB488 REN control:** GO_TO_LOCAL timed out. This matches libsigrok's RL1 blacklist for this VID:PID. REN is now skipped for it.
3. **A separate, non-USBTMC bug:** with `--presenter hex` (which is also the parser unless `--parser` is given), typing a line that isn't valid hex crashes the CLI with an unhandled `FormatException` instead of reporting it. It was filed in `BACKLOG.md`.

## Follow-up: Rigol DS1102E (same session, DG1022 swapped out)

- **Attached:** `1AB1:0588  Rigol Technologies DS1000 SERIES   SN:DS1ET180300759`, firmware `00.04.02.01.00`.
  It was the only USBTMC device attached. Bulk-IN wMaxPacketSize = 64.

| Run | Result |
|---|---|
| `RealHardwareUsbtmcTests.CliMode_AgainstRigolDs1102e...`, 3 runs | **Pass, 3 of 3.** `*IDN?` → `Rigol Technologies,DS1102E,DS1ET180300759,00.04.02.01.00`, `:MEAS:VPP? CHAN1` → `3.08e-02`, `:MEAS:FREQ? CHAN1` → `1.00e+03`. The documented "phantom empty reply after open" did not appear. |
| Raw probe, 0 ms command→request gap, 2 runs | Every query answered. **The DS1102E does not need the DG1022's request delay.** It shares the VID:PID, so it still gets the harmless 20 ms. |
| Raw probe, `:WAV:DATA? CHAN1` (normal mode), 2 runs | Read of 632 bytes into a 65,600-byte buffer, i.e. a proper short packet. Header TransferSize = 610 (0x262), EOM set. Payload = `#800000600` + 600 samples = exactly 610 bytes, **plus 10 trailing bytes** `33323333B33FB3B70333`. Those are identical on every read and unlike the samples (about 0x71), so they are padding, not data. |
| CLI, `--presenter hex --parser ascii`, `:WAV:DATA? CHAN1` then `*IDN?` | The transport surfaces exactly 610 bytes: the block, with the padding dropped. The next `*IDN?` is clean. |
| CLI, 7 unpaced queries including a waveform | All answered with correct sizes (56/8/8/610/8/56/9). |
| New `RealHardwareUsbtmcTransportTests` (DS1102E ×3) | **Pass**: unpaced back-to-back queries, close/reopen ×3, and a waveform checked byte-exact against its IEEE block length followed by a clean `*IDN?`. |

**The literature finding does not match this unit.** pyvisa-py #472 reports the waveform TransferSize as 10 bytes *short*. On this unit it is exact, and the 10 extra bytes are trailing padding, so discarding them (as the rework does) is correct. A missing ZLP at an exact packet boundary was not exercised: a 600-sample reply never lands on one.
