# 2026-09-29

## Fix bug 044: a profile's numeric parameter limits can throw or force every value to 0

`ScpiParameterDefinition.Minimum`/`Maximum` (`src/DevTerm.Devices.Scpi/ScpiParameterDefinition.cs`) were
plain non-nullable `double`, so a Numeric parameter that legitimately omitted both defaulted to 0/0 —
`ScpiControlSurface.FormatNumeric`'s `Math.Clamp(number, Min, Max)` then forced every value sent for
that parameter to 0. Worse, a profile that explicitly set `Minimum > Maximum` made that same
`Math.Clamp` call throw `ArgumentException` outright. Both are now fixed:

- `Minimum`/`Maximum` are now nullable `double?` (null = unbounded), mirroring the existing
  `DeviceManifest.CommandParameter.Minimum`/`Maximum` pattern.
- `ScpiControlSurface.FormatNumeric`'s clamp now reads
  `Math.Clamp(number, parameter.Minimum ?? double.NegativeInfinity, parameter.Maximum ??
  double.PositiveInfinity)`, mirroring `ManifestControlSurface.FormatNumber`'s existing clamp — an
  omitted limit is genuinely unbounded rather than forcing the value to 0.
- `ScpiUiDefinitionBuilder.BuildParameterControl`'s `NumericControl`/`SliderControl`/default-value reads
  (which need a plain non-nullable `double` widget bound) fall back to `?? 0`, preserving today's
  widget-rendering behavior for an omitted bound exactly. `ValueConstraint.Minimum`/`Maximum` were
  already nullable and needed no change.
- `ScpiProfileCatalog.LoadFrom` now rejects a loaded profile whose Numeric parameter has both
  `Minimum` and `Maximum` set with `Minimum > Maximum` — skipped and reported via the existing
  `errors` list, the same treatment as an unreadable/malformed profile file (bug 023's fix), via a new
  `FindBadNumericLimits` helper. `Math.Clamp` can no longer see that combination at runtime.

Regression tests:
`ScpiControlSurfaceTests.InvokeAsync_NumericParameterWithNoLimitsSet_IsNotForcedToZero` (fails against
the pre-fix code — the wire text was `GAIN 0` instead of `GAIN 12345`) and
`ScpiProfileCatalogTests.Load_WithANumericParameterWhereMinimumExceedsMaximum_SkipsThatProfileAndReportsIt`
(fails against the pre-fix code — the bad profile loaded successfully instead of being rejected). Both
pass with the fix. Full `TestCategory=Unit` run green across the whole solution (no regressions). See
[044](../bugs/fixed/044-scpi-clamp-bad-limits.md).

## Fix bug 045: device control surfaces parsed numbers with a throwing Parse

`BusylightControlSurface.ParseByte`, `K8055ControlSurface.ParseByte`, and
`RadexOneControlSurface.ParseUInt16` all built on a bare `double.Parse(value ?? "0",
CultureInfo.InvariantCulture)`, throwing `FormatException` for blank or non-numeric text. For
`K8055ControlSurface` specifically this was worse than "throws" — its `PreviewCommand` already
wrapped the shared `Plan` method in a try/catch for exactly this, but `InvokeAsync` had no equivalent
protection, so bad numeric text bypassing UI validation threw an *unhandled* exception straight out of
`InvokeAsync` (Busylight/RadexOne set state directly in `InvokeAsync`'s own switch, with the same gap).

All three helpers now use `double.TryParse(value, NumberStyles.Float, CultureInfo.InvariantCulture,
out var parsed) ? parsed : 0` before the existing `Math.Clamp`, mirroring the already-shipped
non-throwing pattern in `ManifestControlSurface.FormatNumber` — `IControlSurface.InvokeAsync` has no
result/error channel to report a validation failure through, so silently falling back to `0` (matching
what an omitted/empty value already did) was preferred over inventing one. `InvokeAsync` and
`PreviewCommand` are symmetric again for every device. A pre-existing K8055 test asserting a bad value
previewed as `null` was actually just observing the old throw being caught — split into
`PreviewCommand_UnknownCommand_IsNull` (still null; an unknown command id still throws
`ArgumentException`) and `PreviewCommand_NonNumericValue_FallsBackToZeroRatherThanNull` (documents the
corrected behavior).

Regression tests:
`K8055ControlSurfaceTests.InvokeAsync_AnalogOutWithNonNumericValue_DoesNotThrow_AndFallsBackToZero`,
`BusylightControlSurfaceTests.InvokeAsync_OnMsWithNonNumericValue_DoesNotThrow_AndFallsBackToZero`,
`RadexOneControlSurfaceTests.InvokeAsync_ThresholdWithNonNumericValue_DoesNotThrow_AndFallsBackToZero`
(all three fail against the pre-fix code with an unhandled `FormatException`). Full `TestCategory=Unit`
run green across the whole solution (no regressions). See
[045](../bugs/fixed/045-control-surface-parse-throws.md).

## Fix bug 046: manifest numbers could go out as NaN, or rounded past a fractional Max

`ManifestControlSurface.FormatNumber` (`src/DevTerm.DeviceManifests/ManifestControlSurface.cs:177-197`)
had two related defects:

- `double.TryParse` accepts `"NaN"`/`"Infinity"`/`"-Infinity"` as literal text regardless of
  `NumberStyles`, and the method's own `Math.Clamp(number, Min, Max)` passes `NaN` through unchanged
  (every comparison against `NaN` is false) — so a typed value of `"NaN"` reached the wire verbatim
  instead of being rejected.
- Rounding (for an `IsInteger` parameter) happened *after* clamping, so an already-in-range value could
  round past a fractional bound: Max `10.5`, value `10.5` clamped to `10.5` unchanged, then rounded to
  `11` — over the declared maximum.

Fixed with a new private `TryParseFinite` helper (`double.TryParse` plus `double.IsFinite`), used for
both the raw value and the `parameter.DefaultValue` fallback, and by reordering `FormatNumber` to round
before clamping rather than after.

Regression tests:
`ManifestControlSurfaceTests.InvokeAsync_NonFiniteNumericValue_DoesNotSendNaNOrInfinityLiterally` (fails
against the pre-fix code — sent `VSET1:NaN\n`) and
`ManifestControlSurfaceTests.InvokeAsync_IntegerParameterRoundingToAFractionalMaximum_IsStillClampedToIt`
(fails against the pre-fix code — sent `TRIM11\n`, past the parameter's `Maximum` of `10.5`). Both pass
with the fix; confirmed via a temporary `git stash` of just the source file that both tests fail for the
right reason against pre-fix code before the fix was reapplied. Full `TestCategory=Unit` run green
across the whole solution (no regressions). See
[046](../bugs/fixed/046-manifest-formatnumber-nan.md).
