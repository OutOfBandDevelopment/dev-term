# 2026-09-29

## Fix bug 044: a profile's numeric parameter limits can throw or force every value to 0

`ScpiParameterDefinition.Minimum`/`Maximum` (`src/DevTerm.Devices.Scpi/ScpiParameterDefinition.cs`) were
plain non-nullable `double`, so a Numeric parameter that legitimately omitted both defaulted to 0/0 —
`ScpiControlSurface.FormatNumeric`'s `Math.Clamp(number, Min, Max)` then forced every value sent for
that parameter to 0. Worse, a profile that explicitly set `Minimum > Maximum` made that same
`Math.Clamp` call throw `ArgumentException` outright. Both are now fixed:

- `Minimum`/`Maximum` are now nullable `double?` (null = unbounded), mirroring the existing
  `DeviceManifest.CommandParameter.Minimum`/`Maximum` pattern.
- `ScpiControlSurface.FormatNumeric`'s clamp now reads
  `Math.Clamp(number, parameter.Minimum ?? double.NegativeInfinity, parameter.Maximum ??
  double.PositiveInfinity)`, mirroring `ManifestControlSurface.FormatNumber`'s existing clamp — an
  omitted limit is genuinely unbounded rather than forcing the value to 0.
- `ScpiUiDefinitionBuilder.BuildParameterControl`'s `NumericControl`/`SliderControl`/default-value reads
  (which need a plain non-nullable `double` widget bound) fall back to `?? 0`, preserving today's
  widget-rendering behavior for an omitted bound exactly. `ValueConstraint.Minimum`/`Maximum` were
  already nullable and needed no change.
- `ScpiProfileCatalog.LoadFrom` now rejects a loaded profile whose Numeric parameter has both
  `Minimum` and `Maximum` set with `Minimum > Maximum` — skipped and reported via the existing
  `errors` list, the same treatment as an unreadable/malformed profile file (bug 023's fix), via a new
  `FindBadNumericLimits` helper. `Math.Clamp` can no longer see that combination at runtime.

Regression tests:
`ScpiControlSurfaceTests.InvokeAsync_NumericParameterWithNoLimitsSet_IsNotForcedToZero` (fails against
the pre-fix code — the wire text was `GAIN 0` instead of `GAIN 12345`) and
`ScpiProfileCatalogTests.Load_WithANumericParameterWhereMinimumExceedsMaximum_SkipsThatProfileAndReportsIt`
(fails against the pre-fix code — the bad profile loaded successfully instead of being rejected). Both
pass with the fix. Full `TestCategory=Unit` run green across the whole solution (no regressions). See
[044](../bugs/fixed/044-scpi-clamp-bad-limits.md).

## Fix bug 045: device control surfaces parsed numbers with a throwing Parse

`BusylightControlSurface.ParseByte`, `K8055ControlSurface.ParseByte`, and
`RadexOneControlSurface.ParseUInt16` all built on a bare `double.Parse(value ?? "0",
CultureInfo.InvariantCulture)`, throwing `FormatException` for blank or non-numeric text. For
`K8055ControlSurface` specifically this was worse than "throws" — its `PreviewCommand` already
wrapped the shared `Plan` method in a try/catch for exactly this, but `InvokeAsync` had no equivalent
protection, so bad numeric text bypassing UI validation threw an *unhandled* exception straight out of
`InvokeAsync` (Busylight/RadexOne set state directly in `InvokeAsync`'s own switch, with the same gap).

All three helpers now use `double.TryParse(value, NumberStyles.Float, CultureInfo.InvariantCulture,
out var parsed) ? parsed : 0` before the existing `Math.Clamp`, mirroring the already-shipped
non-throwing pattern in `ManifestControlSurface.FormatNumber` — `IControlSurface.InvokeAsync` has no
result/error channel to report a validation failure through, so silently falling back to `0` (matching
what an omitted/empty value already did) was preferred over inventing one. `InvokeAsync` and
`PreviewCommand` are symmetric again for every device. A pre-existing K8055 test asserting a bad value
previewed as `null` was actually just observing the old throw being caught — split into
`PreviewCommand_UnknownCommand_IsNull` (still null; an unknown command id still throws
`ArgumentException`) and `PreviewCommand_NonNumericValue_FallsBackToZeroRatherThanNull` (documents the
corrected behavior).

Regression tests:
`K8055ControlSurfaceTests.InvokeAsync_AnalogOutWithNonNumericValue_DoesNotThrow_AndFallsBackToZero`,
`BusylightControlSurfaceTests.InvokeAsync_OnMsWithNonNumericValue_DoesNotThrow_AndFallsBackToZero`,
`RadexOneControlSurfaceTests.InvokeAsync_ThresholdWithNonNumericValue_DoesNotThrow_AndFallsBackToZero`
(all three fail against the pre-fix code with an unhandled `FormatException`). Full `TestCategory=Unit`
run green across the whole solution (no regressions). See
[045](../bugs/fixed/045-control-surface-parse-throws.md).

## Fix bug 046: manifest numbers could go out as NaN, or rounded past a fractional Max

`ManifestControlSurface.FormatNumber` (`src/DevTerm.DeviceManifests/ManifestControlSurface.cs:177-197`)
had two related defects:

- `double.TryParse` accepts `"NaN"`/`"Infinity"`/`"-Infinity"` as literal text regardless of
  `NumberStyles`, and the method's own `Math.Clamp(number, Min, Max)` passes `NaN` through unchanged
  (every comparison against `NaN` is false) — so a typed value of `"NaN"` reached the wire verbatim
  instead of being rejected.
- Rounding (for an `IsInteger` parameter) happened *after* clamping, so an already-in-range value could
  round past a fractional bound: Max `10.5`, value `10.5` clamped to `10.5` unchanged, then rounded to
  `11` — over the declared maximum.

Fixed with a new private `TryParseFinite` helper (`double.TryParse` plus `double.IsFinite`), used for
both the raw value and the `parameter.DefaultValue` fallback, and by reordering `FormatNumber` to round
before clamping rather than after.

Regression tests:
`ManifestControlSurfaceTests.InvokeAsync_NonFiniteNumericValue_DoesNotSendNaNOrInfinityLiterally` (fails
against the pre-fix code — sent `VSET1:NaN\n`) and
`ManifestControlSurfaceTests.InvokeAsync_IntegerParameterRoundingToAFractionalMaximum_IsStillClampedToIt`
(fails against the pre-fix code — sent `TRIM11\n`, past the parameter's `Maximum` of `10.5`). Both pass
with the fix; confirmed via a temporary `git stash` of just the source file that both tests fail for the
right reason against pre-fix code before the fix was reapplied. Full `TestCategory=Unit` run green
across the whole solution (no regressions). See
[046](../bugs/fixed/046-manifest-formatnumber-nan.md).

## Fix bug 048: SCPI *IDN? matching ran profile regexes with no timeout

`ScpiProfileCatalog.TryMatchByIdn` (`src/DevTerm.Devices.Scpi/ScpiProfileCatalog.cs`) ran a
profile-supplied `IdnPattern` through `Regex.IsMatch` with no timeout, unlike
`ManifestReplyPresenter`/`ManifestEditorForms`'s existing 250 ms pattern — a catastrophic-backtracking
pattern in a user-dropped profile could hang auto-detect. Now calls `Regex.IsMatch` with
`RegexOptions.IgnoreCase | RegexOptions.CultureInvariant` and a 250 ms `TimeSpan` timeout, and catches
`RegexMatchTimeoutException` per profile — a timed-out pattern is treated as "doesn't match" and the
loop continues to the next profile, mirroring `ManifestReplyPresenter.AddLineValues`'s own
`catch (RegexMatchTimeoutException) { continue; }` rather than letting the exception propagate as a new
unhandled failure. Split into a public `TryMatchByIdn(string)` (against `All`) and an internal
`TryMatchByIdn(string, IEnumerable<ScpiInstrumentProfile>)` overload so a test can exercise matching
against a synthetic catastrophic-backtracking profile without depending on the process's real loaded
profiles.

Regression test:
`ScpiProfileCatalogTests.TryMatchByIdn_CatastrophicBacktrackingPattern_CompletesWithinTheRegexTimeoutBudget`
(an MSTest `[Timeout(1000)]` test against the pattern `^(a+)+$` — fails as "timed out" against the
pre-fix code, confirmed via a temporary revert of just the timeout/catch behavior). Full
`TestCategory=Unit` run green across the whole solution (no regressions). See
[048](../bugs/fixed/048-scpi-idn-regex-no-timeout.md).

## Fix bug 049: UI definition and device manifest XML were parsed without prohibiting DTDs

`UiDefinitionSerializer.FromXml` (`src/DevTerm.UiDefinitions/UiDefinitionSerializer.cs`) deserialized
via `XmlSerializer.Deserialize(TextReader)` with no DTD restriction. Reproduced first: a document with
an internal-entity DOCTYPE (`<!DOCTYPE UiDefinition [<!ENTITY evil "expanded">]>`) deserialized
without error, confirming the entity reference was accepted rather than rejected. A manifest's
`UiFile`/`device.xml` is untrusted input, so this was a real billion-laughs exposure, not just a
theoretical one. `DeviceManifestSerializer.FromXml`
(`src/DevTerm.DeviceManifests/DeviceManifestSerializer.cs`) mirrors the identical
`XmlSerializer.Deserialize(TextReader)` pattern one class down (its own doc comment already says so)
and is reachable from the same untrusted manifest input, so it got the identical fix rather than
leaving a live copy of the same defect behind.

Both now deserialize via `XmlReader.Create(stringReader, new XmlReaderSettings { DtdProcessing =
DtdProcessing.Prohibit })` per the bug report's suggested fix — `XmlSerializer` wraps the resulting
`XmlException` as `InvalidOperationException` the moment a DOCTYPE is encountered, before any entity
can be defined or expanded.

Regression tests:
`UiDefinitionSerializerTests.FromXml_DocumentWithAnInternalDtdEntity_DoesNotExpandIt` and
`DeviceManifestTests.FromXml_DocumentWithAnInternalDtdEntity_DoesNotExpandIt` (both fail against the
pre-fix code — no exception was thrown). Full `TestCategory=Unit` run green across the whole solution
(no regressions). See [049](../bugs/fixed/049-uidefinition-xml-dtd.md).

## Fix bug 051: LF followed by CR counted as two lines

`LineReplyPresenter.Render` (`src/DevTerm.Core/Presenters/LineReplyPresenter.cs`) already treated CR
LF as one terminator (a `_pendingCr` flag set on CR swallows an immediately-following LF), but had no
symmetric handling the other way around: a device ending its lines in LF CR produced a second,
spurious empty line, which consumed the next pending query's reply id (see
[006](../bugs/fixed/006-reply-queue-desync.md)'s desync failure mode). Skipping empty lines while an
id is pending — the report's other suggested fix — was already rejected in bug 006's own resolution,
since some devices legitimately reply with an empty line, so this instead mirrors the existing CRLF
handling: a new `_pendingLf` flag, set when an LF completes a line, swallows an
immediately-following CR.

Regression test: `ScpiReplyPresenterTests.Render_LfThenCr_CountsAsOneLine_NotAnExtraEmptyOne` (fails
against the pre-fix code — the spurious empty line shifted a later reply onto the wrong query id).
Full `TestCategory=Unit` run green across the whole solution (no regressions). See
[051](../bugs/fixed/051-line-reply-lf-cr-two-lines.md).

## Fix bug 053: BLE pipe writes from Bluetooth threads weren't synchronized

`BleTransport` (`src/DevTerm.Transports.Ble/BleTransport.cs`) started a fire-and-forget
`WriteToPipeAsync` per incoming notification with no synchronization between calls, and
`OnAdapterDisconnected`/`CloseAsync` completed the writer from other threads — `PipeWriter` is
single-writer. This report's `Plausible` confidence was reproduced first: a test raising two
notifications back-to-back, the first large enough to exceed the `Pipe`'s default 64 KiB
pause-writer threshold with nothing reading yet (so its `WriteAsync` is still flushing when the
second arrives), showed the defect is worse than described — the second `WriteAsync`'s
`InvalidOperationException: Concurrent reads or writes are not supported` is swallowed as expected,
but the concurrent access also corrupts the `Pipe`'s internal state badly enough that the *reader*
side stops working afterward: a later `PipeReader.ReadAsync` throws `InvalidOperationException:
Reading is not allowed after reader was completed`, even though nothing ever completed the reader.
So in practice the whole BLE session died with an unhandled framework exception on some later read,
not just a dropped notification.

Fixed per the report's suggested fix: a `SemaphoreSlim _writeGate` that `WriteToPipeAsync` holds
around its `writer.WriteAsync` call, and a new `CompleteWriter()` helper (used by both
`OnAdapterDisconnected` and `CloseAsync`) that holds the same gate before completing the writer —
a write and a completion (or two writes) can no longer race.

Regression test: `BleTransportTests.NotificationArrivingWhileAPriorWriteIsStillFlushing_DoesNotLoseData`
(fails against the pre-fix code with the reader-side `InvalidOperationException` above). Full
`TestCategory=Unit` run green across the whole solution (no regressions). See
[053](../bugs/fixed/053-ble-pipe-writes-unsynchronized.md).

## Fix bug 054: a cancelled BLE connect left its ValueChanged handler attached

`WindowsBleAdapter.ConnectAsync` (`src/DevTerm.Transports.Ble.Windows/WindowsBleAdapter.cs`) already
unsubscribed `notifyCharacteristic.ValueChanged` when `WriteClientCharacteristicConfigurationDescriptorAsync`
returned a non-success `GattCommunicationStatus`, but not when that call itself threw (cancellation, or
a WinRT `COMException`) - that path skipped straight to the outer `catch`, which disposed `service`/
`device` but never unsubscribed the handler. `notifyCharacteristic` is now hoisted to the same scope
as `service`, and the `catch` block unsubscribes it (when non-null) before disposing and rethrowing -
covering every failure after the subscribe in one place, including the case the explicit branch
already handled (now folded into the same cleanup instead of duplicated).

No automated regression test: `BluetoothLEDevice`/`GattDeviceService`/`GattCharacteristic` are sealed
WinRT types with no public constructors and no interface seam in this class, so a throwing CCCD write
can't be faked - only real Bluetooth hardware exercises this path. See
[054](../bugs/fixed/054-ble-cancelled-connect-handler-leak.md).

## Fix bug 055: a HID read thread could crash the process; OpenAsync/CloseAsync could block the caller

`HidReadStream.ReadLoop` (`src/DevTerm.Transports.Hid/HidReadStream.cs`) called
`_stream.Device.GetMaxInputReportLength()` before its `try`, on a raw background `Thread` (not a
`Task`) - any exception there would go unhandled and crash the whole process. The whole method body,
including that call, is now inside a `try`/`catch (Exception)`/`finally`, so any exception on this
thread ends the read loop gracefully (same as end-of-stream) instead of crashing the process.

`HidTransport.OpenAsync` (`src/DevTerm.Transports.Hid/HidTransport.cs`) called `device.Open()` -
HidSharp's real, synchronous device enumerate-and-claim call - directly in its own synchronous body
with no `Task.Run`, so the `OpenAsync(...)` call itself didn't return a `Task` until `Open()`
returned, blocking whatever thread called it (often the UI thread). Reproduced first: a regression
test gates a mocked `Open()` and measures how long the `OpenAsync(...)` call expression takes to
return - it blocked for the full ~5s gate against the pre-fix code. `OpenAsync` now runs `Open()` via
`Task.Run(device.Open, CancellationToken.None)`, awaited with `ConfigureAwait(false)`.

The report's "Close blocks the calling thread" half needed correction rather than a blind fix:
`CloseAsync` already awaited its pump task with `ConfigureAwait(false)` before the blocking
`_device.Close()` call, which does move a genuine suspension's continuation off the caller's thread.
But when that pump task is *already complete* by the time the `await` runs (e.g. the device had
already disconnected), `await`ing an already-completed `Task` continues synchronously on the caller's
own thread regardless of `ConfigureAwait(false)` - so the report's concern held for that one narrower,
timing-dependent case. `CloseAsync`'s `_device.Close()` (which blocks on `HidReadStream.Stop()`'s
bounded ~2s thread `Join`) now also runs via `Task.Run(device.Close, CancellationToken.None)`,
removing the caller-thread-blocking risk unconditionally instead of leaving it timing-dependent.

No regression test targets `HidReadStream.ReadLoop`'s crash path or the `CloseAsync` timing edge case
directly: `HidReadStream` is `internal` (no `InternalsVisibleTo` exists for
`DevTerm.Transports.Hid`, unlike `DevTerm.Transports.Serial`) and wraps a real HidSharp `HidStream`
obtainable only from a real, already-open HID device - the same class of constraint as
[054](../bugs/fixed/054-ble-cancelled-connect-handler-leak.md)'s WinRT types.

Regression test: `HidTransportTests.OpenAsync_DoesNotBlockTheCallingThreadOnTheDevicesSynchronousOpen`
(fails against the pre-fix code, confirmed via a temporary `git stash` of just
`HidTransport.cs` before the fix was reapplied). Full `TestCategory=Unit` run green across the whole
solution (no regressions). See [055](../bugs/fixed/055-hid-read-thread-and-close-blocking.md).

## Fix bug 056: TCP listen mode rejected hostnames and was IPv4-only

`SystemTcpConnectionSource.AcceptAsync` (`src/DevTerm.Transports.Tcp/SystemTcpConnectionSource.cs`)
called `IPAddress.Parse(options.Host)` directly on the raw `--host` string, throwing `FormatException`
for a hostname like `"localhost"` instead of resolving it, and bound `IPAddress.Any` unconditionally,
which only accepts IPv4 peers. Confirmed confidence, reproduced first with two new regression tests
against pre-fix code: connecting to a `--host localhost` listener failed with `SocketException`
("actively refused") because the listener never started at all, and connecting to a no-host listener
over IPv6 loopback failed the same way.

Fixed per the report's suggested approach: `AcceptAsync` now tries `IPAddress.TryParse` first and
falls back to `Dns.GetHostAddressesAsync(host, cancellationToken)` (taking the first resolved
address) for a non-literal host, and the no-host case now binds `IPAddress.IPv6Any` with
`listener.Server.DualMode = true` set explicitly before `Start()` — the `TcpListener(IPAddress, int)`
constructor doesn't enable dual-mode on its own the way the static `TcpListener.Create(port)` helper
does. A caveat found while writing the test, not in the original report: a hostname that resolves to
more than one address (`"localhost"` commonly resolves to both `127.0.0.1` and `::1`) only binds
whichever address comes back first — a single address, not both families — documented on
`ResolveBindAddressAsync` rather than solved further, since only the wildcard (no-host) case was ever
meant to be dual-stack.

Regression tests (both fail against pre-fix code with `SocketException`):
`SystemTcpConnectionSourceTests.AcceptAsync_WithAHostname_ResolvesItInsteadOfThrowingFormatException`,
`SystemTcpConnectionSourceTests.AcceptAsync_WithNoHost_AcceptsAnIPv6LoopbackPeer` — plus two
same-behavior-as-before checks, `AcceptAsync_WithNoHost_StillAcceptsAnIPv4LoopbackPeer` and
`AcceptAsync_WithAnIpLiteralHost_StillBindsToThatAddress`. Full `TestCategory=Unit` run green across
the whole solution (no regressions). See [056](../bugs/fixed/056-tcp-listen-rejects-hostnames.md).

## Fix bug 057: a serial read could hang forever after a silent unplug

`SerialPortReadStream.ReadAsync` (`src/DevTerm.Transports.Serial/SerialPortReadStream.cs`) waited
only on `SerialPort.DataReceived` when no bytes were already pending — confirmed by reading the code
end to end, exactly matching the bug report's claim. Neither `DataReceived` nor `ErrorReceived` is
guaranteed to fire when a USB-serial adapter is physically unplugged with no data in flight, so the
wait had no way to notice and could hang indefinitely; the loss only used to surface on the next
write. `ReadAsync` now also subscribes `ErrorReceived` (cheap, doesn't hurt) and, the part that
actually matters, polls `port.BytesToRead` on a 1-second interval while waiting instead of an
unconditional `await` — `BytesToRead` touches the real device handle, so it throws on a genuinely
removed port the same way the eventual `Read()` call already would. `IsOpen` (the report's other
suggested poll target) was considered and rejected: it only reflects whether `Close()` was called,
not whether the device is still physically present, so it wouldn't have detected this at all.

A real Radex One happens to be attached to this machine on COM8, which made it possible to verify
this against real hardware rather than relying on code-reading alone (the report explicitly asked
for that before fixing): `RealHardwareSerialPortReadStreamTests` opens COM8 directly (bypassing the
Radex One's own protocol — only the port itself matters), starts a real `ReadAsync` with nothing
pending, then closes the port out from under it to simulate the same "no event ever fires" gap a
physical unplug leaves. Run against the pre-fix code it failed (still waiting past a 5-second bound);
against the fix it passed in ~1 second, matching the poll interval. This is the first real-hardware
serial test in the repo. Full solution build and `TestCategory=Unit` run stayed clean. See
[057](../bugs/fixed/057-serial-unplug-not-detected.md).

## Fix bug 058: two close requests during a slow cleanup ran OnClosing twice

`MainWindow.OnClosing` (`src/DevTerm.Wpf/MainWindow.xaml.cs`) cancelled the first close request,
then ran its cleanup (stream monitor dispose, unsubscribe, `Session.CloseAsync`/`DisposeAsync`,
stop logging) across several `await`s before setting `_closeConfirmed` and calling `Close()` for
real — a second close request (Ctrl+Q, Alt+F4, File > Exit) arriving while that cleanup was still
in flight re-entered the same method concurrently, since `_closeConfirmed` wasn't set yet.

Reproduced first, since the report's confidence was `Plausible`: a new test-only
`internal int ClosingCleanupRunCount` counter (incremented only when `OnClosing`'s cleanup body
actually runs, past the new guard) showed the cleanup genuinely running twice before the fix and
once after, confirming the reentrancy is real. The report's specific claim that the second run "may
throw inside an `async void` handler" did not reproduce, deterministically, across 30 stress-test
iterations against the pre-fix code — `StreamMonitor.Dispose()`, `StopLogging`, and
`Session.CloseAsync`/`DisposeAsync` all already guard against being called twice, so the redundant
run completed harmlessly. The reentrancy itself — relying on that idempotency by accident rather
than preventing the double-run by design — is still a real defect and is what this fix removes.

Fixed per the report's suggested fix: a new `_closing` flag is set right before the method's first
genuine `await`, and checked at the top on entry — a second, overlapping close request now just
cancels itself and returns, leaving the first request's own cleanup to finish once.
`StaTestRunner` (`tests/DevTerm.Wpf.Tests/StaTestRunner.cs`) gained a `Dispatcher.UnhandledException`
handler so a test can safely probe an `async void` handler's failure path without an unhandled
exception crashing the whole test process.

Regression test:
`MainWindowTests.Close_CalledAgainWhileTheFirstCloseIsStillCleaningUp_ClosesOnceWithoutThrowing`
(fails against the pre-fix code — `ClosingCleanupRunCount` is 2, not 1). Full `TestCategory=Unit`
run green across the whole solution (no regressions); full solution `dotnet build` clean (0
warnings, 0 errors). See [058](../bugs/fixed/058-wpf-onclosing-reentry.md).

## Fix bug 059: CLI Ctrl+C may not interrupt a pending read on Linux/macOS

Reproduced first, since the report's confidence was `Plausible`, and against real hardware rather
than just theory: installed a .NET SDK inside a WSL2 Ubuntu environment (a real Linux kernel) and
ran a minimal program isolating the exact mechanism in `CliMode.RunAsync`
(`src/DevTerm.Console/CliMode.cs`) — `Console.CancelKeyPress` plus `Console.In.ReadLineAsync
(CancellationToken)` — driven with a real `kill -INT` against a job-control-enabled backgrounded
foreground process. Result: `CancelKeyPress` fires promptly, but the concurrently pending
`ReadLineAsync(cts.Token)` call does not throw `OperationCanceledException` — it stays blocked
until a real line of input arrives. This confirms the report's claim and disproves the code
comment it quoted: `Console.In` is a `SyncTextReader`, whose `ReadLineAsync(CancellationToken)`
checks the token once before starting a plain synchronous read, and does not observe cancellation
for the rest of that blocked read. Only Linux (via WSL2) was actually verified this way; macOS
was not, though it shares the same CoreCLR `SyncTextReader` implementation.

Fixed by no longer awaiting `stdin.ReadLineAsync(cts.Token)` directly: the loop now races that
task against a genuinely cancellable `Task.Delay(Timeout.Infinite, cts.Token)` via
`Task.WhenAny`, breaking immediately when the delay task wins regardless of whether the real read
task ever observes the token. This follows the report's "read stdin on a dedicated thread"
suggestion in spirit without changing the injectable `TextReader` contract the existing tests
depend on — a well-behaved reader (the existing `ScriptedStdin` test fake, built on a genuinely
cancellable `Channel<T>`) sees no behavior change, since its own read always wins the race
already. An abandoned real read task (if the underlying reader never completes it) is left on a
background thread-pool wait, which doesn't block process exit — the same tradeoff already
accepted elsewhere in this codebase for `SerialPort`/`HidStream`'s own uncancellable blocking
reads. To make this testable without needing to raise a real, internally-constructed
`ConsoleCancelEventArgs`, `CliMode.RunAsync` gained a seventh, test-only overload parameter
(`CancellationTokenSource shutdownRequested`) that a test can `Cancel()` directly to simulate
Ctrl+C; the existing six-argument overload delegates to it with a fresh one, unchanged for
existing callers.

Regression test:
`CliModeCancellationTests.CtrlC_WhileStdinNeverObservesCancellation_StillExitsPromptly`, using a
new `UncancellableStdin` fake `TextReader` that mirrors `SyncTextReader`'s real defect (never
observes the token once called). Confirmed failing (5s timeout) against the pre-fix direct-await

## Fix bug 060: a TUI profile switch could close/reassign the wrong session under overlap

`TuiMode.cs`'s `SwitchProfileAsync` local function was the source bug 017's WPF fix
(`MainWindow.SwitchProfileAsync`) was ported from, and turned out to share both gaps it had before
that fix: it unsubscribed/closed/disposed the *old* session by reading the shared `session` closure
variable after an `await` (rather than a value captured before it), and reassigned
`session = mySession;` with no `ReferenceEquals(switchCts, cts)` supersede check — so two
overlapping switches could each end up closing whatever session the other one had just adopted,
or a stale switch could stomp a newer one's already-open session back onto the shared field.

Fixed by porting bug 017's WPF fix verbatim: `var oldSession = session;` is captured immediately
after `var mySession = built.Session;`, before any `await`, and that local is what gets torn down
as the outgoing session; the final `session = mySession;` reassignment is now guarded by
`ReferenceEquals(switchCts, cts)`, disposing `mySession` without adopting it when a newer switch has
already superseded this one.

No new deterministic regression test was added for the fix's exact race window: the test named in
the bug report (`TuiModeSwitchProfileTests.SwitchProfileAsync_SupersededByAnotherSwitchBeforeItResolves_DoesNotStompTheNewerOne`,
now tagged `BugRegression`) passed against both pre-fix and post-fix code when checked via a
temporary `git stash` of just the fix, because it only exercises the later `OpenAsync`-catch-block
supersede guard, which was already correct. A test built to force the actual window — gating the
old session's `FakeTransport.CloseAsync()` and starting a second overlapping switch against the same
session — deadlocked instead of racing: `Session._lifecycleLock` (`SemaphoreSlim(1,1)`) serializes
`OpenAsync`/`CloseAsync` per instance, and `StopAsync` unconditionally calls
`_transport.CloseAsync()` on every close, so the old session's teardown acquires that lock twice
(once via `CloseAsync()`, once via the following `DisposeAsync()`); with the gate held, the second
switch's own close of that same session blocked on the first, a circular wait with no way out short
of test-only hooks in `Session.cs` production code. Full `TestCategory=Unit` run green across the
whole solution (1291 tests, no regressions); full solution `dotnet build` clean (0 warnings, 0
errors). See [060](../bugs/fixed/060-tui-profile-switch-session-race.md) for the full testability
writeup.

## NMEA GPS decoder no longer blanks indicators with a sentence that has no data for them

## BLE discovery no longer requires a completed Windows pairing bond

`WindowsBleDeviceDiscovery.GetDevices` (`src/DevTerm.Transports.Ble.Windows/WindowsBleDeviceDiscovery.cs`)
previously listed only `BluetoothLEDevice.GetDeviceSelectorFromPairingState(true)` — Windows' paired-

since that handler can fire several times per second per device while scanning and only needs to
record which addresses exist.

## BLE reconnect issue root-caused to the peripheral, not dev-term; closed as a documented limitation

Interactive real-hardware pass (`docs/test/2026-09-29-17-12-20.md`) reproduced the reconnect failure
left open in `TODO.md`, found from both TUI and WPF against a second "Other BLE" SH-HC-08-family
bridge, and narrowed it to a trigger: reconnect only fails if the peripheral's TTL-serial side hasn't
been reset since the prior disconnect. Checked the manufacturer's HC-08 V3.1 User Manual
(hc01.com) and tested its two AT-tunable candidates against the real module: `AT+MODE?` returned
`OK+GET:0` (already full-power/always-advertising, ruling out a power-saving mode), and `AT+CTOUT`
got no response at all (this module, firmware `SH-V1.251` per `AT+VERSION` — an "SH"-vendor fork,
not stock hc01.com firmware — doesn't implement it). The manual also confirms AT command mode only
works while the module has no active BLE connection at all, with no escape sequence back into it
while connected, so any further AT-based workaround has to be issued in the gap between a disconnect
and the next reconnect attempt.

Conclusion: this is an inherent limitation of this device class, not a dev-term defect —
`WindowsBleAdapter.Cleanup()` already disposes/unsubscribes cleanly on every close, and nothing in the
manual describes expected/documented re-arm behavior this could be misconfiguring. Documented as a
known limitation in `docs/design/transports.md`'s BLE section rather than left open; removed from
`TODO.md` accordingly. No code change.

## WPF layout review follow-up: field widths now capped on wide windows

Closes the `TODO.md` "Cap field widths on wide windows" item.

Root cause: `FormRenderer.BuildRow` gives every control a two-column `Grid` (Auto-width label column,

normal-width row exactly as before and only stops growing once the row itself would otherwise push it
past 420px. `Device Profiles`/Connection Editor and the Manifest Editor's form pane both go through
this one shared renderer, so both got the cap with no per-window change needed.

## TUI layout review follow-ups: three design-call fixes

Resolves three of the "design call" items the 2026-09-25 TUI layout review left open, per the user's
explicit decisions on each:

- **Ctrl+Q now confirms before quitting the whole app, but only when there's a live connection to
  lose.** `TuiMode`'s Ctrl+Q previously always called `app.RequestStop()` directly, which already
  behaved like Escape for a nested panel/dialog (`RequestStop()` with no argument only ever stops
  whichever `Application.Run` loop is currently topmost) but gave no warning when it was about to end
  the whole app mid-session. `TuiMode.cs`'s new `Quit()` local function checks
  `app.TopRunnableView == window && session.State == ConnectionState.Open` before showing a
  `MessageBox.Query` ("Quit dev-term? This closes the current connection.") — an already-disconnected
  session quits immediately, matching `ConfigureMode`'s existing quit-confirmation pattern. Covered by
  three new `TuiModeTests`: `CtrlQ_WhileDisconnected_RequestsStopImmediately`,
  `CtrlQ_WhileConnected_AsksFirst_AndStopsWhenConfirmed`,
  `CtrlQ_WhileConnected_DoesNotStopIfDeclined` (the latter two drive the real modal via
  `TuiTestRunner.RunWithLoop`, since headless mode can't interact with a nested blocking dialog).
- **A control-panel button row no longer repeats its label.** `ControlPanelMode.cs`'s `AddControlRow`
  (TUI) and `ControlPanelWindow.xaml.cs`'s `BuildSectionGrid` (WPF) each built a `control.Label + ":"`
