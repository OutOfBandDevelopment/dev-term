## SCPI real-hardware follow-ups

Driving the same physical 34401A over real RS-232 (not just the report above) surfaced correct
settings and a real root cause for the "beeps, no measurement" symptom, prompting four follow-ups —
all landed today. See `docs/design/proposals/scpi-instrument-control.md`'s updated "Status" section.

  remote mode the way GPIB does, so `SYSTem:REMote` must be sent before any query, or the instrument

  knowledge (required non-default settings, a mandatory preamble command), folded into

  `ControlPanelMode` rendered `Description` before this: WPF gained a `DescriptionText` `TextBlock`
  (collapsed when empty) above the sections panel; the TUI equivalent renders it the same way other
  panel text does. The 34401A profile's `Notes` documents the settings/`SYSTem:REMote` requirement
  above.
- **`CliOptions.Handshake` exposed in both configuration UIs** — already fully wired end-to-end into
  the real serial transport, but previously unreachable from either editor. `DeviceProfilesWindow`

- **`CliOptions.ScpiProfile` persists a saved connection's instrument-profile/auto-detect choice** —

## Fixed the SCPI Measure/beep-with-no-reply root cause

Confirmed the leading hypothesis from this same file's earlier real-hardware report (a Measure
button beeping the 34401A with no reply shown anywhere) by reading the code, not by re-testing
against the physical instrument (no hardware access this session — still worth re-verifying live):
`PresenterCatalog.TryGet("scpi", ...)` resolves the DI-registered `ScpiReplyPresenter` singleton
unconditionally (`AddScpiPresenter()` registers it regardless of what a connection's profile
selected), while the session's actual live `Pipeline` — the thing that decides which presenters ever
see incoming bytes — is fixed once, at session-build time, from `CliOptions.EffectivePresenters`
(`DevTermSessionBuilder.Build`). So opening the SCPI Instrument panel on a connection that hadn't
selected "scpi" in its presenter list resolved a real, non-null presenter from the catalog, sent
commands through it successfully (`session.SendAsync` bypasses the pipeline entirely), but the
device's replies were never routed through `ScpiReplyPresenter.Render()` — nothing decoded/
correlated them, and nothing told the user why.

- **Fix — bind the presenter into the session's existing pipeline, don't just detect and warn about
  it being missing.** `Pipeline` (`DevTerm.Core.Presenters`) gained `AddPresenter(IPresenter)`,
  mutating its own live presenter collection in place rather than requiring a caller to build/swap in
  a replacement `Pipeline` — `Session`'s read loop (`PumpAsync`) holds one `Pipeline` reference for
  the session's whole lifetime, so a rebuilt instance would never be seen by the already-running
  loop; only mutating the exact same instance works. `Session` gained a matching
  `AddPresenter(IPresenter)` that delegates to it. `TuiMode.ResolveActiveScpiPresenter` and
  `MainWindow.ResolveActiveScpiPresenter` (the "SCPI Instrument..." menu handlers in both front ends)
  now call `session.AddPresenter(presenter)` before using the catalog-resolved presenter, so opening
  the SCPI panel always wires reply correlation in, regardless of what was selected when the
  connection was made — no warning dialog needed, since the gap is actively closed rather than
  merely reported.
- **`Pipeline`'s presenter collection stays a plain `List<IPresenter>`, synchronized with a
  `System.Threading.Lock`** — an immutable-snapshot-plus-CAS-swap (`ImmutableList<T>`) and
  `System.Collections.Concurrent.ConcurrentQueue<T>` were both tried and rejected during review: the
  former isn't a mutable collection at all (just swapped references), and the latter's
  producer/consumer (Enqueue/Dequeue) naming doesn't match how it's actually used here — nothing is
  ever dequeued, `AddPresenter` only appends and `Render` only enumerates. A lock is cheap: it's held
  only long enough to copy a snapshot, both for `AddPresenter` (rare, from a UI thread opening a
  device control panel) and `Render` (the session's background read loop, called many times a
  second) — the presenters' own `Render` calls, and any lock contention between the two call sites,
  never happen while the lock itself is held.
- **Tests**: 3 new `UNIT` tests in `DevTerm.Core.Tests/Presenters/PipelineTests.cs`
  (`AddPresenter_AppendsToTheSameLiveInstance`, `AddPresenter_AlreadyPresent_DoesNotDuplicate`,
  `AddPresenter_AfterConstruction_IsPickedUpByRender`) and 1 new in
  `DevTerm.Core.Tests/Sessions/SessionTests.cs`
  (`AddPresenter_WhileOpen_IsPickedUpByTheAlreadyRunningReadLoop`) — the last one is the direct
  regression test for this bug: it opens a session with an empty pipeline, calls
  `session.AddPresenter` *after* `OpenAsync` (mirroring the real "already-connected, then open the
  SCPI panel" sequence), then proves a byte written to the transport afterward still reaches the
  late-bound presenter. Full `dotnet test --filter "TestCategory=UNIT"` run after: all 15 test
  projects pass with no regressions.
- **Not yet verified against real hardware** — this session had no access to the 34401A or any other
  bench instrument; the fix is confirmed correct at the code/unit-test level (root cause reproduced
  and closed by a targeted test), but the original live-hardware report that raised this bug hasn't
  itself been re-run.

## USBTMC: explicitly ruled out NI-VISA/IVI as an alternative to WinUSB, added Zadig setup tooling

Follow-up discussion after the above: whether libusb could instead ride on the driver NI-VISA/
Keysight IO Libraries installs (`usbtmc.sys`), avoiding the Zadig/WinUSB rebind entirely. Confirmed
no: `libusb`'s Windows backend only speaks to WinUSB/libusbK/libusb-win32-bound interfaces, not an
arbitrary vendor class driver like `usbtmc.sys` — that driver is what VISA's own `viRead`/`viWrite`
calls into instead, a separate API surface. Going the VISA/IVI route was already rejected in
`docs/design/usbtmc-transport.md` for requiring a proprietary, machine-wide vendor runtime install;
confirmed the two paths are also mutually exclusive per-interface, not just independently
undesirable. Decision stands: WinUSB via Zadig.

- **New `docs/design/usbtmc-transport.md` section, "Setting up WinUSB for a USBTMC device
  (Windows)"**: documents the Zadig GUI walkthrough, and is explicit that full unattended
  automation isn't currently possible — checked directly against the `libwdi`/Zadig GitHub project
  (releases and wiki) rather than assumed: every `libwdi` release only ever published `zadig*.exe`

- **Real-hardware verification of `UsbtmcTransport`/`SystemUsbtmcDevice` against a real Rigol
  DM3000-series multimeter (VID 0x1AB1 PID 0x09C4, USB 1.1, bulk-OUT 0x01/bulk-IN 0x82/interrupt-IN
  0x83, 64-byte packets)** surfaced and fixed two real bugs, and turned up one apparent
  device/firmware limitation:
  - **Fixed: first bulk-OUT write on a fresh connection failed with `Error.Pipe` (a STALL)** — a
    prior run, or the device itself on power-up, can leave a bulk endpoint halted, and
    `SystemUsbtmcDevice.Open()` never cleared it before use. Fixed by calling `ClearHalt()` on both
    the reader and writer right after opening them, plus stall-retry-once logic in
    `WriteBulkOut`/`ReadBulkIn` (clear the halt and retry the same transfer once on `Error.Pipe`
    before giving up) — this is the stall-recovery behavior `docs/design/usbtmc-transport.md` had
    described as designed but not yet built. Confirmed fixed by re-running against the real device.
  - **Fixed: a genuine USBTMC spec violation** — `UsbtmcTransport` used two independent `bTag`
    counters (one for the `DEV_DEP_MSG_OUT` command, one for the following `REQUEST_DEV_DEP_MSG_IN`),
    both starting at 0, so a query's two consecutive Bulk-OUT transfers could carry the identical
    tag — the spec requires consecutive Bulk-OUT transfers to use different tags. Consolidated into
    one shared `_bulkOutTag` counter. Worthwhile on its own merits, but did not resolve the deeper
    issue below when tested against real hardware afterward.
  - **Open/unresolved: reading a query's reply from this specific DM3000 unit consistently stalls
    (`Error.Pipe`) on the bulk-IN endpoint**, even after both fixes above, `INITIATE_CLEAR`/
    `CHECK_CLEAR_STATUS` (both report `STATUS_SUCCESS`, not pending), `SetConfiguration(1)`, and a
    full `ResetDevice()` port reset + re-claim. Investigated exhaustively before concluding this is
    likely a real device/firmware limitation, not a `dev-term` bug:
    - Reproduced byte-for-byte identically from a second, independent USB stack (Python/pyusb over
      libusb1, pointed at the same native `libusb-1.0.dll`) — rules out a LibUsbDotNet/.NET-specific
      cause.
    - Reproduced across five protocol variants: no trailing newline, an added delay before the read,
      `TermCharEnabled` with an LF term char, a smaller `maxSize` (64), and a CRLF terminator — all
      failed identically.
    - Confirmed the USBTMC/USB488 control-transfer layer itself works on this device:
      `GET_CAPABILITIES`, `INITIATE_CLEAR`/`CHECK_CLEAR_STATUS`, `REN_CONTROL`, and
      `READ_STATUS_BYTE` all returned `STATUS_SUCCESS`.
    - Polled `READ_STATUS_BYTE` every ~300ms for 6 seconds after sending `*IDN?` — the Status Byte's
      MAV (message available) bit never set, and ESB (error) never set either — the device's own
      firmware never appears to register the command as received/processed at all, despite the raw
      USB-level bulk-OUT write reporting a full, successful transfer (bytes physically ACKed by the
      device). This is the strongest evidence it's a firmware-level limitation of this unit's
      USBTMC command handling rather than a framing/timing bug in `dev-term`'s transport.
    - Not yet tried: an official Rigol/NI-VISA reference stack against the same unit, and testing a
      second physical DM3000 (if one becomes available) to rule out a single unit's own hardware
      fault. Recorded here as a known limitation, not chased further this session.
  - **Fixed: two undisposed-native-handle bugs causing a real access-violation crash.**
    `LibUsbDotNet.Device` (the concrete type behind `IUsbDevice`) is a `SafeHandle`-backed
    `IDisposable`; a `UsbContext.List()` device that's iterated over but not the one ultimately kept
    was never disposed in either `SystemUsbtmcDeviceDiscovery.GetDevices()` (non-USBTMC candidates)
    or `SystemUsbtmcDevice.Open()` (VID/PID mismatches, serial-number mismatches). Left undisposed,
    each one's finalizer runs later on the GC finalizer thread — potentially after the owning
    `UsbContext` has already been disposed — and unref'ing a device against an already-freed libusb
    context is undefined behavior. This reproduced as a real `0xC0000005` access violation in
    `LibUsbDotNet.NativeMethods.UnrefDevice` → `Device.ReleaseHandle` → `SafeHandle.Finalize` →
    `GC.RunFinalizers`, aborting `dotnet test --filter "TestCategory=UNIT"` mid-run (surfaced only
    once real USBTMC hardware was attached to the dev machine, since
    `ConnectionEditorViewModel`'s constructor calls the real `SystemUsbtmcDeviceDiscovery` by default
    whenever no fake is supplied, and several UNIT-tagged WPF/TUI tests construct one). Fixed by
    disposing every enumerated device that isn't kept, in both call sites, plus disposing (not just
    closing) `SystemUsbtmcDevice`'s own device handle on `Close()` and on the `Open()`
    exception path. Confirmed fixed: `dotnet test --filter "TestCategory=UNIT|TestCategory=INTEGRATION"`
    now runs to completion with real USBTMC hardware attached, no crash.
  - **Fixed: `ConnectionEditorViewModel.Transport`'s setter never raised `PropertyChanged` for
    `IsUsbDeviceTransport`** (only for `IsHidTransport`/`IsUsbtmcTransport` individually), so WPF's
    `DeviceProfilesWindow.xaml` binding of `UsbDevicePanel.Visibility` to `IsUsbDeviceTransport`
    never re-evaluated when switching transports — caught by

  - **Fixed a stale test assertion** left over from the `Hid*` → shared `VendorId`/`ProductId` field

    label text `"HID vendor ID"`; the field is now the shared `"Vendor ID:"` label. Updated to match

- **Fixed: Korad KA3005P/KA6003P `VSET`/`ISET` commands silently failed to change the setpoint.**
  Root-caused on real hardware (both units, COM6/COM7) after the user reported "set voltage
  commands are failing for the 6003p": `ScpiControlSurface.FormatNumeric` sent a bare
  `double.ToString()` (e.g. `"5"` or, after a first fix attempt, `"5.00"`), but the Korad protocol
  has no command terminator at all and its firmware parses a fixed-width field after `VSET1:` —
  either width mismatch (missing decimal places, or missing the leading zero in `"05.00"`) desyncs
  its parser and the set is silently dropped; a follow-up `VSET1?` read back the unchanged previous
  value both times. Added `ScpiParameterDefinition.DecimalPlaces` and `.IntegerDigits`;
  `korad-ka3005p.json`/`korad-ka6003p.json`'s Voltage now formats as `"00.00"` (2+2 digits) and
  Current as `"0.000"` (1+3 digits), matching the well-known Korad wire format.
  - **Verified end-to-end on both real units** (KA3005P on COM6, KA6003P on COM7, no load attached):
    `VSET1:05.00` → `VSET1?` replied `05.00`; `OUT1` → `VOUT1?` replied `05.00` (output tracked the
    setpoint); `OUT0` → `VOUT1?` replied `00.00`. KA6003P's `*IDN?` also now confirmed:

  - Note on Korad's protocol fragility: any wrong-width byte sent to it (including a stray CR
    appended after a command, tried while debugging) leaves its parser desynced for the *rest of
    that connection* — a subsequent, correctly-formatted command can then also get no reply.
    Reconnecting (a fresh `SerialPort` open) resets it cleanly. Not a dev-term bug, just how this
    device's fixed-width, terminator-less parser behaves — worth remembering before concluding a
    correctly-formatted command "doesn't work" mid-session.
  - Correction to the earlier "KA6003P inconclusive" note below: COM7 does work — the earlier no-reply
