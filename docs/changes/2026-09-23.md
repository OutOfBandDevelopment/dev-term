## SCPI real-hardware follow-ups

Driving the same physical 34401A over real RS-232 (not just the report above) surfaced correct
settings and a real root cause for the "beeps, no measurement" symptom, prompting four follow-ups —
all landed today. See `docs/design/proposals/scpi-instrument-control.md`'s updated "Status" section.

- **Root cause found**: 9600 baud/8 data bits/2 stop bits/no parity/**no hardware handshake**/**LF**
  terminator are the correct settings for this instrument. RS-232 on the 34401A never auto-enters
  remote mode the way GPIB does, so `SYSTem:REMote` must be sent before any query, or the instrument
  answers SCPI error `+550 "Command not allowed in local"` with no measurement. The bundled
  `hp-agilent-keysight-34401a.json` profile now has a `remote` command.
- **`ScpiInstrumentProfile.Notes`** — a free-text field for exactly this kind of operational
  knowledge (required non-default settings, a mandatory preamble command), folded into
  `UiDefinition.Description` by `ScpiUiDefinitionBuilder.Build`. Neither `ControlPanelWindow` nor
  `ControlPanelMode` rendered `Description` before this: WPF gained a `DescriptionText` `TextBlock`
  (collapsed when empty) above the sections panel; the TUI equivalent renders it the same way other
  panel text does. The 34401A profile's `Notes` documents the settings/`SYSTem:REMote` requirement
  above.
- **`CliOptions.Handshake` exposed in both configuration UIs** — already fully wired end-to-end into
  the real serial transport, but previously unreachable from either editor. `DeviceProfilesWindow`
  (WPF) gets a "Handshake:" `ComboBox` row bound to `HandshakeText`/`HandshakeOptions`, right after
  Stop bits. `ConfigureMode` (TUI) gets an `OptionSelector<Handshake>` row in the same position,
  wired through the existing push/pull-fields-to/from-view-model pattern and the serial-only
  visibility toggle every other serial field already uses.
- **`CliOptions.ScpiProfile` persists a saved connection's instrument-profile/auto-detect choice** —
  both front ends' "SCPI Instrument..." menu item now skips its picker dialog when the saved value
  still resolves to a real choice (`ScpiProfileCatalog.AutoDetectChoiceName`, `Generic.Name`, or a
  currently-loaded profile's name), via a small `ResolveSavedScpiProfileChoice` helper duplicated
  (not shared) in `TuiMode.cs`/`MainWindow.xaml.cs`, consistent with this codebase's existing
  precedent for small per-front-end pieces. An unresolvable/blank saved value falls back to showing
  the picker exactly as before. Both front ends' local `ScpiAutoDetectChoice`/`ScpiGenericChoice`
  literals are now derived from the new `ScpiProfileCatalog.AutoDetectChoiceName` const and
  `Generic.Name` respectively, rather than independently redeclared, so a saved choice and the live
  picker can never silently drift out of agreement. Also exposed as a "SCPI profile:" editor row in
  both UIs (a bound `ComboBox` in WPF gated on `IsScpiPresenterSelected`; a `TextField` + "Pick..."
  button reusing the TUI's existing `PickFromList` modal, gated on the `scpi` presenter checkbox).
- **`ScpiProfileCatalog` loads from a per-user `~/.dev-term/scpi-profiles` folder** — in addition to
  the bundled `Profiles/` and app-folder `ScpiProfiles/` drop-in, mirroring
  `DevTermUserDataPaths.ProfilesDirectory`/`UserManifestsDirectory`'s existing convention (computed
  locally in `DevTerm.Devices.Scpi` rather than shared from `DevTerm.Configuration`, which
  references this project, not the other way around).
- **`CliOptions.ExportDirectory`** (unrelated to SCPI specifically, prep for the not-yet-built
  Stream Monitor feature — see `BACKLOG.md`) — a configurable auto-save destination, defaulting to
  a new `DevTermUserDataPaths.ExportsDirectory` (`~/.dev-term/exports`) via
  `EffectiveExportDirectory`. A plain nullable string property needs no special binding code to pick
  up command-line/`DEVTERM_`-environment-variable/settings-file values — confirmed this is already
  true for every such property via the existing `DevTermConfiguration` layering, unlike the
  `Presenter` array property's own special-cased comma-splitting. No editor UI row yet, matching the
  existing `ManifestName` precedent (a `CliOptions` property with no editor field).
- **Test fix**: the Handshake/SCPI-profile rows above push `ConfigureMode`'s HID field group one row
  further down, past what fits in an unscrolled 80x24 headless window —
  `ScreenshotTests.ConfigureMode_HidTransport_IsCaptured` started failing (`'HID vendor ID'` not
  found in the captured buffer). Fixed the same way `ConfigureMode_LoopbackTransport_IsCaptured`
  already handles the same fold: focus the description field and send one `PageDown` before
  capturing. Full `dotnet test --filter "TestCategory=UNIT"` run after the fix: all 14 test projects
  pass, including `DevTerm.Console.Tests` (68/68).
