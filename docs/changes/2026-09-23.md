# 2026-09-23

## Completed

- **SCPI instrument control module** (`DevTerm.Devices.Scpi`) — see
  `docs/design/proposals/scpi-instrument-control.md`'s new "Status: implemented" section and
  `TODO.md` for the full design writeup; this entry covers what landed today specifically.
  - `ButtonControl.ParameterFieldIds` (`DevTerm.UiDefinitions`) — the one non-additive change to an
    existing shared type: a button that reads named sibling controls' current values, comma-joins
    them, and invokes `CommandId ?? Id` with the joined string. Both generic renderers
    (`ControlPanelMode.AddControlRow` in the TUI, `ControlPanelWindow.BuildWidget` in WPF) got a new
    branch for it, checked before the plain `ButtonControl` case — same ordering precedent as the
    existing `ColorPickerTargetCommandId` branch.
  - New project `DevTerm.Devices.Scpi`: `ScpiInstrumentProfile`/`ScpiCommandDefinition`/
    `ScpiParameterDefinition` (the declarative command/response schema), `ScpiProfileCatalog`
    (bundled `Profiles/*.json` plus a drop-in `ScpiProfiles/` folder, no rebuild needed to add a
    profile), `ScpiControlSurface` (`IControlSurface`), `ScpiReplyPresenter`
    (`IPresenter`/`IStructuredPresenter`/`IScpiReplyTracker`, FIFO query/reply correlation), and
    `ScpiUiDefinitionBuilder` (profile → `UiDefinition`). Six curated starter profiles: HP/Agilent/
    Keysight 34401A, Rigol DM3058E, Rigol DG1022/DG1022Z, Rigol DS1105E, Korad KA3005P, Korad
    KA6003P.
  - WPF wiring: `ControlPanelWindow.xaml.cs` gets the `ParameterFieldIds` branch and a
    `GetCurrentValue` helper; a new `ScpiInstrumentPickerWindow` (mirrors `ColorPickerWindow`'s
    constructor-sets-state/`DialogResult`-on-confirm convention) lists
    `Auto-detect (*IDN?)`/`Generic (manual)`/each named profile; `MainWindow` gets a
    "SCPI Instrument..." menu item under `_Device`, an auto-detect flow
    (`DetectScpiProfileAsync`/`DetectAndOpenScpiInstrumentAsync` — sends `*IDN?` over the live
    session, awaits the first correlated reply via `ValuesChanged`, regex-matches it, falls back to
    Generic on no match or a 3-second timeout), and `OpenScpiInstrumentWindow` (reuses the current
    session rather than opening a second connection, `Show()` not `ShowDialog()` since the panel
    stays open alongside the main window).
  - Incidental cleanup: removed a leftover, entirely unused private method
    (`CollectionsMarshal_ToArray`, zero call sites anywhere in the repo) found while reading
    `ScpiReplyPresenter.cs` closely for test-writing — dead code from an earlier draft.
  - Tests: new `tests/DevTerm.Devices.Scpi.Tests` project (37 `UNIT` tests across
    `ScpiControlSurfaceTests`, `ScpiReplyPresenterTests`, `ScpiProfileCatalogTests`,
    `ScpiUiDefinitionBuilderTests` — template substitution/clamping/terminator/custom-command
    passthrough, line-buffering/FIFO correlation/unsolicited-line fallback, bundled+drop-in profile
    loading against a synthetic temp directory, IDN matching against the real bundled profiles, and
    per-command-shape UI mapping). Extended both `ControlPanelModeTests` (TUI) and
    `ControlPanelWindowTests` (WPF) with two `ParameterFieldIds` cases each (joined-sibling-values
    invocation, and reading a live-edited field value with a `CommandId` override). Added `"scpi"`
    to `ConnectionEditorViewModel.PresenterOptions` up front (it now reads
    `["ascii", "utf8", "hex", "decimal", "octal", "binary", "k8055", "busylight", "scpi"]`) and
    updated both `ConfigureModeTests`' and `DeviceProfilesWindowTests`' presenter-checkbox-list
    assertions to match — deliberately done as part of this feature rather than discovered later,
    since forgetting exactly this for `k8055`/`busylight` was a real bug fixed the same week (see
    2026-09-22's entry).
  - **Full-solution `dotnet test --filter "TestCategory=UNIT"` regression run: all 14 test

- **Tektronix 2230 got a minimal `DevTerm.Devices.Scpi` profile after all**
  (`Profiles/tektronix-2230.json`), revising the "out of scope, needs its own decoder" call above:
  `ScpiControlSurface`'s template substitution has no real dependency on SCPI syntax, so the one
  confirmed command (`ID?`) needed nothing beyond an ordinary profile entry. No `IdnPattern` (the
  existing auto-detect flow hardcodes `*IDN?`, which this device doesn't understand, so it must
  always be picked manually from the list — same convention as `ScpiProfileCatalog.Generic`). See
  `docs/design/proposals/tektronix-2230-protocol.md`'s revised "Status" section for the caveats this
  carries (unconfirmed reply framing — the one known reply is `;`-terminated, not confirmed
  newline-terminated the way `ScpiReplyPresenter` needs; unconfirmed outbound terminator). Bundled
  profile count is now 7; `ScpiProfileCatalogTests.All_BundledProfiles_AreAllLoaded` and a new
  `Tektronix2230_HasNoIdnPatternSoItIsNeverAutoDetected` test updated/added
  (`DevTerm.Devices.Scpi.Tests` now 38/38).
- **Real-hardware report from a 34401A on COM3 (9600 8N2)**: clicking a Measure button beeps the
  device but shows no reply anywhere in the UI. Not yet root-caused with tool access — leading
  hypothesis is the `"scpi"` presenter not being enabled for that connection (unlike `k8055`/
  `busylight`, opening a SCPI panel doesn't itself guarantee the `"scpi"` presenter is active in the
  session's `Pipeline`; `ScpiInstrumentPickerWindow`'s `_catalog.TryGet("scpi", ...)` resolves the
  registered singleton either way, so a null tracker isn't the tell — an inactive pipeline entry
  looks identical from that call site). Not yet fixed or confirmed against the actual hardware;
  carried forward as open follow-up work, not resolved in this entry.
