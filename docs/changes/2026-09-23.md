## SCPI real-hardware follow-ups

Driving the same physical 34401A over real RS-232 (not just the report above) surfaced correct
settings and a real root cause for the "beeps, no measurement" symptom, prompting four follow-ups —
all landed today. See `docs/design/proposals/scpi-instrument-control.md`'s updated "Status" section.

- **Root cause found**: 9600 baud/8 data bits/2 stop bits/no parity/**no hardware handshake**/**LF**
  terminator are the correct settings for this instrument. RS-232 on the 34401A never auto-enters
  remote mode the way GPIB does, so `SYSTem:REMote` must be sent before any query, or the instrument
  answers SCPI error `+550 "Command not allowed in local"` with no measurement. The bundled
  `hp-agilent-keysight-34401a.json` profile now has a `remote` command.
- **`ScpiInstrumentProfile.Notes`** — a free-text field for exactly this kind of operational
  knowledge (required non-default settings, a mandatory preamble command), folded into
  `UiDefinition.Description` by `ScpiUiDefinitionBuilder.Build`. Neither `ControlPanelWindow` nor
  `ControlPanelMode` rendered `Description` before this: WPF gained a `DescriptionText` `TextBlock`
  (collapsed when empty) above the sections panel; the TUI equivalent renders it the same way other
  panel text does. The 34401A profile's `Notes` documents the settings/`SYSTem:REMote` requirement
  above.
- **`CliOptions.Handshake` exposed in both configuration UIs** — already fully wired end-to-end into
  the real serial transport, but previously unreachable from either editor. `DeviceProfilesWindow`
  (WPF) gets a "Handshake:" `ComboBox` row bound to `HandshakeText`/`HandshakeOptions`, right after
  Stop bits. `ConfigureMode` (TUI) gets an `OptionSelector<Handshake>` row in the same position,
  wired through the existing push/pull-fields-to/from-view-model pattern and the serial-only
  visibility toggle every other serial field already uses.
- **`CliOptions.ScpiProfile` persists a saved connection's instrument-profile/auto-detect choice** —
  both front ends' "SCPI Instrument..." menu item now skips its picker dialog when the saved value
  still resolves to a real choice (`ScpiProfileCatalog.AutoDetectChoiceName`, `Generic.Name`, or a
  currently-loaded profile's name), via a small `ResolveSavedScpiProfileChoice` helper duplicated
  (not shared) in `TuiMode.cs`/`MainWindow.xaml.cs`, consistent with this codebase's existing
  precedent for small per-front-end pieces. An unresolvable/blank saved value falls back to showing
  the picker exactly as before. Both front ends' local `ScpiAutoDetectChoice`/`ScpiGenericChoice`
  literals are now derived from the new `ScpiProfileCatalog.AutoDetectChoiceName` const and
  `Generic.Name` respectively, rather than independently redeclared, so a saved choice and the live
  picker can never silently drift out of agreement. Also exposed as a "SCPI profile:" editor row in
  both UIs (a bound `ComboBox` in WPF gated on `IsScpiPresenterSelected`; a `TextField` + "Pick..."
  button reusing the TUI's existing `PickFromList` modal, gated on the `scpi` presenter checkbox).
- **`ScpiProfileCatalog` loads from a per-user `~/.dev-term/scpi-profiles` folder** — in addition to
  the bundled `Profiles/` and app-folder `ScpiProfiles/` drop-in, mirroring
  `DevTermUserDataPaths.ProfilesDirectory`/`UserManifestsDirectory`'s existing convention (computed
  locally in `DevTerm.Devices.Scpi` rather than shared from `DevTerm.Configuration`, which
  references this project, not the other way around).
- **`CliOptions.ExportDirectory`** (unrelated to SCPI specifically, prep for the not-yet-built
  Stream Monitor feature — see `BACKLOG.md`) — a configurable auto-save destination, defaulting to
  a new `DevTermUserDataPaths.ExportsDirectory` (`~/.dev-term/exports`) via
  `EffectiveExportDirectory`. A plain nullable string property needs no special binding code to pick
  up command-line/`DEVTERM_`-environment-variable/settings-file values — confirmed this is already
  true for every such property via the existing `DevTermConfiguration` layering, unlike the
  `Presenter` array property's own special-cased comma-splitting. No editor UI row yet, matching the
  existing `ManifestName` precedent (a `CliOptions` property with no editor field).
- **Test fix**: the Handshake/SCPI-profile rows above push `ConfigureMode`'s HID field group one row
  further down, past what fits in an unscrolled 80x24 headless window —
  `ScreenshotTests.ConfigureMode_HidTransport_IsCaptured` started failing (`'HID vendor ID'` not

## Send-line history recall (Up/Down)

New, shared `SendHistory` (`DevTerm.Configuration`) — a bounded (100-entry), most-recent-first,
in-memory-only history of lines sent from the live session screen's send field in either front end,
so Up/Down cycles through prior input the way a shell history does. `Add(line)` records (no-ops on
blank), `Previous()`/`Next()` step older/newer and reset once past either end, `ResetCursor()` is
exposed for callers that edit the field by hand (not currently wired to either front end — see Open
items below).

- **WPF**: `MainWindow.xaml`'s `SendBox` changed from a plain `TextBox` to an editable `ComboBox`
  (`IsEditable="True"`, `IsTextSearchEnabled="False"`), with `ItemsSource` bound directly to
  `SendHistory.Items` so the drop-down itself shows the same history live. Enter/Up/Down are handled
  on `PreviewKeyDown` (tunneling), not the bubbling `KeyDown` the old `TextBox` used — the same
  "don't trust a native widget's own key handling to compose with ours" reasoning already documented
  for Ctrl+Q (`CLAUDE.md`) — and pulled out into a directly-testable `internal bool
  HandleSendBoxKey(Key key)` method rather than only reachable through the routed event, mirroring
  why `SendCurrentInputAsync` is itself a testable method. `SendBox.Clear()` (a `TextBoxBase`-only
  method, not on `ComboBox`) became `SendBox.Text = string.Empty`.
- **TUI**: Terminal.Gui 2.5.0 has no combo box, so `sendField` in `TuiMode.cs` stays a plain
  `TextField` — its existing `KeyDown` handler gained `Key.CursorUp`/`Key.CursorDown` branches (both
  confirmed as real `Key` properties, and `TextField.MoveEnd()` as a real method, by checking
  `terminal.gui/2.5.0`'s own shipped XML doc comments directly rather than guessing, per this
  repo's established practice for unverified Terminal.Gui API shape) doing the same recall, calling
  `sendField.MoveEnd()` after setting `.Text` so the caret lands after the recalled text rather than
  before it. No visible drop-down — recall-only, functionally equivalent to the WPF side.
- Both front ends call `SendHistory.Add(line)` at the same point they already clear the field on
  Enter/Send, regardless of whether the send itself succeeds afterward (matches how the field already
  cleared unconditionally before this change).
- **Tests**: 12 new `UNIT` tests in `DevTerm.Configuration.Tests/SendHistoryTests.cs` (blank-line
  no-op, most-recent-first ordering, capacity trimming, `Previous`/`Next` boundary behavior,
  `Add`/`ResetCursor` interaction with the cursor). 3 new in `DevTerm.Wpf.Tests/MainWindowTests.cs`
  driving `HandleSendBoxKey` directly (Up recalls the last sent line; Up-Up-Down recalls the newer of
  two; an unrecognized key returns `false`). 2 new in `DevTerm.Console.Tests/TuiModeTests.cs` raising
  `sendField.NewKeyDownEvent(Key.CursorUp/CursorDown)` directly (the same "raise the view's own
  KeyDown instead of the flaky `IInputInjector`" precedent already used by
  `SetParser_SwitchesHowTheNextTypedLineIsEncoded_AndUpdatesTheTitle`, since these tests are about
  recall logic, not key routing). Full `dotnet test --filter "TestCategory=UNIT"` run after: all 15
  test projects pass (`DevTerm.Configuration.Tests` 202/202, `DevTerm.Wpf.Tests` 56/56,
  `DevTerm.Console.Tests` 70/70).
- Docs updated per this repo's "a new user-facing feature needs both a spec and a user-guide entry"
  practice: `docs/user-guide/sending-and-receiving.md` gained Up/Down paragraphs for both the TUI and
  WPF sections; `docs/specs/tui-main-screen.md`/`wpf-main-window.md` gained `Send:`/`SendBox` field
  notes and a Cursor Up/Down (TUI) / Up/Down (WPF) Actions row.
- **Open items**: not persisted across restarts (in-memory for the life of the process only).

## Fixed the SCPI Measure/beep-with-no-reply root cause

Confirmed the leading hypothesis from this same file's earlier real-hardware report (a Measure
button beeping the 34401A with no reply shown anywhere) by reading the code, not by re-testing
against the physical instrument (no hardware access this session — still worth re-verifying live):
`PresenterCatalog.TryGet("scpi", ...)` resolves the DI-registered `ScpiReplyPresenter` singleton
unconditionally (`AddScpiPresenter()` registers it regardless of what a connection's profile
selected), while the session's actual live `Pipeline` — the thing that decides which presenters ever
see incoming bytes — is fixed once, at session-build time, from `CliOptions.EffectivePresenters`
(`DevTermSessionBuilder.Build`). So opening the SCPI Instrument panel on a connection that hadn't
selected "scpi" in its presenter list resolved a real, non-null presenter from the catalog, sent
commands through it successfully (`session.SendAsync` bypasses the pipeline entirely), but the
device's replies were never routed through `ScpiReplyPresenter.Render()` — nothing decoded/
correlated them, and nothing told the user why.

- **Fix — bind the presenter into the session's existing pipeline, don't just detect and warn about
  it being missing.** `Pipeline` (`DevTerm.Core.Presenters`) gained `AddPresenter(IPresenter)`,
  mutating its own live presenter collection in place rather than requiring a caller to build/swap in
  a replacement `Pipeline` — `Session`'s read loop (`PumpAsync`) holds one `Pipeline` reference for
  the session's whole lifetime, so a rebuilt instance would never be seen by the already-running
  loop; only mutating the exact same instance works. `Session` gained a matching
  `AddPresenter(IPresenter)` that delegates to it. `TuiMode.ResolveActiveScpiPresenter` and
  `MainWindow.ResolveActiveScpiPresenter` (the "SCPI Instrument..." menu handlers in both front ends)
  now call `session.AddPresenter(presenter)` before using the catalog-resolved presenter, so opening
  the SCPI panel always wires reply correlation in, regardless of what was selected when the
  connection was made — no warning dialog needed, since the gap is actively closed rather than
  merely reported.
- **`Pipeline`'s presenter collection stays a plain `List<IPresenter>`, synchronized with a
  `System.Threading.Lock`** — an immutable-snapshot-plus-CAS-swap (`ImmutableList<T>`) and
  `System.Collections.Concurrent.ConcurrentQueue<T>` were both tried and rejected during review: the
  former isn't a mutable collection at all (just swapped references), and the latter's
  producer/consumer (Enqueue/Dequeue) naming doesn't match how it's actually used here — nothing is
  ever dequeued, `AddPresenter` only appends and `Render` only enumerates. A lock is cheap: it's held
  only long enough to copy a snapshot, both for `AddPresenter` (rare, from a UI thread opening a
  device control panel) and `Render` (the session's background read loop, called many times a
  second) — the presenters' own `Render` calls, and any lock contention between the two call sites,
  never happen while the lock itself is held.
- **Tests**: 3 new `UNIT` tests in `DevTerm.Core.Tests/Presenters/PipelineTests.cs`
  (`AddPresenter_AppendsToTheSameLiveInstance`, `AddPresenter_AlreadyPresent_DoesNotDuplicate`,
  `AddPresenter_AfterConstruction_IsPickedUpByRender`) and 1 new in
  `DevTerm.Core.Tests/Sessions/SessionTests.cs`
  (`AddPresenter_WhileOpen_IsPickedUpByTheAlreadyRunningReadLoop`) — the last one is the direct
  regression test for this bug: it opens a session with an empty pipeline, calls
  `session.AddPresenter` *after* `OpenAsync` (mirroring the real "already-connected, then open the
  SCPI panel" sequence), then proves a byte written to the transport afterward still reaches the
  late-bound presenter. Full `dotnet test --filter "TestCategory=UNIT"` run after: all 15 test
  projects pass with no regressions.
- **Not yet verified against real hardware** — this session had no access to the 34401A or any other
  bench instrument; the fix is confirmed correct at the code/unit-test level (root cause reproduced
  and closed by a targeted test), but the original live-hardware report that raised this bug hasn't
  itself been re-run.
