# 2026-09-22

## Completed

- **Fix: switching TUI profiles after a failed attempt could silently revert the just-succeeded
  one** — reported as "I tried connecting to 192.168.0.108 and it failed so I tried .107 and it
  won't even try to connect now." Root cause: `TuiMode.SwitchProfileAsync` builds a brand-new
  `Session`/transport per attempt (`DevTermSessionBuilder.Build`), but had no guard against
  overlapping attempts. A slow-to-fail connect (an unreachable LAN host that never actively
  refuses, so it sits on the OS connect timeout, unlike a fast "actively refused" loopback failure)
  could still be pending when the user switched to a *different* host; once the stale attempt
  finally resolved, its success/failure handler ran anyway — using by-then-stale `cliOptions` — and
  overwrote `connectMenuItem.Title`/`sendField.Enabled`/the output log back over whatever the
  newer, current attempt had already set. The newer connection was never actually broken; the UI
  just reverted to looking disconnected sometime after the switch, which reads exactly like "won't
  even try."

  Fix: a `CancellationTokenSource`-based generation guard (`switchCts`). Every call to
  `SwitchProfileAsync` cancels the previous attempt's token before starting its own — real TCP
  connects genuinely honor `CancellationToken` (unlike the documented `SerialPort.BaseStream`/
  `HidStream` cancellation hazards in `CLAUDE.md`), so a superseded attempt now fails fast instead
  of leaking a connect in the background. `ReferenceEquals(switchCts, cts)` checks ensure only the
  *current* (non-superseded) attempt's outcome is ever applied to the shared UI state; a locally
  captured `mySession` (rather than relying solely on the shared `session` closure variable) means a
  superseded-but-successfully-connected stray session gets closed/disposed instead of accidentally
  becoming the active one.

  Also fixed as a related consistency issue: `ToggleConnectionAsync` (the File > Connect/Disconnect
  menu item, which reuses the same session/transport across retries rather than rebuilding) wasn't
  resetting `connectMenuItem.Title`/`sendField.Enabled` back to "disconnected" on a failed *retry* —
  only `SwitchProfileAsync` did. Now symmetric.

  **Regression test**: `TuiModeSwitchProfileTests.SwitchProfileAsync_SupersededByAnotherSwitchBeforeItResolves_DoesNotStompTheNewerOne`
  reproduces the overlapping-attempts race deterministically — the first switch targets
  `TcpTransportMode.Listener` on a port nobody connects to (so `AcceptAsync` blocks indefinitely, a
  controllable stand-in for a slow-to-fail connect) and is never awaited before a second, real
  switch is started and completes; the test then confirms the second attempt's UI state survives the
  first (superseded) attempt's later cancellation/resolution. Console 62 tests (3 skipped), all
  passing; no regressions in the existing `SwitchProfileAsync`/`ToggleConnectionAsync` coverage.

- **WPF "the app crashes if the connection errors out" — investigated live, not reproduced; a
  related state bug fixed for consistency.** This was recorded in `TODO.md`'s Architect notes
  *after* `979dd45`'s `OnClosing` reentrancy fix (2026-09-18), so it wasn't obvious whether it was a
  stale report or a real remaining gap. `MainWindow.ConnectAsync`'s failure path (the one reachable
  at real app startup, via `Loaded` → `ConnectAsync`) shows a `MessageBox` then calls `Close()`,
  which is exactly the reentrant-`OnClosing` shape `979dd45` fixed — but that fix's regression tests
  (`MainWindowTests.Close_*`) call `Close()` directly, never through `ConnectAsync`'s own catch
  block, so the exact reported path was never actually exercised by a test.

  Verified live instead, since `MessageBox.Show` is a real blocking modal with no automated way to
  dismiss it (see `MainWindowSwitchProfileTests`'s doc comment — an already-accepted gap for this
  front end's failure paths): built and launched the real `DevTerm.Wpf.exe` against a refused TCP
  loopback port, located the resulting "dev-term — connection failed" dialog and its OK button via
  `user32.dll` window enumeration, and drove it with `BM_CLICK` (bypasses the foreground-window
  focus restrictions `SetForegroundWindow`/`SendKeys` hit when driven from an unrelated process).
  Twice, on two different refused ports: the process exited cleanly afterward (`HasExited: True`,
  no hang, no Windows Error Reporting), and the Application event log had no `.NET Runtime`/
  `Application Error` entries for either run. **Could not reproduce the crash** — this path already
  behaves as intended (report the error, then close, matching `CliMode`/`TuiMode`'s startup-failure
  behavior) as of `979dd45`.

  What *was* still a real (if separate) bug: `ToggleConnectionAsync`'s failure catch — reusing the
  same session/transport across retries, unlike `ConnectAsync`/`SwitchProfileAsync` — showed the
  `MessageBox` but never reset `ConnectMenuItem.Header`/`SendBox.IsEnabled` back to "disconnected"
  on a failed retry, the same asymmetry just fixed in the TUI. Fixed to match. Not independently
  testable for the same `MessageBox.Show`-is-blocking reason as the rest of this method's failure
  path — verified by code review/parity with the TUI fix (which *is* covered by a real regression
  test) rather than an automated WPF test. Wpf 41 tests (2 skipped), all passing; no regressions.

- **Added `LoopbackTransport`, a scripted deterministic test device** (`DevTerm.Console.Tests`) —
  motivated by wanting to exercise request/response and multi-line "event" behavior in tests without
  needing a real device online (only two were reachable at the time this was discussed) and without
  the `INTEGRATION`-tier ceremony of a real `TcpListener` loopback socket when the actual network
  stream isn't what's under test. It's an in-process `ITransport`, the same `Pipe`-backed shape as
  the existing `FakeTransport`, but driven by a script of regex-matched commands
  (`LoopbackRule`/`LoopbackScript`) instead of requiring a test to manually call
  `PushIncomingAsync` after every write. `LoopbackGenerators` produces deterministic (no `Random`)
  multi-character/multi-line output so tests can assert exact text; each response line is pushed
  back as its own write so a line-buffering presenter sees separate lines, which is what makes an
  "N discrete events" reply possible. An unmatched command gets a visible `? Unrecognized: ...` reply
  rather than silence, so a test with an incomplete script fails on wrong output instead of hanging.

  `LoopbackScript.Default()` covers three example commands: an exact-match `"hello"` →
  `"From Loopback test"`, a parameterized `"Send Stream: N, ascii"` → an N-character deterministic
  ASCII run, and a parameterized `"Send Events: N"` → N separate `"Event 1"` .. `"Event N"` lines.
  `LoopbackTransportTests` (5 tests, `UNIT`) exercises it through a real `Session`/`AsciiPresenter`
  pair, the same composition `TuiMode`/`MainWindow` use. See `docs/design/testing.md`'s "Scripted
  responses without a real device" section for the full design rationale. Not yet wired into any
  TUI/WPF-level test — this is a building block for future ones, not a replacement for the existing
  `FakeTransport`/real-loopback patterns where those already fit.
