## Completed

- **Fix: switching TUI profiles after a failed attempt could silently revert the just-succeeded
  one** — reported as "I tried connecting to 192.168.0.108 and it failed so I tried .107 and it
  won't even try to connect now." Root cause: `TuiMode.SwitchProfileAsync` builds a brand-new
  `Session`/transport per attempt (`DevTermSessionBuilder.Build`), but had no guard against
  overlapping attempts. A slow-to-fail connect (an unreachable LAN host that never actively
  refuses, so it sits on the OS connect timeout, unlike a fast "actively refused" loopback failure)
  could still be pending when the user switched to a *different* host; once the stale attempt
  finally resolved, its success/failure handler ran anyway — using by-then-stale `cliOptions` — and
  overwrote `connectMenuItem.Title`/`sendField.Enabled`/the output log back over whatever the
  newer, current attempt had already set. The newer connection was never actually broken; the UI
  just reverted to looking disconnected sometime after the switch, which reads exactly like "won't
  even try."

  Fix: a `CancellationTokenSource`-based generation guard (`switchCts`). Every call to
  `SwitchProfileAsync` cancels the previous attempt's token before starting its own — real TCP
  connects genuinely honor `CancellationToken` (unlike the documented `SerialPort.BaseStream`/
  `HidStream` cancellation hazards in `CLAUDE.md`), so a superseded attempt now fails fast instead
  of leaking a connect in the background. `ReferenceEquals(switchCts, cts)` checks ensure only the
  *current* (non-superseded) attempt's outcome is ever applied to the shared UI state; a locally
  captured `mySession` (rather than relying solely on the shared `session` closure variable) means a
  superseded-but-successfully-connected stray session gets closed/disposed instead of accidentally
  becoming the active one.

  Also fixed as a related consistency issue: `ToggleConnectionAsync` (the File > Connect/Disconnect
  menu item, which reuses the same session/transport across retries rather than rebuilding) wasn't
  resetting `connectMenuItem.Title`/`sendField.Enabled` back to "disconnected" on a failed *retry* —
  only `SwitchProfileAsync` did. Now symmetric.

  **Regression test**: `TuiModeSwitchProfileTests.SwitchProfileAsync_SupersededByAnotherSwitchBeforeItResolves_DoesNotStompTheNewerOne`
  reproduces the overlapping-attempts race deterministically — the first switch targets
  `TcpTransportMode.Listener` on a port nobody connects to (so `AcceptAsync` blocks indefinitely, a
  controllable stand-in for a slow-to-fail connect) and is never awaited before a second, real
  switch is started and completes; the test then confirms the second attempt's UI state survives the
  first (superseded) attempt's later cancellation/resolution. Console 62 tests (3 skipped), all
  passing; no regressions in the existing `SwitchProfileAsync`/`ToggleConnectionAsync` coverage.

- **Added `LoopbackTransport`, a scripted deterministic test device** (`DevTerm.Console.Tests`) —
  motivated by wanting to exercise request/response and multi-line "event" behavior in tests without
  needing a real device online (only two were reachable at the time this was discussed) and without
  the `INTEGRATION`-tier ceremony of a real `TcpListener` loopback socket when the actual network
  stream isn't what's under test. It's an in-process `ITransport`, the same `Pipe`-backed shape as
  the existing `FakeTransport`, but driven by a script of regex-matched commands
  (`LoopbackRule`/`LoopbackScript`) instead of requiring a test to manually call
  `PushIncomingAsync` after every write. `LoopbackGenerators` produces deterministic (no `Random`)
  multi-character/multi-line output so tests can assert exact text; each response line is pushed
  back as its own write so a line-buffering presenter sees separate lines, which is what makes an
  "N discrete events" reply possible. An unmatched command gets a visible `? Unrecognized: ...` reply
  rather than silence, so a test with an incomplete script fails on wrong output instead of hanging.

  `LoopbackScript.Default()` covers three example commands: an exact-match `"hello"` →
  `"From Loopback test"`, a parameterized `"Send Stream: N, ascii"` → an N-character deterministic
  ASCII run, and a parameterized `"Send Events: N"` → N separate `"Event 1"` .. `"Event N"` lines.
  `LoopbackTransportTests` (5 tests, `UNIT`) exercises it through a real `Session`/`AsciiPresenter`
  pair, the same composition `TuiMode`/`MainWindow` use. See `docs/design/testing.md`'s "Scripted
  responses without a real device" section for the full design rationale. Not yet wired into any
  TUI/WPF-level test — this is a building block for future ones, not a replacement for the existing
  `FakeTransport`/real-loopback patterns where those already fit.

- **Global unhandled-exception handling, so a genuine bug doesn't take the whole app down** —
  explicit request: an unexpected exception (anything past the deliberate, already-handled
  `ConnectionErrorMessages.IsConnectionFailure` cases) shouldn't kill the process outright.

  `DevTerm.Wpf`'s `App.xaml.cs` hooks two events in `OnStartup`: `DispatcherUnhandledException`
  (reports via a `MessageBox` and sets `e.Handled = true`, which is what actually tells WPF not to
  terminate — left unset, the runtime tears the app down right after the handler returns regardless
  of what it does) and `TaskScheduler.UnobservedTaskException` (a faulted, never-`await`ed background
  `Task`; fires on the finalizer thread, so the `MessageBox.Show` call is marshaled over via
  `Current?.Dispatcher.BeginInvoke` rather than called directly). Verified: full WPF `UNIT` suite
  (38/38) plus a live relaunch of the built exe confirming normal startup/connect still works.

  `DevTerm.Console` has no `Dispatcher` to intercept a synchronous exception the same way, so the
  equivalent behavior split across its two front ends: `Program.cs` hooks
  `TaskScheduler.UnobservedTaskException` process-wide (reports to stderr; covers both `CliMode` and
  `TuiMode`, e.g. `TuiMode`'s fire-and-forget menu actions like `_ = ToggleConnectionAsync(...)`),
  and `TuiMode.RunAsync` passes an `errorHandler` to `Application.Run` — a real Terminal.Gui v2.5.0
  API (`Run(IRunnable, Func<Exception, bool>)`) found by reflecting the installed package rather than
  guessing: returning `true` from the handler resumes the main loop instead of exiting, reported via
  `MessageBox.ErrorQuery(Application.Instance, ...)`. Per Terminal.Gui's own XML doc comment on that
  overload, it only takes effect in RELEASE builds — a DEBUG build still rethrows so a debugger can
  break on the original exception. `CliMode` needed no change beyond the process-wide hook above: it
  already catches the same known failure modes per line every other front end does, and an
  unanticipated exception there should still produce a hard non-zero-exit crash rather than being
  swallowed, since it's the scriptable/automation-facing mode and hiding a real bug from whatever's
  driving it via a script or CI pipeline would be worse than a visible failure.

  Not independently unit-tested (would mean either faking a `Dispatcher`/main-loop exception, which
  none of the existing test infrastructure does, or actually throwing from inside a real
  `Application.Run`/WPF dispatch cycle) — verified by full-solution regression instead:
  `dotnet build` (0 errors, only pre-existing obsolete-API warnings) and
  `dotnet test --filter "TestCategory=UNIT"` across all 12 assemblies, 0 failed.

  **Counter 1 anomaly, investigated and resolved**: immediately after clicking Reset, the panel
  showed Counter 1 at 22819 rather than 0 (Counter 2 correctly read 0). Root-caused by reading raw
  `hex`-presenter frames directly (bypassing `K8055Decoder` entirely) with nothing wired to the
  board: Counter 1's byte pair climbed by a rock-steady ~70 counts *per HID report*, hundreds of
  reports/second, in a near-perfectly linear ramp — while Counter 2's byte pair sat frozen at
  `0x0000` for the entire multi-hundred-report capture. Same decode path, same code, wildly
  different behavior per field is strong evidence this is genuine board electrical behavior, not a
  decoder or reset-encoding bug: an unconnected, high-impedance CMOS counter input pin can
  self-oscillate at a stable rate (input hysteresis charging/discharging through parasitic
  capacitance), and Counter 1's floating pin apparently does this on this board/environment while
  Counter 2's doesn't. At the observed rate, the 16-bit counter wraps roughly every ~9 seconds, so
  22819 is fully explained by the real-world delay (several sequential UI-automation steps, each
  with its own overhead) between the Reset click and the screenshot capture — the reset itself
  works correctly.

- **Three issues reported from live use of the K8055/Busylight panels, all fixed the same day.**

  **K8055: digital inputs never read as anything but 0.** Reported as "the k8055 doesn't seem to read
  in the digital inputs... but the other values seem to work fine." Root cause: `K8055Decoder.DecodeFrame`
  read `digitalInRaw` from `frame[0]` — but byte 0 of this 9-byte frame is the same leading HID
  report-ID byte already confirmed live for both this device's own outbound frames and
  `BusylightControlSurface` (always `0x00`, never real device data — see `CLAUDE.md`'s HID
  report-ID-prefix note). The real 8-byte K8055 payload starts at byte 1, so `digitalInRaw` always
  reported a constant `0x00` regardless of physical input state — indistinguishable from "nothing
  wired" until something actually was. Fixed: `digitalInRaw = frame[1]`.
  `K8055DecoderTests.Render_WithNonZeroDigitalInByte_ReportsItRawInHex` updated to mutate byte 1
  instead of byte 0 to match. This is a code-inspection fix consistent with the already-confirmed
  report-ID convention, not a new real-hardware finding — **not yet reconfirmed live**; that, and the
  digital-in bit-to-channel mapping itself, both still need the board rewired one pin at a time (see
  `docs/design/proposals/velleman-k8055-protocol.md`'s open questions).

  **Busylight: "Custom..." did nothing.** Reported along with a specific ask: a modal with RGB
  selection, and (corrected from an initial "HSB" typo) HSV too. Rather than a Busylight-specific
  fix, added `ButtonControl.ColorPickerTargetCommandId` (`DevTerm.UiDefinitions`) — a new, generic,
  device-agnostic field any button in any device's `UiDefinition` can set to mean "open a modal
  RGB/HSV color picker instead of invoking me directly; on confirm, send the result as an
  `"r,g,b"`-formatted string (each 0-255, invariant culture) to the command id named here." Both
  generic renderers implement it: WPF's new `ColorPickerWindow` (a preview swatch, a hex text box, RGB
  sliders, and HSV sliders, all kept in sync via internal `RgbToHsv`/`HsvToRgb` conversions — OK/
  Cancel buttons sized `32`x`80` after a follow-up report that the original size was unreadable) and
  the TUI's new `ControlPanelMode.PickColor` (a nested `Application.Run(dialog)` modal, matching
  `ConfigureMode`'s existing picker pattern, with the same RGB/HSV fields as text inputs — its
  `Accepting` handlers are inline lambdas rather than named methods with an explicit `EventArgs` type,
  since the installed Terminal.Gui version's exact event-args type wasn't confirmed and every other
  handler in this codebase already uses the same inline-lambda convention rather than spelling it
  out). `BusylightUiDefinition`'s "Custom..." button now sets
  `ColorPickerTargetCommandId = "color"`, and `BusylightControlSurface.SetColor` accepts either a
  named preset (unchanged) or a `"r,g,b"` triple (`TryParseRgbTriple`, new). The RGB↔HSV math is
  duplicated between the two front ends (not shared) — no project sits between `DevTerm.Core`/
  `DevTerm.UiDefinitions` and either front end, and ~20 lines of conversion math didn't justify a new
  shared dependency.

  **Busylight: "Program Sequence..." did nothing.** This was already a confirmed, real-hardware-tested
  no-op (the batch/program-mode write is checksum-correct per
  `docs/design/proposals/kuando-busylight-protocol.md` but has no visible effect on the real device) —
  rather than re-investigating an already-closed question, the button was removed from
  `BusylightUiDefinition` entirely, since a button that does nothing on real hardware is worse than no
  button. `BusylightControlSurface` still accepts `programSequence` as a no-op command, for backward
  compatibility with anything already scripted against it.

  **Output-cap parity between the two front ends.** While verifying the above, noticed the WPF/TUI
  output panes didn't actually follow the same rule despite `MainWindow`'s own doc comment claiming
  one: `MainWindow.AppendOutput` capped `OutputList` at `MaxOutputLines` (1000, oldest dropped first),
  but 8 other call sites (`Disconnected.`, `Connected to ...`, `Not connected...`, send failures/
  timeouts, manifest warnings, profile-switch messages) added directly to `OutputList.Items` instead,
  bypassing the cap entirely. All 8 now route through `AppendOutput`. The TUI's `TuiMode.AppendOutput`
  had no cap at all — it grew a single concatenated `TextView.Text` string without bound for the
  entire session. Fixed with the same oldest-dropped-first rule via a bounded `List<string>`, but at a
  shorter cap (300, not 1000): unlike WPF's virtualized `ListBox`, the TUI pane rebuilds one `string`
  from the whole buffer on every trim, so keeping that rebuild cheap mattered more than matching WPF's
  number exactly.

  Full-solution regression after all four fixes: `dotnet build` (0 errors, only the same pre-existing
  Terminal.Gui obsolete-API warnings as before) and `dotnet test --filter "TestCategory=UNIT"` — 416
  tests across 13 assemblies, 0 failed. No new test coverage was added for the color-picker RGB/HSV
  conversion helpers or the `ColorPickerTargetCommandId` rendering path itself (both front ends'
  conversions are straightforward, verified by build + live use rather than unit-tested); this is a
  known gap, not an oversight, if revisited later.

- **K8055: stop re-rendering live indicators on every unchanged report.** Reported alongside the
  above: the K8055 streams its 9-byte input report continuously and unprompted (confirmed in
  `docs/design/proposals/velleman-k8055-protocol.md`), and most consecutive frames repeat the exact
  same reading — `K8055Decoder.Render` was firing `ValuesChanged` with the full 5-key dictionary on
  *every* frame regardless, so both control panels' indicator labels were being reassigned dozens of
  times a second even when nothing on the device actually changed, described as "runaway data
  streaming." `K8055Decoder` now keeps a `Dictionary<string, string>` of the last value published per
  key and only includes a key in the dictionary it raises `ValuesChanged` with when that key's value
  actually differs from what it last published — and skips raising the event at all for a frame where
  nothing changed. Both `ControlPanelMode` (TUI) and `ControlPanelWindow` (WPF) already iterate
  `foreach (id, value) in values` and update only the matching indicator, so a partial dictionary
  (only the changed keys) needed no consumer-side changes. Covered by two new unit tests in
  `K8055DecoderTests`: an identical repeated frame raises the event exactly once (on the first frame),
  and a frame that changes only one field raises a second event containing only that field. Not yet
  re-verified against the real board (the original report was about UI responsiveness, not a decoding
  correctness bug), but the fix only changes *when* a correctly-decoded value is published, not how
  it's decoded.

- **Fix: the K8055/Busylight control panels' live indicators never updated when the device was
  selected through the Device Profiles / Configure Connection editor, only via `--presenter` on the
  command line.** Reported live (WPF): "I can now set the outputs but the input values dont capture
  the data" after launching unconfigured and switching to the K8055 through the GUI editor. Root
  cause: `ConnectionEditorViewModel.PresenterOptions` — the fixed list backing both front ends'
  presenter checkbox picker — was hardcoded to the six built-in text presenters
  (`ascii`/`utf8`/`hex`/`decimal`/`octal`/`binary`) and never included `k8055`/`busylight`. Picking a
  device through the editor could set the right transport/HID ids (so `K8055ControlSurface`'s writes,
  built directly from the live `Session`, worked fine) but had no way to also check the `k8055`
  presenter, so `CliOptions.EffectivePresenters` stayed on its default and the `K8055Decoder`
  instance the control panel resolves via `PresenterCatalog.TryGet("k8055", ...)` was never actually
  part of the session's `Pipeline` — it existed in the catalog but was never fed a single byte, so its
  `ValuesChanged` never fired. This was never reachable via `--presenter k8055` on the command line
  (all real-hardware verification so far used that), which is why it wasn't caught earlier.

  Fixed by adding `"k8055"`/`"busylight"` to `PresenterOptions`; the separate `Parser`
  (`ConfigureMode.PresenterChoice`) enum correctly stays untouched, since neither decoder implements
  `IPresenterInput` (they're display-only, can't encode typed sends). Two existing tests asserting
  the exact checkbox list/order needed updating for the two new entries:
  `ConfigureModeTests.PresenterCheckBoxes_ShowTheInitialPresenters_...` (TUI) and
  `DeviceProfilesWindowTests`'s equivalent (WPF) — both now pass with the 8-entry list. Also
  discovered and removed two now-superseded diagnostic test methods from `ControlPanelModeTests`
  (real-key-injection probes written while chasing an earlier, narrower "TUI analog-out slider does
  not function" report before this broader root cause was found) — they were triggering the
  documented cross-test `IInputInjector` degradation gotcha (`CLAUDE.md`) and intermittently breaking
  an unrelated `TuiModeTests` test in the same run; the commit logic they were probing is already
  covered without real key injection by `Slider_WhenCommitted_ClampsAndInvokesItsIdWithTheValue`.
  Full-solution regression: `dotnet build` (0 errors) and `dotnet test --filter "TestCategory=UNIT"`
  — 428 tests across 14 assemblies, 0 failed. The connection-editor screenshot fixtures in
  `docs/user-guide/images/` were regenerated as a side effect (they now show the two additional
  checkboxes) — not independently re-verified against real hardware yet.
