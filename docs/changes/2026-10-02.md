## Tektronix TDS2024: the "no reply to TRIGger queries" finding was write pacing

Re-checked against the real unit (`192.168.0.110:23`) after the user saw `TRIGger:STATE?` answer with
byte-paced writes. With `--writebytedelayms 50`, `TRIGger:STATE?` replied `TRIGGER`; without it, every
`TRIGger...?` query had been silent in both earlier sessions. The unit (and its serial-to-Ethernet bridge)
has no input FIFO, so a command written as one burst loses bytes. This overturns BACKLOG's old hypothesis
that the unit needs TDS2024B firmware. Also observed: the bridge can deliver a reply one connection late.
No code change; `tektronix-tds2024.json`'s `Notes` now records the delay and the stale-reply behavior, and
BACKLOG's TDS2024 item became a smaller follow-up (re-enable `TRIGger` in `RealHardwareTcpTests`). Full
transcript: `docs/test/2026-10-02-07-01-24.md`.

## Bug 065 filed: HP-GL plots split into several Stream Monitor captures

Reported live on a Tektronix 2230 (`192.168.0.108`, 4800 baud): one "Plot Start" produced several HP-GL
captures. `StreamContentEndFinder.For(Hpgl)` returns `null` by design, so only the 2 s idle timeout ends
an HP-GL capture, and at 4800 baud (~480 bytes/s) a pause past 2 s mid-plot is easy to hit. Filed as
[065](../bugs/065-hpgl-no-end-detection-splits-one-plot.md) (Medium, Open, not fixed); its suggested fix
covers a real HP-GL end finder and a baud-rate-aware idle timeout.

## `scripts/image-diff/image_diff.py`: opt-in auto-restore and cropped diff previews

`diff` gained `--auto-restore-threshold N` (off by default; restores a file whose unmasked diff is at most
N pixels and logs it as `AUTO`) and `--crop-padding`. `--save-diff` now writes a cropped before/after/diff
image around the diff's bounding box instead of the whole screenshot, so reviewing a flagged diff costs far
less. The threshold is deliberately not a tolerance: the tool's premise is that every unmasked diff pixel is
a real change, so it is for a diff already reviewed and judged incidental, not for unattended runs.

## DS1102E: baseline pass, and why block replies can't reach the missing-ZLP boundary

Bench pass over USBTMC (`docs/test/2026-10-02-07-08-35.md`): `*IDN?`, `:ACQ:MEMD?`, `:WAV:POIN:MODE?`, `:TIM:SCAL?`,
`:CHAN1:SCAL?` and a 610-byte `:WAV:DATA? CHAN1` all replied cleanly, and a following `*IDN?` was uncorrupted. For
BACKLOG's missing-ZLP item: from the observed 610- and 8202-byte replies, a block reply's bulk-IN transfer is N + 24
bytes (12 header + 10 block header + 2 pad), 24 mod 64 for any power-of-two N, so it can never end on a 64-byte
boundary. The edge case needs a text reply of 52/116 payload bytes. Still unreproduced; no code change.

## Value-path catalog and unknown-reference warning (expression picker, step 1)

`DevTerm.DeviceManifests.ValuePathCatalog.Enumerate(manifest)` lists every id an expression can read, from the
manifest alone: response-pattern names and named capture groups (type inferred from the group's regex: numeric
classes read as a number, else text), query reply ids, and panel controls (slider/numeric range and unit, toggle,
choice options). `DeviceManifestValidator` now warns, without blocking, when an indicator, chart-channel or button
parameter expression reads an id nothing publishes (a typo otherwise evaluates as 0 silently). Tests:
`ValuePathCatalogTests` (8, including one that loads every bundled manifest and expects no such warning). A full
`dotnet build` hit a file lock on `DevTerm.Wpf` output from a running WPF app; the touched projects built and their
tests passed (DeviceManifests 74, UiDefinitions 128, Console manifest-filtered 32). Not yet done: sample data, picker, language.

### SCPI profile input

`ValuePathCatalog.Enumerate(UiDefinition)` reads a bare UI definition, so a SCPI instrument profile is catalogued via
`ScpiUiDefinitionBuilder.Build(profile)` (a `{command}.reply` per query, a `{command}.{parameter}` per parameter with its
range/unit). The catalog gains no dependency on `DevTerm.Devices.Scpi`; the SCPI test project references DeviceManifests
instead. `ScpiValuePathTests` (2, including every bundled profile) pass.

## Sample-data generator (expression picker, step 2)

`DevTerm.DeviceManifests.SampleDataGenerator.Values(paths, seed, step)` returns a numeric dictionary that
`Expression.Evaluate` can read, from the catalog's paths: numbers walk smoothly (sine plus a little noise) inside the
path's Minimum/Maximum (0..100 when undeclared, rounded to a span-appropriate precision), booleans alternate, choices
cycle by index (`Text` gives the label), text paths are omitted. Deterministic: seeded with an FNV-1a hash, since
`string.GetHashCode` is randomized per process. `SampleDataGeneratorTests` (4, including an expression evaluated over
generated data). Not yet wired into the manifest editor preview; recorded-log and declared-example sources are later.

## Manifest editor preview shows sample data

`ManifestEditorViewModel.PublishSampleData` fills the preview panel's presenter with `SampleDataGenerator` values
(numbers invariant-culture, choices by label), called after the preview is built in both the TUI
(`ManifestEditorMode.ShowPreview`) and WPF (`ManifestEditorWindow.RefreshPreview`) editors, so indicators and
expression results show realistic values with no device. Backed by a new `LineReplyPresenter.PublishValues` and
`ManifestReplyPresenter.PublishSampleValues`. Tests: two in `ManifestEditorTests`; DeviceManifests 80, Core 147 and the
Console manifest-editor tests (18) pass. The WPF project compiled without `CS` errors but its build could not finish
(a running WPF app locks the output), so the WPF preview is not exercised yet.
