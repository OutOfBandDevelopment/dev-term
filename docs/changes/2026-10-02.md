## Tektronix TDS2024: the "no reply to TRIGger queries" finding was write pacing

Re-checked against the real unit (`192.168.0.110:23`) after the user saw `TRIGger:STATE?` answer with
byte-paced writes. With `--writebytedelayms 50`, `TRIGger:STATE?` replied `TRIGGER`; without it, every
`TRIGger...?` query had been silent in both earlier sessions. The unit (and its serial-to-Ethernet bridge)
has no input FIFO, so a command written as one burst loses bytes. This overturns BACKLOG's old hypothesis
that the unit needs TDS2024B firmware. Also observed: the bridge can deliver a reply one connection late.
No code change; `tektronix-tds2024.json`'s `Notes` now records the delay and the stale-reply behavior, and
BACKLOG's TDS2024 item became a smaller follow-up (re-enable `TRIGger` in `RealHardwareTcpTests`). Full
transcript: `docs/test/2026-10-02-07-01-24.md`.

## Bug 065 filed: HP-GL plots split into several Stream Monitor captures

Reported live on a Tektronix 2230 (`192.168.0.108`, 4800 baud): one "Plot Start" produced several HP-GL
captures. `StreamContentEndFinder.For(Hpgl)` returns `null` by design, so only the 2 s idle timeout ends
an HP-GL capture, and at 4800 baud (~480 bytes/s) a pause past 2 s mid-plot is easy to hit. Filed as
[065](../bugs/065-hpgl-no-end-detection-splits-one-plot.md) (Medium, Open, not fixed); its suggested fix
covers a real HP-GL end finder and a baud-rate-aware idle timeout.

## `scripts/image-diff/image_diff.py`: opt-in auto-restore and cropped diff previews

`diff` gained `--auto-restore-threshold N` (off by default; restores a file whose unmasked diff is at most
N pixels and logs it as `AUTO`) and `--crop-padding`. `--save-diff` now writes a cropped before/after/diff
image around the diff's bounding box instead of the whole screenshot, so reviewing a flagged diff costs far
less. The threshold is deliberately not a tolerance: the tool's premise is that every unmasked diff pixel is
a real change, so it is for a diff already reviewed and judged incidental, not for unattended runs.

## DS1102E: baseline pass, and why block replies can't reach the missing-ZLP boundary

Bench pass over USBTMC (`docs/test/2026-10-02-07-08-35.md`): `*IDN?`, `:ACQ:MEMD?`, `:WAV:POIN:MODE?`, `:TIM:SCAL?`,
`:CHAN1:SCAL?` and a 610-byte `:WAV:DATA? CHAN1` all replied cleanly, and a following `*IDN?` was uncorrupted. For
BACKLOG's missing-ZLP item: from the observed 610- and 8202-byte replies, a block reply's bulk-IN transfer is N + 24
bytes (12 header + 10 block header + 2 pad), 24 mod 64 for any power-of-two N, so it can never end on a 64-byte
boundary. The edge case needs a text reply of 52/116 payload bytes. Still unreproduced; no code change.
