# 2026-09-15

## Completed

- Formalized a design discussion into the docs: whether a declarative command/response schema for
  device control modules already had a plan (it did, partially), and what DSL options fit.
  Added a new section to `docs/design/device-control-modules.md` (cross-linked from
  `presenters.md`'s mapping-format open question): a dev-term-owned schema for command+response
  definitions (reusing the existing mapping-file precedent, not a new external format), with
  [Kaitai Struct](https://kaitai.io/) recommended specifically for binary response layouts (it has
  no concept of *sending*, so only ever covers the response half), and a built-in SCPI baseline
  (`*IDN?`, `*RST`, `*CLS`, `*OPC?`) as a zero-authoring fallback for common bench-instrument
  commands.
- Full documentation review pass across every markdown file in the repo, requested explicitly
  rather than left to drift. Found and fixed real staleness/bugs, not just cosmetic touch-ups:
  - `CLAUDE.md` was completely stale — still described the repo as empty (from the very first
    `/init`, before any code existed). Fully rewritten to reflect the actual current project:
    build/test commands, project layout, the Pipelines-based read path, the
    zero-or-more-outputs `IPresenter.Render` contract, the Options-pattern/`DevTermConfiguration`
    layering, and — most valuable for future sessions — the non-obvious constraints that cost
    real debugging time this project (Moq can't mock `Span<T>`, `SerialPort.BaseStream.ReadAsync`
    doesn't reliably cancel, `SerialPort` defaults DTR/RTS off, `Configuration.CommandLine` has no
    bare-boolean-flag support) so they don't get silently reintroduced or rediscovered later.
  - `README.md`'s "Status" section still said "no application code yet" — updated to reflect what's
    actually built and verified against real hardware, and added the missing `rfc2217.md` link to
    the documentation list.
  - `docs/design/frontends.md` had a literal duplicate `## TUI (full-screen terminal UI)` heading
    (a leftover editing artifact) and an internal inconsistency — the doc's own "Executables"
    section explains there are two deployable apps (not three), but "Shared foundation" still said
    "all three front ends"; retitled the doc "CLI, TUI, GUI" (modes, not separate front ends) and
    fixed the wording throughout. Also added an "Implemented" note on the CLI section: the built
    CLI is actually an interactive REPL-like loop by default, not the pure batch/pipe mode the
    original design text described — that description is still the intent for a dedicated
    non-interactive mode, just not what exists today under the same heading.
  - `docs/design/plugin-model.md` overstated current reality — its "Built-in vs. plugin" section
    read as if built-ins were already loaded through the (unbuilt) plugin mechanism. Clarified that
    today's built-ins are wired by hand in each front end's `Program.cs` against the same
    contracts a real plugin would use, but dynamic loading itself doesn't exist yet.
  - Updated `TODO.md`: moved the TUI/WPF work from backlog to "in progress" (see below), added the
    new declarative-schema backlog item, and added the presenter-lifetime issue as an explicit
    backlog item tied to when it'll actually start mattering (concurrent sessions in one process).
  - `docs/design/transports.md`, `presenters.md`, `platform.md`, `rfc2217.md`, and the design
    index were already accurate from prior sessions' updates — no changes needed there.
