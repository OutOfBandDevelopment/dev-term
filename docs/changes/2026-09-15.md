- **Scoped USB HID, BLE, GPIB, and USBTMC transports** in `docs/design/transports.md` against
  real target hardware and a direct architecture decision:
  - USB HID: [HidSharp](https://www.nuget.org/packages/HidSharp) (cross-platform, no vendor driver
    needed).
  - BLE: explicitly chosen to be **cross-platform**, via a small internal per-OS adapter seam
    (Windows/`Windows.Devices.Bluetooth` first; Linux/BlueZ and macOS/CoreBluetooth addable later,
    including as community/self-contributed adapters) rather than shipping Windows-only the way
    the WPF front end does. Named the common "BLE Serial" pattern explicitly (Nordic UART Service
    UUIDs as the default, but configurable — not every "acts like serial over BLE" device actually
    uses NUS). Target hardware: an LCR meter reachable over BLE, pending identification of its
    make/model and GATT profile.
  - GPIB: researched what cheap eBay "IEEE-488 to USB" adapters actually speak — most (including
    DIY [AR488](https://github.com/Twilight-Logic/AR488)-firmware boards) implement the Prologix
    `++` ASCII protocol over a plain serial or TCP connection, needing only a thin controller layer
    on the existing transports, not a new one. A separate, **not recommended**, family instead
    clones National Instruments' proprietary GPIB-USB-HS protocol (non-serial, driver-dependent,
    reportedly unreliable even against genuine NI hardware) — flagged so a purchase decision can
    check which protocol a specific listing actually speaks first.
  - USBTMC: identified as the actual USB class most bench SCPI equipment uses locally over USB
    (confirmed via vendor docs for the Rigol DG1022 family — the DG1022Z/DG1062Z also support LAN
    with VXI-11 and raw-socket SCPI, already covered by the existing TCP transport, but the plain
    DG1022 has no LAN option). Neither HID nor serial — its own USB class with bulk endpoints and
    message framing — so it needs its own raw-USB transport (WinUSB/LibUsbDotNet), not yet designed
    in detail.
  - Also noted: the project's own Tek 2230 test device is itself an example of the "SCPI-precursor,
    needs a custom decoder" oscilloscope category (Tektronix's own pre-SCPI "codes" command
    language, comma/semicolon-delimited) mentioned for a wider scope fleet — a candidate for its
    own proposal doc once specific models are identified.
