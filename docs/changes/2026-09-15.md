- **Built the USB HID transport** (`DevTerm.Transports.Hid`, HidSharp 2.6.4) end-to-end: options,
  `IHidDevice`/`SystemHidDevice`/`IHidDeviceFactory`/`IHidDeviceDiscovery` mirroring the serial
  transport's shape exactly, and CLI wiring (`--transport hid --hidvendorid <n> --hidproductid <n>
  [--hidserialnumber <sn>]`, `--listhiddevices true`, validator, `ConnectionDescription`,
  `ConnectionErrorMessages` hint, `AddDevTermFrontEnd`). 136 tests across the solution now (10 new
  for the HID transport, 9 new in `DevTerm.Configuration.Tests`).

  The interesting design problem: HidSharp gives no event analogous to `SerialPort.DataReceived`
  to wait on for "a report is ready," and its `Read`/`Write` are plain `BeginRead`/`EndRead`-backed
  under a default `Stream.ReadAsync`, which — like `SerialPort.BaseStream.ReadAsync` — doesn't
  meaningfully honor a `CancellationToken` once a read is in flight. Solved with a dedicated
  background thread (owned and joined on close, not a `Task.Run`-wrapped blocking call per read,
  which was already rejected for serial for the same "orphaned, unobserved background work" reason)
  that blocks on `HidStream.Read` bounded by `ReadTimeout` and hands completed reports to a
  `Channel<byte[]>`; the actual `ReadAsync` only ever awaits the channel, so cancellation is
  immediate and correct regardless of the background thread's own bounded shutdown.

  Verified against real hardware (a mouse's RGB-control HID interface, and `--listhiddevices`
  against every HID device on the machine) — this caught a real bug immediately: typing an empty
  line with no line ending crashed the whole app with a raw Win32 `IOException`, because unlike
  serial/TCP, a zero-length write is invalid at the Windows HID API level (a report is a fixed,
  non-zero, device-defined length), not a harmless no-op. Fixed in two places: `HidTransport.WriteAsync`
  now no-ops on empty data (matching what serial/TCP already do for the same input), and
  `CliMode`/`TuiMode`'s send-path exception handling — previously only caught `TimeoutException` —
  now also catches any device I/O failure and reports it instead of crashing, since a wrong
  *non-zero* length is a real, expected device-specific framing constraint (not something a generic
  text presenter's typed input can guarantee) and still needs to fail, just cleanly. Both fixes
  re-verified against the same real device afterward.

  At the time, not yet verified: the read path against an actual report-producing device — see
  below, this got resolved live later the same day.

- **Built Device Manifests** (`DevTerm.DeviceManifests`), tying the UI Definitions model together
  with the declarative command/response schema already sketched in `device-control-modules.md`
  into one no-code device configuration, per explicit request. New design doc:
  `docs/design/device-manifests.md`, cross-linked from `device-control-modules.md`,
  `ui-definitions.md`, and `plugin-model.md` (a device manifest is a separate, no-code path
  alongside real code plugins, not a competing mechanism).

  Three loading shapes, one code path: a single JSON file; a folder with `device.json` at its root
  plus sibling files it references by relative path (needed once a device's inbound protocol is
  binary — a Kaitai `.ksy` file isn't JSON, so it can't be inlined); or a `.zip` of one, extracted
  to a local folder and then loaded exactly like a folder, no separate zip-handling logic anywhere
  else. `DeviceManifest` covers identity, a loose transport hint, inbound response patterns (or a
  referenced `.ksy` path), outbound command templates, and a `UiDefinition` (inline or by
  reference, resolved relative to the manifest).

  Testing this immediately found a real bug: `XmlSerializer` cannot serialize
  `Dictionary<string,string>` at all — it throws `NotSupportedException` ("implements IDictionary")
  at type-reflection time, not compile time, so the failure only shows up the first time the
  serializer is actually used. Fixed by switching `TransportHint.Options` from a dictionary to a
  plain `List<TransportOption>` (a small Key/Value class), which both `System.Text.Json` and
  `XmlSerializer` handle natively with no special-casing — recorded in `CLAUDE.md` as a constraint
  for any future type meant to round-trip through both serializers. 7 tests, built against a real
  example (a Korad KA3005P manifest, matching the SCPI proposal's actual target hardware) covering
  JSON/XML round-trip, folder-mode with an external UI file, zip-mode, and missing-referenced-file
  failures. 147 tests across the solution now.

## Terminal.Gui (TUI) test automation

Followed up on the "not done" item above: investigated Terminal.Gui v2.5.0's headless-testing
support properly (reflecting over the installed package, then verifying with a real, throwaway
console app before committing to an approach — not just trusting the signatures) and it's
substantially better than the internal-type names suggested. There's a whole public
`Terminal.Gui.Testing` namespace (`IInputInjector`, `InputInjector`) plus a public
`IOutputBuffer`/`Cell[,]` screen-buffer contract — an officially-supported headless testing API,
not a scavenged internal one.

Split `TuiMode.RunAsync` the same way WPF's `MainWindow` was split for testability: pulled window
construction and event wiring out into a new internal `TuiMode.BuildWindow`, returning a
`TuiWindowParts` record (`Window`/`Output`/`SendField`) — `RunAsync` itself now just calls
`BuildWindow` then the same `Application.Run`/`Shutdown` it always did.
`[assembly: InternalsVisibleTo("DevTerm.Console.Tests")]` added to `DevTerm.Console`, mirroring the
WPF project's own `AssemblyInfo.cs`.

New `DevTerm.Console.Tests.TuiTestRunner` (internal test infrastructure) and
`TuiModeTests` (4 tests, `UNIT`) drive a real `TuiMode` window — real `Window`/`TextView`/
`TextField`, a real `Session` over a `FakeTransport` (same shape as `DevTerm.Wpf.Tests.FakeTransport`,
copied rather than shared since each front end's test project already has its own).

Building this surfaced a real, non-obvious constraint that took several rounds of an actual
throwaway console app (not just reading signatures) to pin down: **key injection and cross-thread
`Application.Invoke` don't work at the same time.**

- With no `Application.Run()` loop active (`Init` → `Begin` → manual `LayoutAndDraw`, all on one
  thread), `IInputInjector.InjectKey`/`ProcessQueue()` works immediately and reliably — confirmed by
  injecting `h`, `i`, `!` into a focused `TextField` and reading it back as `"hi!"` right after.
- But `Application.Invoke`, called from any other thread, does *nothing* in that same mode — not
  synchronously, and not later either: neither `LayoutAndDraw(true)` nor `RaiseIteration()` ever
  flushes it, confirmed by a spike that scheduled an `Invoke` from a background thread and checked
  the target `TextView.Text` after each. This matters because `TuiMode`'s own `AppendOutput` uses
  `Application.Invoke` to marshal `Session.Output` events — raised on `Session`'s own background
  read-loop `Task`, never the UI thread — onto the UI.
- Getting `Application.Invoke` to actually run needs a *real*, actively-pumping `Application.Run()`
  loop somewhere — confirmed by running one on a dedicated background thread (mirroring
  `DevTerm.Wpf.Tests.StaTestRunner`'s dedicated STA thread) and marshaling a `TextView.Text` update
  in from the test thread: it landed correctly.
- The natural next step — keep that same loop running and *also* inject keys into it from the test
  thread — does not work. Tried three variants (direct injection from the test thread; injection
  marshaled onto the loop thread via `Invoke`; the same plus an explicit `ProcessQueue()` call and
  `InputInjectionOptions.AutoProcess = true`) and none landed the typed characters in the focused
  `TextField`, even though the exact same injection call sequence worked perfectly with no loop
  running at all.

Rather than dig further into Terminal.Gui's internals to explain *why* (undocumented, closed-source
behavior at this depth isn't worth reverse-engineering further for a test harness), `TuiTestRunner`
just exposes both proven-working modes and uses whichever one a given test actually needs:
`RunHeadless` (single-threaded, for anything that types into the send field, plus a
`DumpBuffer()` text-mode screenshot of the rendered screen) and `RunWithLoop` (dedicated background
thread + `Application.Invoke` marshaling, for the incoming-data-updates-the-UI test specifically).
Confirmed stable across three repeated full test runs, same check already applied to the WPF suite.

Skipped without `--settings devterm.runsettings`).

shortcut argument (`Key` in Terminal.Gui, `InputGestureText` in WPF) only labels the shortcut for
display in the menu — neither framework registers a live accelerator from it by itself.** The real
fix in each case:

- **Terminal.Gui**: a `window.KeyDown` handler for Ctrl+Q worked when nothing had focus, but not
  once the send field (which normally does) had it — a per-view `KeyDown` handler doesn't reliably
  see a key already routed to a focused child first. The global, static `Application.KeyDown` event
  fires ahead of per-view focus routing and is what actually works regardless of focus.
- **WPF**: `MainWindow` got an explicit `PreviewKeyDown` check for Ctrl+Q, since `MenuItem.InputGestureText`
  is display-only there too.

Testing the Terminal.Gui fix needed yet another variant on top of the two `TuiTestRunner` already
has: `IInputInjector`/`ProcessQueue()` (reliable elsewhere in headless mode, including for typed
text) proved unreliable specifically for `Application.KeyDown` once several other tests' Init/Shutdown
cycles had already run earlier in the same process — passed alone, failed once run after the others
in the same class. `Application.RaiseKeyDownEvent(key)`, a direct documented dispatch call, didn't
show the same degradation.

Simulating a **button click** for `ConfigureModeTests` turned out to need its own investigation, a
third Terminal.Gui test-automation technique found today: `View.SetFocus()` makes `HasFocus` report
`true` without fully registering the view for command routing (a button focused this way then sent
an injected Enter/Space did nothing), and Tab-navigating focus onto a button worked alone but not
once several tests ran in the same process — the same "degrades over repeated Init/Shutdown cycles"
pattern as above, hit a third time. `View.InvokeCommand(Command.Accept)` — a direct, documented way
to invoke a view's command, bypassing key-event routing entirely — is what finally worked reliably
across repeated runs.

## Connect/Disconnect menu item, and a real Session bug it surfaced

Added a third menu item, distinct from Device Profiles: "File > Connect"/"Disconnect" (a single
item whose label flips, not two separate ones) in both front ends —
`TuiMode.ToggleConnectionAsync`/`MainWindow.ToggleConnectionAsync` — closing or reopening the exact
same `Session`/transport with no profile change involved. Terminal.Gui's `MenuItem.Title` turned
out to be mutable at runtime (unlike its `Key` shortcut argument from earlier today), so the label
just flips in place rather than needing two items shown/hidden.

Building this surfaced a real, previously-latent bug in `Session` itself: `_readLoopCts` was a
`readonly CancellationTokenSource` created once in the constructor and only ever cancelled, never
recreated. A `CancellationTokenSource` can only be cancelled once, so calling `OpenAsync` again
after a `CloseAsync` started the new read loop with an already-cancelled token — it exited
immediately, silently, with no exception and no indication anything was wrong; incoming bytes after
a reconnect would simply never arrive. This had never been hit before because nothing in the
codebase closed and reopened the same `Session` instance until this menu item did. Fixed by moving
`_readLoopCts` to a field created fresh in `OpenAsync` and disposed in `StopAsync`. Verified as a
genuine regression, not just a plausible-sounding fix: temporarily reverted the fix and confirmed
the new `SessionTests.OpenAsync_AfterClose_RestartsTheReadLoopForRealIncomingData` test actually
fails (times out) without it, then restored the fix and confirmed it passes.

Both front ends also guard against sending while disconnected — a message in the output pane/list
rather than an exception from the transport. New tests: 3 in `DevTerm.Console.Tests.TuiModeTests`
(disconnect-then-reconnect toggling the menu label and send-field enabled state; sending while
disconnected doesn't write to the transport) and 2 in `DevTerm.Wpf.Tests.MainWindowTests` (the same
two scenarios), plus the `SessionTests` regression test — all stable across repeated runs.

187 tests across the solution now (183 pass by default).
