- **Scoped USB HID, BLE, GPIB, and USBTMC transports** in `docs/design/transports.md` against
  real target hardware and a direct architecture decision:
  - USB HID: [HidSharp](https://www.nuget.org/packages/HidSharp) (cross-platform, no vendor driver
    needed).
  - BLE: explicitly chosen to be **cross-platform**, via a small internal per-OS adapter seam
    (Windows/`Windows.Devices.Bluetooth` first; Linux/BlueZ and macOS/CoreBluetooth addable later,
    including as community/self-contributed adapters) rather than shipping Windows-only the way
    the WPF front end does. Named the common "BLE Serial" pattern explicitly (Nordic UART Service
    UUIDs as the default, but configurable — not every "acts like serial over BLE" device actually
    uses NUS). Target hardware: an LCR meter reachable over BLE, pending identification of its
    make/model and GATT profile.
  - GPIB: researched what cheap eBay "IEEE-488 to USB" adapters actually speak — most (including
    DIY [AR488](https://github.com/Twilight-Logic/AR488)-firmware boards) implement the Prologix
    `++` ASCII protocol over a plain serial or TCP connection, needing only a thin controller layer
    on the existing transports, not a new one. A separate, **not recommended**, family instead
    clones National Instruments' proprietary GPIB-USB-HS protocol (non-serial, driver-dependent,
    reportedly unreliable even against genuine NI hardware) — flagged so a purchase decision can
    check which protocol a specific listing actually speaks first.
  - USBTMC: identified as the actual USB class most bench SCPI equipment uses locally over USB
    (confirmed via vendor docs for the Rigol DG1022 family — the DG1022Z/DG1062Z also support LAN
    with VXI-11 and raw-socket SCPI, already covered by the existing TCP transport, but the plain
    DG1022 has no LAN option). Neither HID nor serial — its own USB class with bulk endpoints and
    message framing — so it needs its own raw-USB transport (WinUSB/LibUsbDotNet), not yet designed
    in detail.
  - Also noted: the project's own Tek 2230 test device is itself an example of the "SCPI-precursor,
    needs a custom decoder" oscilloscope category (Tektronix's own pre-SCPI "codes" command
    language, comma/semicolon-delimited) mentioned for a wider scope fleet — a candidate for its
    own proposal doc once specific models are identified.
  - Refined the GPIB write-up further after more research: distinguished genuine Prologix
    hardware, AR488 (open-source Arduino firmware — full Prologix `++` set minus `++lon`, plus its
    own macro/Bluetooth/EEPROM-wear extensions; lowest-risk since it's readable source, whether
    self-built or bought pre-flashed), and NI GPIB-USB-HS clones (still not recommended).

- **Built the USB HID transport** (`DevTerm.Transports.Hid`, HidSharp 2.6.4) end-to-end: options,
  `IHidDevice`/`SystemHidDevice`/`IHidDeviceFactory`/`IHidDeviceDiscovery` mirroring the serial
  transport's shape exactly, and CLI wiring (`--transport hid --hidvendorid <n> --hidproductid <n>
  [--hidserialnumber <sn>]`, `--listhiddevices true`, validator, `ConnectionDescription`,
  `ConnectionErrorMessages` hint, `AddDevTermFrontEnd`). 136 tests across the solution now (10 new
  for the HID transport, 9 new in `DevTerm.Configuration.Tests`).

  The interesting design problem: HidSharp gives no event analogous to `SerialPort.DataReceived`
  to wait on for "a report is ready," and its `Read`/`Write` are plain `BeginRead`/`EndRead`-backed
  under a default `Stream.ReadAsync`, which — like `SerialPort.BaseStream.ReadAsync` — doesn't
  meaningfully honor a `CancellationToken` once a read is in flight. Solved with a dedicated
  background thread (owned and joined on close, not a `Task.Run`-wrapped blocking call per read,
  which was already rejected for serial for the same "orphaned, unobserved background work" reason)
  that blocks on `HidStream.Read` bounded by `ReadTimeout` and hands completed reports to a
  `Channel<byte[]>`; the actual `ReadAsync` only ever awaits the channel, so cancellation is
  immediate and correct regardless of the background thread's own bounded shutdown.

  Verified against real hardware (a mouse's RGB-control HID interface, and `--listhiddevices`
  against every HID device on the machine) — this caught a real bug immediately: typing an empty
  line with no line ending crashed the whole app with a raw Win32 `IOException`, because unlike
  serial/TCP, a zero-length write is invalid at the Windows HID API level (a report is a fixed,
  non-zero, device-defined length), not a harmless no-op. Fixed in two places: `HidTransport.WriteAsync`
  now no-ops on empty data (matching what serial/TCP already do for the same input), and
  `CliMode`/`TuiMode`'s send-path exception handling — previously only caught `TimeoutException` —
  now also catches any device I/O failure and reports it instead of crashing, since a wrong
  *non-zero* length is a real, expected device-specific framing constraint (not something a generic
  text presenter's typed input can guarantee) and still needs to fail, just cleanly. Both fixes
  re-verified against the same real device afterward.
