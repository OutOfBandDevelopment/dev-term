- **Found and fixed two real bugs against actual hardware** (a Tektronix 2230 oscilloscope on a
  serial port, reached via pyserial to confirm the device itself worked before assuming our code
  was correct — pyserial got `ID TEK/2230,V81.1,VERS:14;` back in under a second):
  - **Close/Ctrl+C could hang forever on a real serial port.** `SerialPort.BaseStream.ReadAsync
    (Memory<byte>, CancellationToken)` does not reliably honor the cancellation token on an
    in-flight read on this hardware/driver, so `StreamToPipePump`'s cancellation never landed and
    `CloseAsync` blocked indefinitely waiting for the pump to notice. Root-caused via targeted
    diagnostic logging at each layer (Program → Session → SerialTransport → pump), since a
    synthetic repro of "background ReadAsync + concurrent Write" didn't reproduce it — the actual
    problem was cancellation of the read itself, not read/write contention. Fixed with a new
    `CancellableReadStream` (`DevTerm.Transports.Serial`) that wraps `SerialPort.BaseStream` and
    implements `ReadAsync` via the classic synchronous `Read` (which *does* reliably honor
    `SerialPort.ReadTimeout`) polled against the caller's cancellation token between attempts —
    scoped to the one component that needs the workaround, so `StreamToPipePump` and TCP stay on
    the plain, cancellation-respecting `ReadAsync` path. Added `SerialTransportOptions.ReadTimeoutMs`
    (default 1000ms) and `WriteTimeoutMs` (default 5000ms, so a stalled write under hardware flow
    control also fails instead of hanging) plus matching `CliOptions`/`--readtimeoutms`/`--writetimeoutms`.
  - **The device never responded at all**, independent of the hang: `System.IO.Ports.SerialPort`
    does not assert DTR by default (`DtrEnable = false`), unlike pyserial (which asserts it on
    open) — and this instrument, like many bench devices, stays silent without DTR asserted.
    Added `SerialTransportOptions.DtrEnable`/`RtsEnable` (both default `true`) and matching
    `CliOptions.Dtr`/`Rts` (`--dtr`/`--rts`), with `RtsEnable` left alone when `Handshake` already
    manages RTS (setting it explicitly in that mode throws).
  - Verified the fix on the real device end-to-end through the actual CLI (not just a unit test):
    `ID?\r` sent, `ID TEK/2230,V81.1,VERS:14;` decoded byte-by-byte via the `ascii` presenter,
    clean exit (code 0) in ~6.5s matching the test harness's own held-open stdin window, with
    hardware (RTS/CTS) flow control enabled per the saved profile.

- **Replaced the `Task.Run`-wrapped-synchronous-`Read` serial fix with an event-driven one**, after
  it turned out to have its own hazard: that background work item is itself uncancelable, so if
  anything ever stops awaiting it early (a race with `Close`/`Dispose`, a future timeout wrapper),
  it keeps running and can fault later with nobody observing it — an `UnobservedTaskException`
  waiting to happen. Replaced `CancellableReadStream` with `SerialPortReadStream`
  (`DevTerm.Transports.Serial`), which waits on `SerialPort.DataReceived` via a
  `TaskCompletionSource` (properly interrupted by the caller's `CancellationToken`) and only calls
  the real (fast, non-blocking) `Read` once data is already known to be buffered — no polling, no
  background work item to orphan.
- **`AsciiPresenter` now buffers text until a line terminator (CR, LF, or CRLF as one terminator)
  or a max line length, instead of rendering whatever arrived in a single read** — serial reads
  routinely deliver one byte at a time, which was producing one `[ascii] X` output per character.
  This required a real interface change: `IPresenter.Render` now returns `IReadOnlyList<string>`
  (zero, one, or many complete renderings per call) instead of a single `string`, since a
  buffering presenter can't always produce exactly one output per chunk. `Pipeline.Render` flattens
  this into zero or more `PresenterOutput`s per presenter per chunk. The other presenters
  (hex/decimal/octal/binary/utf8) are unaffected in behavior, just wrap their existing single
  result in a one-element list. Split `IPresenterInput` into its own file alongside `IPresenter`.
  Noted as a known constraint: `AsciiPresenter` is stateful (holds a partial line across calls)
  and presenters are currently registered as DI singletons — fine for the CLI's one-session-at-a-time
  model, but would need per-session instances if concurrent sessions ever share a process.
  - Verified against the real device: `ID?\r` now produces exactly one line,
    `[ascii] ID TEK/2230,V81.1,VERS:14;`, with a fast, clean exit (matching the harness's own
    held-open stdin window, exit code 0).

- Designed (no code yet, by request) support for RFC 2217 (Telnet Com Port Control Option) in
  both client and server roles — new `docs/design/rfc2217.md`:
  - Client (`Rfc2217Transport`) fits the existing `ITransport` contract cleanly; server
    (`Rfc2217ServerBridge`) is structurally different — it bridges an already-open local
    connection out to the network rather than being a session's own transport, so it's designed
    as a composed bridge, not a transport, and is planned to be built second.
  - A shared, pure `Rfc2217Codec` (Telnet IAC escaping + `COM-PORT-OPTION` subnegotiation
    encode/decode) is used by both roles in opposite directions.
  - Testing plan: verify the client against pyserial's `rfc2217_server.py` reference server, and
    the server against pyserial's `serial.rfc2217.Serial` client — the same "verify against an
    independent real implementation" approach that caught the DTR-default and read-cancellation
    bugs in `SerialTransport` this session.
  - **Checked a real target device's actual protocol before assuming compatibility**: the
    USR-TCP232-302 (a concrete device this is meant to support) documents its own protocol as
    "Customized RFC2217... PUSR customized protocol," a vendor-specific variant, not the IETF
    standard — a standards-compliant `Rfc2217Transport` is not guaranteed to interoperate with it.
    Noted the pragmatic near-term path (its plain TCP Server/Client passthrough mode already
    works with the existing `DevTerm.Transports.Tcp`, configuring serial parameters once via the
    device's own AT-command/web UI) versus what a dedicated vendor-specific transport would take.
  - Flagged a real security exposure in the design up front: RFC 2217 has no auth/encryption, so
    server mode means anyone reaching the listening port controls the attached serial device —
    default loopback-only binding, explicit opt-in to expose externally.
