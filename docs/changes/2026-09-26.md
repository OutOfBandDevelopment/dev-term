# 2026-09-26

## Code review of main: 59 bug reports filed under docs/bugs/

The review was a static, read-only pass over `main` @ `42758db`, on branch `dev/review-code`. Five reviewers
worked in parallel, one per area:
- Core, Logging and the text presenters;
- the transports, including the new BLE projects;
- the devices, manifests and UI model, including the new Radex One, DE-5000 and Zoom H4n code;
- Configuration;
- the TUI and WPF front ends.

Each finding cites the code and gives a concrete failure scenario. The DE-5000 sign handling was also checked
against the 4x1md/de5000_lcr_py reference. Nothing was run or reproduced.

The results are in `docs/bugs/`, one file per bug, indexed in `docs/bugs/README.md`: 7 High, 25 Medium and
27 Low. Six were found independently by two reviewers (001, 006, 007, 008, 009, 020). The High ones:
- **001:** a second `Session.OpenAsync` starts a second read loop.
- **002:** USBTMC Close hangs during a reply over 64 KB.
- **003:** Loopback can't reconnect after a Disconnect.
- **004:** a bad profile value crashes the window-title lookup.
- **005:** DE-5000 negative secondary values aren't sign-extended.
- **006:** the reply queue gets out of step after a missing reply.
- **007:** closed TUI windows are never disposed.

Recurring test gaps:
- No transport has an open, close, open-again test.
- `StreamToPipePump` has no tests.
- Nothing tests a missing reply or a UTF-8 character split across reads.

`docs/bugs/` is a new kind of doc and is now listed in CLAUDE.md's Documentation section.

## Bug reports record their commit; a bug-report skill for future ones

- Every `docs/bugs/` report's header now has **Created** (the date) and **Found at commit** (the full hash, here
  `42758db2e9fecc95584fe15465fd7f41e637e2e4` on `main`) in place of a one-line "Found" note. It also has a
  **Found by** row. The line numbers in a report refer to that commit (`git show <hash>:<path>`).
- New `.claude/skills/bug-report/SKILL.md` gives the protocol for future reports:
  - check for an existing report first;
  - verify against the code and record `git rev-parse HEAD`;
  - next-number and file-name rules, and the exact template;
  - severity and confidence definitions;
  - adding the index row;
  - committing reports separately from fixes;
  - the Fixed/Resolution lifecycle.
- `docs/bugs/README.md` and CLAUDE.md now point to the skill.

## Fixing docs/bugs/ reports, starting with 001

Started working through the 59 filed reports on branch `dev/fix-bugs`, one at a time: reproduce with a failing
regression test first, then fix, per the bug-report skill's "Fixing a reported bug" section.

- New `TestCategories.BugRegression`, added at the method level alongside a test's own `Unit`/`Integration`
  category, so `dotnet test --filter TestCategory=BugRegression` runs every regression test written from a
  `docs/bugs/` report across the solution. `docs/coding-standards.md` documents this as the one method-level
  exception to the class-level `[TestCategory]` rule; `TestCategoryStandardsTests` now recognizes it.
- **[001](../bugs/fixed/001-session-double-open.md) fixed:** `Session.OpenAsync` (`src/DevTerm.Core/Sessions/Session.cs`)
  now returns early, inside `_lifecycleLock`, when a read loop is already running — a second call while already
  open (or still opening) is a no-op instead of starting a second `PumpAsync` on the same `PipeReader`, which used
  to throw "reading is already in progress" and fault a healthy connection. Confirmed with a new regression test
  (`SessionTests.OpenAsync_CalledAgainWhileAlreadyOpen_DoesNotStartASecondReadLoop`) that fails without the guard
  (the connection faults instead of the second write being received) and passes with it.
- **[002](../bugs/fixed/002-usbtmc-close-hang-large-reply.md) fixed:** `UsbtmcTransport.CloseAsync`
  (`src/DevTerm.Transports.Usbtmc/UsbtmcTransport.cs`) now calls `_pipe?.Writer.CancelPendingFlush()` before
  waiting on `_ioLock`, unblocking a `WriteAsync` stuck flushing a reply over the pipe's default 64 KB pause
  threshold into a pipe nobody is reading any more (`Session` stops its read loop before calling `CloseAsync`).
  `CancelPendingFlush` cancels only that one pending flush, so the write still completes rather than throwing.
  Confirmed with a new regression test
  (`UsbtmcTransportTests.CloseAsync_DuringAWriteFlushingAReplyOverThePauseThreshold_CompletesWithoutHanging`) that
  times out without the fix (via `git stash` on just the source change) and passes with it.
- **[003](../bugs/fixed/003-loopback-cannot-reconnect.md) fixed:** `LoopbackTransport`
  (`src/DevTerm.Transports.Loopback/LoopbackTransport.cs`) now creates a fresh `Pipe` in `OpenAsync` instead
  of reusing one `Pipe` for its whole lifetime — `CloseAsync` completes that pipe's writer permanently, so a
  reopen over the same pipe threw "Writing is not allowed after writer was completed" on the next send.
  Confirmed with a new regression test
  (`LoopbackTransportTests.OpenAsync_AfterClose_CanReconnectAndExchangeData`) that fails without the fix and
  passes with it.
- **[004](../bugs/fixed/004-bad-profile-value-crashes-title.md) fixed:** `ConnectionProfileStore.FindName`
  (`src/DevTerm.Configuration/ConnectionProfileStore.cs`) now also catches `InvalidOperationException`,
  which is what `ConfigurationBinder.Bind` throws for a profile value that fails to convert (e.g.
  `"Baud": "fast"`) — previously uncaught, so it crashed the TUI title lookup at startup and blocked the
  WPF connect. The report's other scenario (a duplicate JSON key) doesn't reproduce: it throws
  `InvalidDataException` on this .NET version, already in the filter. Confirmed with a new regression test
  (`ConnectionProfileStoreTests.FindName_SkipsAProfileWithAValueThatFailsToConvert_AndKeepsLooking`) that
  fails without the fix and passes with it.
- **[005](../bugs/fixed/005-de5000-negative-secondary.md) fixed:** `De5000Framer.TryParse`
  (`src/DevTerm.Devices.De5000/De5000Framer.cs`) now sign-extends the secondary 16-bit value via a `(short)`
  cast when `secondaryUnit is "%" or "deg"` — those are the only two secondary units the reference
  implementation treats as signed, so a negative phase angle or D reading no longer decodes as a huge
  positive (θ = -45.0deg, raw `0xFE3E`, used to decode as `6508.6deg`). Confirmed with two new regression
  tests (`De5000FramerTests.TryParse_NegativeSecondaryDegrees_DecodesAsANegativeValue` and
  `TryParse_NegativeSecondaryPercent_DecodesAsANegativeValue`) that fail without the fix (reproducing the
  report's own `6508.6` example exactly) and pass with it.
- **[006](../bugs/fixed/006-reply-queue-desync.md) fixed:** `IReplyTracker` gained `Cancel(string replyIndicatorId)`
  (`src/DevTerm.Core/Presenters/IReplyTracker.cs`); `LineReplyPresenter` (the shared base of
  `ScpiReplyPresenter`/`ManifestReplyPresenter`) implements it by dropping exactly one matching pending id from its
  `ConcurrentQueue<string>`. `ScpiAutoDetect.DetectAsync` now cancels its own pending id on both a failed `*IDN?`
  send and a `NoReply` timeout; `ScpiControlSurface.InvokeAsync` and `ManifestControlSurface.InvokeAsync` cancel
  the tracker's pending id when their send throws, then rethrow — previously a failed send or timeout left the id
  queued forever, so the *next* query's reply landed on it instead of its own. A new `IResettablePresenter`
  interface (`src/DevTerm.Core/Presenters/IResettablePresenter.cs`) lets `Session.OpenAsync`
  (`src/DevTerm.Core/Sessions/Session.cs`) clear each presenter's pending-reply queue and partial line on every
  reopen, so state from a previous connection can't carry into a new one; `LineReplyPresenter`'s internal buffer
  also now caps at 4096 bytes instead of growing unbounded against a terminatorless/binary stream. Confirmed with
  new regression tests in `ScpiReplyPresenterTests`, `ScpiAutoDetectTests`, `ScpiControlSurfaceTests`,
  `ManifestControlSurfaceTests`, and `SessionTests` (all cited in the report's Resolution section) that fail
  without the fix and pass with it.
- **[007](../bugs/fixed/007-tui-modal-windows-not-disposed.md) fixed:** every TUI window opened via
  `app.Run(x.Window)` with no matching `Dispose()` — the six Device menu control panels and the SCPI instrument
  window, and the "_Device Profiles..." menu item in `src/DevTerm.Console/TuiMode.cs`; `ManifestPanelMode.Run`
  (`src/DevTerm.Console/ManifestPanelMode.cs`); `ConfigureMode.Run` (`src/DevTerm.Console/ConfigureMode.cs`) — now
  wraps its `app.Run` in `try { ... } finally { x.Dispose(); }`, the same plain inline pattern
  `ManifestEditorMode.cs`/`TuiMode.OpenStreamMonitor` already used (not a shared `RunModal` helper). Two dialog-only
  pickers not explicitly named in the report (`TuiMode.PickFromList`, `ManifestPanelMode.Pick`) got the same fix for
  consistency. Previously, `window.Disposing`-registered cleanup — unsubscribing the global
  `app.Keyboard.KeyDown` scroll handler, a K8055/Busylight/etc. panel's `structuredPresenter.ValuesChanged`
  subscription, the Connection Editor's `FileSystemWatcher` — never ran, so PageUp/PageDown stopped reaching the
  main window after any panel closed, and each panel open leaked another live subscription. Confirmed with a new
  regression test (`TuiModeTests.K8055MenuItem_AfterThePanelCloses_UnsubscribesFromValuesChanged`) that drives the
  real "_K8055 Control Panel..." menu item's own `Action` and fails (one leaked subscriber) without the fix, passes
  with it.
- **[008](../bugs/fixed/008-pump-swallows-read-errors.md) fixed:** `StreamToPipePump.RunAsync`
  (`src/DevTerm.Core/Transports/StreamToPipePump.cs`) now completes the pipe writer with whatever exception
  `source.ReadAsync` threw, unless the read was cancelled deliberately (a real close), which still completes clean.
  It previously caught `IOException`/`ObjectDisposedException`/`OperationCanceledException` unconditionally and
  always completed with no error, so `Session.PumpAsync` reported a real read failure (TCP reset, USB-serial
  unplug) the same as a peer's clean hang-up, with no error captured anywhere. Confirmed with two new regression
  tests in a new `StreamToPipePumpTests` (`RunAsync_WhenTheStreamThrowsDuringARead_CompletesTheWriterWithThatExceptionInsteadOfACleanHangUp`,
  `RunAsync_WhenCancelledDuringARead_CompletesTheWriterWithNoErrorAsACleanClose`) that fail/pass respectively.
- **[009](../bugs/fixed/009-pump-flush-cancel-close-leak.md) fixed:** `StreamToPipePump.RunAsync` now also catches a
  cancellation from `writer.FlushAsync` (a paused pipe unblocked by a deliberate close) as a normal `break`, instead
  of letting `OperationCanceledException` turn the pump's own `Task` `Canceled`. `SerialTransport`/`TcpTransport`/
  `HidTransport`'s `CloseAsync` now await `_pumpTask` inside `try/catch (OperationCanceledException)` with teardown
  moved into `finally`, and `Session.StopAsync` swallows an `OperationCanceledException` from `_transport.CloseAsync`
  unless it's the caller's own token — previously a cancelled-while-backpressured pump could leave `CloseAsync`
  throwing part-way, the port/socket/HID handle never released, and a later `OpenAsync` on the same port failing.
  Confirmed with a new regression test
  (`StreamToPipePumpTests.RunAsync_WhenTheTokenIsCancelledBeforeTheFlushThatFollowsARead_CompletesWithoutThrowing`)
  that fails without the fix (`TaskCanceledException` escapes `RunAsync`) and passes with it.
- **[010](../bugs/fixed/010-manifest-path-traversal.md) fixed:** new `ManifestRelativePath`
  (`src/DevTerm.DeviceManifests/ManifestRelativePath.cs`) rejects a rooted `UiFile`/`KaitaiFile` path or one
  containing a `..` segment, and confirms the resolved path still falls inside the manifest's own folder.
  `DeviceManifestLoader.LoadFromFile` and `DeviceManifestWriter.Save` (`src/DevTerm.DeviceManifests/`) now combine
  both fields through it instead of a bare `Path.Combine` — previously a rooted path or `..\..\` let Save write a
  UI file anywhere on disk and copy an arbitrary Kaitai source to an arbitrary destination, and let Load read (and
  parse as a UI definition) or existence-probe any file on disk. The guard has to live in the loader/writer
  themselves, not only in `DeviceManifestValidator`, since `Load(path, validate: false, ...)` (the manifest
  editor's "open a broken manifest" path) still reads `UiFile`/`KaitaiFile` before any validation runs.
  `DeviceManifestValidator.Validate` also gained the same check as an error, so the editor's own save-time
  validation catches it too. Confirmed with six new regression tests in `DeviceManifestTests` (three `Load_*`, two
  `Save_*`, one `Validate_*`) that fail without the fix and pass with it.
- **[011](../bugs/fixed/011-manifest-zip-unbounded-temp-leak.md) fixed:** `DeviceManifestLoader.ResolveManifestFile`'s
  zip branch (`src/DevTerm.DeviceManifests/DeviceManifestLoader.cs`) now walks the zip's entries via
  `ZipFile.OpenRead` before extracting anything, throwing `InvalidDataException` if it has more than 500 entries
  or more than 100 MiB of total uncompressed content. The extraction folder is also no longer a fresh
  `Path.GetRandomFileName()` on every open — it's now a deterministic `%TEMP%\devterm-manifests\<hash>` keyed on
  the zip's full path, length and last-write time (deleted and re-extracted fresh each load, but reused across
  repeated opens of the same zip), instead of leaking a new folder every time. A folder-per-zip-content, rather
  than delete-right-after-load, was chosen because `ManifestEditorViewModel.Open` keeps the extracted directory
  as `SourceDirectory` for a later `DeviceManifestWriter.Save`. Confirmed with two new regression tests in
  `DeviceManifestTests` (`Load_ZipWithTooManyEntries_ThrowsAndDoesNotExtract`,
  `Load_SameZipTwice_ReusesOneExtractionFolderInsteadOfLeakingANewOneEachTime`) that fail without the fix and pass
  with it.
