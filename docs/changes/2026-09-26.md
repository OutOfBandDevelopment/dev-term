# 2026-09-26

## Code review of main: 59 bug reports filed under docs/bugs/

The review was a static, read-only pass over `main` @ `42758db`, on branch `dev/review-code`. Five reviewers
worked in parallel, one per area:
- Core, Logging and the text presenters;
- the transports, including the new BLE projects;
- the devices, manifests and UI model, including the new Radex One, DE-5000 and Zoom H4n code;
- Configuration;
- the TUI and WPF front ends.

Each finding cites the code and gives a concrete failure scenario. The DE-5000 sign handling was also checked
against the 4x1md/de5000_lcr_py reference. Nothing was run or reproduced.

The results are in `docs/bugs/`, one file per bug, indexed in `docs/bugs/README.md`: 7 High, 25 Medium and
27 Low. Six were found independently by two reviewers (001, 006, 007, 008, 009, 020). The High ones:
- **001:** a second `Session.OpenAsync` starts a second read loop.
- **002:** USBTMC Close hangs during a reply over 64 KB.
- **003:** Loopback can't reconnect after a Disconnect.
- **004:** a bad profile value crashes the window-title lookup.
- **005:** DE-5000 negative secondary values aren't sign-extended.
- **006:** the reply queue gets out of step after a missing reply.
- **007:** closed TUI windows are never disposed.

Recurring test gaps:
- No transport has an open, close, open-again test.
- `StreamToPipePump` has no tests.
- Nothing tests a missing reply or a UTF-8 character split across reads.

`docs/bugs/` is a new kind of doc and is now listed in CLAUDE.md's Documentation section.

## Bug reports record their commit; a bug-report skill for future ones

- Every `docs/bugs/` report's header now has **Created** (the date) and **Found at commit** (the full hash, here
  `42758db2e9fecc95584fe15465fd7f41e637e2e4` on `main`) in place of a one-line "Found" note. It also has a
  **Found by** row. The line numbers in a report refer to that commit (`git show <hash>:<path>`).
- New `.claude/skills/bug-report/SKILL.md` gives the protocol for future reports:
  - check for an existing report first;
  - verify against the code and record `git rev-parse HEAD`;
  - next-number and file-name rules, and the exact template;
  - severity and confidence definitions;
  - adding the index row;
  - committing reports separately from fixes;
  - the Fixed/Resolution lifecycle.
- `docs/bugs/README.md` and CLAUDE.md now point to the skill.

## Fixing docs/bugs/ reports, starting with 001

regression test first, then fix, per the bug-report skill's "Fixing a reported bug" section.

- New `TestCategories.BugRegression`, added at the method level alongside a test's own `Unit`/`Integration`
  category, so `dotnet test --filter TestCategory=BugRegression` runs every regression test written from a
  `docs/bugs/` report across the solution. `docs/coding-standards.md` documents this as the one method-level
  exception to the class-level `[TestCategory]` rule; `TestCategoryStandardsTests` now recognizes it.
- **[001](../bugs/fixed/001-session-double-open.md) fixed:** `Session.OpenAsync` (`src/DevTerm.Core/Sessions/Session.cs`)
  now returns early, inside `_lifecycleLock`, when a read loop is already running — a second call while already
  open (or still opening) is a no-op instead of starting a second `PumpAsync` on the same `PipeReader`, which used
  to throw "reading is already in progress" and fault a healthy connection. Confirmed with a new regression test
  (`SessionTests.OpenAsync_CalledAgainWhileAlreadyOpen_DoesNotStartASecondReadLoop`) that fails without the guard
  (the connection faults instead of the second write being received) and passes with it.
- **[002](../bugs/fixed/002-usbtmc-close-hang-large-reply.md) fixed:** `UsbtmcTransport.CloseAsync`
  (`src/DevTerm.Transports.Usbtmc/UsbtmcTransport.cs`) now calls `_pipe?.Writer.CancelPendingFlush()` before
  waiting on `_ioLock`, unblocking a `WriteAsync` stuck flushing a reply over the pipe's default 64 KB pause
  threshold into a pipe nobody is reading any more (`Session` stops its read loop before calling `CloseAsync`).
  `CancelPendingFlush` cancels only that one pending flush, so the write still completes rather than throwing.
  Confirmed with a new regression test
  (`UsbtmcTransportTests.CloseAsync_DuringAWriteFlushingAReplyOverThePauseThreshold_CompletesWithoutHanging`) that
  times out without the fix (via `git stash` on just the source change) and passes with it.

## Fix bug 039: calling SendAsync from the read-loop thread deadlocks if the send fails

`Session.StopAsync` (`src/DevTerm.Core/Sessions/Session.cs`) awaits the read-loop task (`_readLoopTask`) to make
sure it's fully stopped before closing the transport. If a caller invokes `SendAsync` synchronously from within
the read loop's own call stack - e.g. a `Session.Output` handler that reacts to received data by calling
`session.SendAsync(...).GetAwaiter().GetResult()` - and that send fails, `SendAsync`'s catch block awaits
`FaultAsync` inline, which reaches `StopAsync` and awaits that same read-loop task from a call that's still on its
own stack: a genuine self-await deadlock, confirmed by reproducing it in a test (which hung until killed) before
fixing it.

A first fix attempt - deferring `SendAsync`'s own fault dispatch via `Task.Run` so it could never be reentrant -
broke a real, already-tested, CLAUDE.md-documented guarantee: "a send's catch only reports when `session.State` is
still `Open`" (`TuiModeErrorHandlingTests.SendAsync_DeviceFailure_DisconnectsAndLeavesReportingToTheDisconnectedHandler`),
which relies on the fault path synchronously closing the transport before the exception reaches a normal caller's
catch block. Reverted.

The actual fix instead detects the specific reentrant case and fails fast instead of deadlocking, leaving every
other caller's synchronous fault handling untouched. `Session` gained an `AsyncLocal<bool> _onReadLoop` field, set
`true` at the top of `PumpAsync`; `AsyncLocal` makes exactly the right distinction here - it stays `true` for the
entire logical call chain descending from `PumpAsync` (including a synchronous `Output` handler calling
`SendAsync` inline), but reads `false` for an unrelated, concurrent caller (a normal `CloseAsync` from the UI
thread) even while `PumpAsync` is itself still blocked in a read, since ambient flow only follows the chain it was
set on. The one call that must *not* inherit `true` - `PumpAsync`'s own natural end-of-loop dispatch to
`FaultAsync` via `Task.Run` - is wrapped in `ExecutionContext.SuppressFlow()` so that task starts with a fresh
context. `StopAsync` now checks `_onReadLoop.Value` before awaiting the read loop, throwing
`InvalidOperationException` instead when it's `true`. (An earlier attempt compared `Task.CurrentId` against
`_readLoopTask.Id` instead; it never matched and the deadlock reproduced identically, because
`Task.Run(Func<Task>)` returns an unwrapped proxy task with a different `Id` than the actual async state machine
executing `PumpAsync`'s body - confirmed by hitting the same hang again before switching to `AsyncLocal`.)
Regression test:
`SessionTests.SendAsync_CalledSynchronouslyFromTheReadLoopsOutputHandler_FailsFastInsteadOfDeadlockingWhenTheSendFails`
(confirmed to hang against the pre-fix code; passes in ~70ms with the fix). Full `TestCategory=Unit` run otherwise
green, including `TuiModeErrorHandlingTests`; the same pre-existing, unrelated
`TuiToolWindowLayoutTests.Playback_PartWayThroughWithANote` failure noted in bug 037's entry above reproduces
identically with this change stashed out. See [039](../bugs/fixed/039-sendasync-from-read-loop-deadlock.md).

that strips the header and begins a capture with no fixed length. Since the wrapped content's own signature may
not have fully arrived by the time the header alone is parsed (confirmed by a first attempt that called
`StreamContentSniffer.Identify` once, immediately after the header, which worked only when a whole reply arrived
in one read and produced no capture at all when fed one byte at a time), identification is instead retried lazily
in `AppendToCapture` on every chunk while a capture still has no known kind/end-finder; once recognized, its
structural end-finder takes over instead of only ever falling back to the idle timeout. An unrecognizable
indefinite-length payload still ends on the idle timeout, same as today's undeclared/unrecognized-bytes case.
Regression tests: `StreamContentSnifferTests.Find_IndefiniteLengthBlockWrappingAnImage_ReportsTheHeaderWithNoPayloadLength`,
`StreamContentWatcherTests.DeclaredImage_InAnIndefiniteLengthBlock_IsCapturedByItsOwnStructuralEndWithNoHeaderBytes`
(fails with zero captures against the first, premature-identify fix attempt; passes against the final fix), plus
`UndeclaredIndefiniteLengthBlockWrappingAnImage_CapturesExactlyThePayload` and
`DeclaredImage_InAnIndefiniteLengthBlockWithUnrecognizedBytes_EndsOnIdleTimeout` covering the sniffed and
unrecognized-payload paths. Full `TestCategory=Unit` run otherwise green; the same pre-existing, unrelated
`TuiToolWindowLayoutTests.Playback_PartWayThroughWithANote` failure noted above reproduces identically and is
unrelated to this change. See [042](../bugs/fixed/042-stream-watcher-indefinite-block.md).

## Radex One: added a fifth command, Reset Accumulated (`0x0803`)

A user-captured trace not present in the original source reverse-engineering doc revealed a fifth
Radex One command — clearing the device's accumulated-dose counter. Checksum-verified byte-for-byte
against the trace (both request and reply, using the same word-sum-checksum formula documented for
the other four commands):

```
>: 7bff 2000 0600 4e01 0000 0fff 0308 0100 fbf7
<: 7aff 2080 0600 4e01 0000 107f 0308 0000 fcf7
```

Command code `0x0803`; request extension shares the existing 6-byte query shape
(`CommandCode(2) + word(2) + Checksum(2)`) but with the second word `0x0001` instead of the other
three queries' `0x000C`; reply extension is identical in shape to the existing Write Settings ack.

Changes:
- `RadexOneCommand.ResetAccumulated = 0x0803` (`RadexOneFramer.cs`).
- `RadexOneExtensionCodec.BuildQuery` gained a `word` parameter (default `0x000C`, unchanged for the
  three existing callers) so the new command's `0x0001` variant didn't need a separate builder.
- `RadexOneDecoder` gained a "reset accumulated acknowledged" branch.
- `RadexOneControlSurface` gained a `"resetAccumulated"` action/preview, sent via the same
  `SendQueryAsync`/`PreviewQuery` paths (now `word`-parameterized) as the other one-shot queries.
- `RadexOneUiDefinition` gained a "Maintenance" section with a "Reset Accumulated" button.
- 5 new unit tests in `tests/DevTerm.Devices.RadexOne.Tests` (27 total, up from 22), including exact
  byte-for-byte assertions against the new trace in both directions.
- `docs/design/proposals/radex-one-protocol.md` updated: command-codes table, command-extensions
  list, and Status section.

Not yet verified against the real COM8 device — folds into the existing pending real-hardware
re-run for this module (see `TODO.md`).

## Added a generic NMEA 0183 GPS sentence decoder (`DevTerm.Devices.Nmea`)

New device module for the DeLorme Earthmate GPS BT-20 (USB HID, VID 0x1163/PID 0x0200) — built as a
**generic NMEA 0183 decoder**, not device-specific code, since NMEA 0183 is an openly published
standard many receivers speak identically. Only the VID/PID gate that decides when the Device menu
offers the panel is tied to this one confirmed-compatible unit; see
`docs/design/proposals/nmea-gps-protocol.md` for the full writeup (protocol summary, why the panel
is structured this way, and what's confirmed vs. assumed).

Changes:
- `DevTerm.Devices.Nmea`: `NmeaSentence` (internal parse/checksum/field-conversion helpers),
  `NmeaGpsDecoder` (`IPresenter`/`IStructuredPresenter`, decodes GGA/RMC/GSA/GSV/VTG into both a
  summary line and structured values; defensively strips embedded HID-padding NUL bytes before
  line-buffering), `NmeaGpsControlSurface` (a deliberate no-op — a GPS receiver has no writable
  commands), `NmeaGpsUiDefinition` (read-only indicators).
- Wired into both front ends' Device menu as "NMEA 0183...", gated on
  `DevicePanels.Nmea0183` (the confirmed VID/PID).
- `tests/DevTerm.Devices.Nmea.Tests`: unit tests for `NmeaSentence` and `NmeaGpsDecoder` against
  real, independently-computed-checksum sentence literals (verified via a `node -e` XOR-checksum
  script rather than trusted-by-eye values), plus an opt-in `RealHardwareEarthmateBt20Tests`
  (`TestCategory=Integration,Hid,Delorme_EarthmateBt20,Hardware`) — not yet run, no unit was
  available this session.
- `ConnectionEditorViewModel.PresenterOptions` (the Connection Editor's presenter checkbox list,
  shared by both front ends) is now derived from the DI container's actual registered `IPresenter`
  implementations (`AddDevTermPresenters`, in registration order) instead of a hand-maintained
  string array — this was the third time a new device's presenter name had been forgotten from that
  list, so the fix removes the failure mode structurally rather than just fixing this one instance.

Not yet verified against the real Earthmate BT-20 — the exact HID report framing (report length,
report-ID byte) is a reasoned assumption, not a confirmed fact; see the proposal doc's Open
Questions.
