# 2026-09-18

## Completed

- **Multi-select Presenter picker and per-line send format ("parser") landed together** — two
  Connection Editor backlog items built as one change because they share a design question (with
  several display presenters active, which one encodes a typed line?). The answer: **display and
  send are separate concepts.** Presenters (`IPresenter`) decode incoming bytes for display, any
  number at once; the *parser* is the `IPresenterInput` that encodes typed text, chosen on its own.
  All six text presenters (ascii, utf8, hex, decimal, octal, binary) implement both.

  - **Config shape**: `CliOptions.Presenter` is now a `string[]` (a JSON array in a saved profile,
    `--presenter ascii,hex` on the command line) and a new `CliOptions.Parser` names the encoder.
    `EffectivePresenters` (trimmed, blanks dropped, case-insensitive distinct, `["hex"]` if none)
    and `EffectiveParser` (`Parser`, else the first effective presenter) are the read-side views.
    Chosen by the user over keeping a scalar plus a second list.
  - **Backward compatibility**: an old profile with `"Presenter": "hex"` and no `Parser` still loads
    and behaves as before. Two real .NET config-binder behaviours forced the shape, both verified
    with a throwaway test rather than assumed: the binder **appends** bound array items to a
    non-empty default (`["hex"]` + bound `["a"]` came out `hex|a`, so the property defaults to `[]`
    and the "hex" fallback lives in `EffectivePresenters`), and it **silently drops a scalar bound
    to an array property** (so a scalar `Presenter` from an old profile, a flag, or
    `DEVTERM_PRESENTER` would vanish). New `DevTermConfiguration.Bind(configuration, options)` runs
    the normal bind, then splits a scalar `Presenter` value on commas; `Program.cs`, `App.xaml.cs`,
    and `ConnectionProfileStore` all call it. A scalar comes from a higher-precedence source than a
    JSON array, so it wins. Saved profiles now write the array form plus an explicit `Parser`.
  - **Core/wiring**: `PresenterCatalog` gained `InputNames`/`TryGetInput`;
    `DevTermSessionBuilder.ResolvePresenters(catalog, options)` builds the ordered presenter list
    and throws `InvalidOperationException` for an unknown presenter or a parser that can't encode
    ("Unknown parser '…'. Available: …"); `DevTermSessionBuilder.Result` now carries the
    `PresenterCatalog`. All three front ends take a `PresenterCatalog` instead of one `IPresenter`,
    which is what lets the send format change per line and on a live profile switch.
    `ConnectionDescription.Formats` renders `ascii, hex; send as hex` for titles/banners.
  - **Connection Editor**: WPF shows a wrapped row of `CheckBox`es (`PresenterSelection`, an
    observable name/`IsSelected` pair, bound through an `ItemsControl`) plus a "Send as" `ComboBox`;
    the TUI shows one `CheckBox` per presenter on a row (`OptionSelector<T>` is radio-only) plus a
    "Send as" `OptionSelector`. Ticking a box marks the editor dirty; Connect/Save/Export with
    nothing ticked fails with "Select at least one presenter." (`ValidateFields`).
  - **Main windows**: TUI gained a "Send as" menu-bar menu, WPF a "Send as:" `ComboBox` beside the
    Send button — both start at the profile's parser and change it for every line typed afterward,
    without reconnecting; the title shows `(presenters; send as parser)`. The CLI takes `--parser`
    for the whole run only — a stdin line loop has no per-line syntax that can't collide with real
    input. The old "Presenter does not support sending" branches are gone (every text presenter can
    encode).
  - **Tests**: 24 new across the projects — `CliOptionsBindingTests` (7: comma-separated flag, JSON
    array without the default leaking in, old single-string profile, flag over array, dedupe/blank
    handling, `EffectiveParser` default/independence), `ConnectionEditorViewModelTests` (4),

    and `DeviceProfilesWindowTests` (1). Full run after the docs edits: Core 18, UiDefinitions 4,
    Presenters.Text 30, Transports.Hid 10 / Tcp 16 / Serial 9, DeviceManifests 7, CodingStandards
    2, Wpf 30 (+2 skipped), Configuration 139, Console 50 (+3 skipped) — 0 failed. The skips are the

- **Bulk profile removal ("Delete Selected")** — the saved-profiles list has supported multi-select
  since Export Selected landed, but Delete still only removed the one highlighted profile.
  `ConnectionEditorViewModel.DeleteSelectedProfilesCommand` deletes everything in
  `SelectedProfileNames` (the same collection Export Selected reads; each front end still fills it
  from its own list control right before the command runs). Unlike single Delete it asks first, via a
  new `ConfirmDeleteProfiles` hook (a native `MessageBox`/`MessageBox.Query` per front end, naming the
  profiles about to go; left null it proceeds without asking, like the other `Confirm*` hooks) —
  deleting several profiles at once is irreversible and reaches past the row the user is looking at.
  Status messages: "Select one or more saved profiles to delete first." (nothing marked), "Delete
  cancelled." (declined), "Deleted N profile(s)." with " M not found." appended if another process
  had already removed some. The single selection is cleared if it was one of the deleted profiles;
  the command works from a copy of the names because refreshing the list makes WPF's `ListBox` fire
  its own selection-changed handler, which mutates `SelectedProfileNames` mid-loop. Placement: WPF
  button column under Delete; TUI on the Export Selected/Export All row (the Load/Delete/Refresh row
  has no room for another button in 80 columns). Tests (+9): 4 view-model, 3 TUI (nothing marked,
  marked + confirmed, declined), 2 WPF (real multi-select list, button bound to the command).
  Screenshots regenerated (the new button shows in every TUI configure capture and WPF profiles
  window capture). Full run afterward: Configuration 143, Console 53 (+3 skipped), Wpf 32 (+2
  skipped), every other project unchanged, 0 failed. WPF tests find the button via
  `LogicalTreeHelper` — an unshown window hasn't built its visual tree.
