# 2026-09-18

## Completed

- **Multi-select Presenter picker and per-line send format ("parser") landed together** — two
  Connection Editor backlog items built as one change because they share a design question (with
  several display presenters active, which one encodes a typed line?). The answer: **display and
  send are separate concepts.** Presenters (`IPresenter`) decode incoming bytes for display, any
  number at once; the *parser* is the `IPresenterInput` that encodes typed text, chosen on its own.
  All six text presenters (ascii, utf8, hex, decimal, octal, binary) implement both.

  - **Config shape**: `CliOptions.Presenter` is now a `string[]` (a JSON array in a saved profile,
    `--presenter ascii,hex` on the command line) and a new `CliOptions.Parser` names the encoder.
    `EffectivePresenters` (trimmed, blanks dropped, case-insensitive distinct, `["hex"]` if none)
    and `EffectiveParser` (`Parser`, else the first effective presenter) are the read-side views.
    Chosen by the user over keeping a scalar plus a second list.
  - **Backward compatibility**: an old profile with `"Presenter": "hex"` and no `Parser` still loads
    and behaves as before. Two real .NET config-binder behaviours forced the shape, both verified
    with a throwaway test rather than assumed: the binder **appends** bound array items to a
    non-empty default (`["hex"]` + bound `["a"]` came out `hex|a`, so the property defaults to `[]`
    and the "hex" fallback lives in `EffectivePresenters`), and it **silently drops a scalar bound
    to an array property** (so a scalar `Presenter` from an old profile, a flag, or
    `DEVTERM_PRESENTER` would vanish). New `DevTermConfiguration.Bind(configuration, options)` runs
    the normal bind, then splits a scalar `Presenter` value on commas; `Program.cs`, `App.xaml.cs`,
    and `ConnectionProfileStore` all call it. A scalar comes from a higher-precedence source than a
    JSON array, so it wins. Saved profiles now write the array form plus an explicit `Parser`.
  - **Core/wiring**: `PresenterCatalog` gained `InputNames`/`TryGetInput`;
    `DevTermSessionBuilder.ResolvePresenters(catalog, options)` builds the ordered presenter list
    and throws `InvalidOperationException` for an unknown presenter or a parser that can't encode
    ("Unknown parser '…'. Available: …"); `DevTermSessionBuilder.Result` now carries the
    `PresenterCatalog`. All three front ends take a `PresenterCatalog` instead of one `IPresenter`,
    which is what lets the send format change per line and on a live profile switch.
    `ConnectionDescription.Formats` renders `ascii, hex; send as hex` for titles/banners.
  - **Connection Editor**: WPF shows a wrapped row of `CheckBox`es (`PresenterSelection`, an
    observable name/`IsSelected` pair, bound through an `ItemsControl`) plus a "Send as" `ComboBox`;
    the TUI shows one `CheckBox` per presenter on a row (`OptionSelector<T>` is radio-only) plus a
    "Send as" `OptionSelector`. Ticking a box marks the editor dirty; Connect/Save/Export with
    nothing ticked fails with "Select at least one presenter." (`ValidateFields`).
  - **Main windows**: TUI gained a "Send as" menu-bar menu, WPF a "Send as:" `ComboBox` beside the
    Send button — both start at the profile's parser and change it for every line typed afterward,

    for the whole run only — a stdin line loop has no per-line syntax that can't collide with real
    input. The old "Presenter does not support sending" branches are gone (every text presenter can
    encode).

- **Bulk profile removal ("Delete Selected")** — the saved-profiles list has supported multi-select
  since Export Selected landed, but Delete still only removed the one highlighted profile.
  `ConnectionEditorViewModel.DeleteSelectedProfilesCommand` deletes everything in
  `SelectedProfileNames` (the same collection Export Selected reads; each front end still fills it
  from its own list control right before the command runs). Unlike single Delete it asks first, via a
  new `ConfirmDeleteProfiles` hook (a native `MessageBox`/`MessageBox.Query` per front end, naming the
  profiles about to go; left null it proceeds without asking, like the other `Confirm*` hooks) —
  deleting several profiles at once is irreversible and reaches past the row the user is looking at.
  Status messages: "Select one or more saved profiles to delete first." (nothing marked), "Delete
  cancelled." (declined), "Deleted N profile(s)." with " M not found." appended if another process
  had already removed some. The single selection is cleared if it was one of the deleted profiles;
  the command works from a copy of the names because refreshing the list makes WPF's `ListBox` fire
  its own selection-changed handler, which mutates `SelectedProfileNames` mid-loop. Placement: WPF
  button column under Delete; TUI on the Export Selected/Export All row (the Load/Delete/Refresh row
  has no room for another button in 80 columns). Tests (+9): 4 view-model, 3 TUI (nothing marked,
  marked + confirmed, declined), 2 WPF (real multi-select list, button bound to the command).
  Screenshots regenerated (the new button shows in every TUI configure capture and WPF profiles

- **Window title reflects what's actually connected** — the Architect's 2026-09-16 item. The main
  windows' title is now `dev-term — {subject} ({presenters}; send as {parser})` where the subject
  is the saved profile's name if the running connection is exactly a saved profile, otherwise a
  URI-style connection definition: `tcp://192.168.0.110:23` (`tcp://*:9000 (listening)`),
  `serial://COM3:4800,8,n,1`, `hid://1915.AFDA[.serial]` (vendor/product in hex, the serial number
  standing in for the instance id, since it's the only per-device identifier `CliOptions` carries).
  It's recomputed on every profile switch and `Send as` change in both front ends (the existing
  hooks — no new event plumbing).
  - **Why matching, not a tracked name**: nothing carries a profile name alongside a `CliOptions`
    (a run starts from the untracked default profile, and the editor's Connect just hands back
    edited fields), and a tracked name would go stale the moment a field was edited.
    `ConnectionProfileStore.FindName(options)` compares `ToProfileJson` (the connection-relevant
    subset) against each saved profile instead, so it also works at startup, ignores run-mode flags,
    treats an older profile with no `Parser` the same as one with its effective parser, skips an
    unreadable profile file, and picks the first alphabetically if two are identical. The cost is
    reading each saved profile on each title refresh, which only happens on a switch or a parser
    change.
  - **Deliberate deviations from the Architect's wording**: kept the em dash the title already used
    rather than a hyphen, and kept the `(presenters; send as parser)` suffix from earlier today,
    since the TUI's "Send as" menu doesn't otherwise show the current selection.
  - **Plumbing**: `ConnectionDescription.Definition`/`WindowTitle`; `TuiMode.RunAsync/BuildWindow`
    and the WPF `MainWindow` constructor take an optional `ConnectionProfileStore` (defaulting to the
    real `~/.dev-term/profiles`) that both the title check and the Device Profiles screen use.
    Tests pass an isolated, nonexistent-directory store (`TuiTestRunner.EmptyProfiles`,
    `IsolatedProfiles.Empty`) so a title assertion can't be broken by a real profile on the
    developer's machine.

- **"Replace All" zip import — delete every saved profile, then import the zip** — the last
  functional Connection Editor follow-up from the 2026-09-16 export/import work. Import's per-name
  Replace/Rename/Skip never removes a profile the zip doesn't mention; this is the "restore from a
  backup" alternative. New `ReplaceAllFromZipCommand` (WPF: button between Import and Export, TUI: on
  the Browse/Import/Export/Save As row) and a `ConfirmReplaceAllProfiles(savedCount, zipCount)` hook
  (native `MessageBox`/`MessageBox.Query`; skipped when nothing is saved — nothing to lose).
  - **Safety over cleverness**: the destructive step is split from the read.
    `ConnectionProfileStore.ReadZip` (static, side-effect free) reads every `*.json` entry and
    rejects invalid JSON naming the entry; only then does `ReplaceAll(profiles)` delete and write.
    So an unreadable/invalid/empty zip, or a declined confirmation, deletes nothing (each has its own
    status message ending "Nothing was deleted" where relevant). Only the JSON *syntax* is checked,
    matching `ImportZip`'s existing leniency. Not transactional once writing starts (an I/O error
    says "failed partway"); a temp-folder-and-swap was judged out of proportion. A `.json` path
    is refused ("Replace All needs a .zip file") rather than silently treated as a one-profile
    restore.
  - **Tests (+12)**: 4 store (`ReadZip` entries/ignored files, invalid entry named, duplicate names
    keep the last, `ReplaceAll` removes profiles the zip omits and overwrites shared names), 6
    view-model (replace + confirm counts + selections cleared, declined, unreadable zip, empty
    zip, nothing saved → no prompt, non-zip/empty path), 1 TUI (button, confirmed), 1 WPF (button
    bound to the command). Full run: Configuration 168, Console 56 (+3 skipped), Wpf 34 (+2
    skipped), every other project unchanged, 0 failed. The TUI scrolled-editor and WPF TCP editor

  - Not verified on real hardware (none available); this feature doesn't touch a device connection.

- **Fix: double-clicking a saved profile in the WPF editor didn't load it** — reported as a request
  ("do the same as select, then Load"); the 2026-09-16 feature was already supposed to do that, but
  only ever passed a test, never worked with a real mouse. Reproduced first by raising real
  `MouseDown` events (ClickCount 1 then 2) on a row: the first selected it, the second did nothing.
  Cause: the `MouseBinding` was on the `ListBox`, and `ListBoxItem` marks the mouse-down handled to
  select the row, so the list's `InputBindings` never saw it. Now a `MouseDoubleClick` `EventSetter`
  in `ItemContainerStyle` → `ProfilesList_ItemDoubleClick`, which selects the clicked row, then runs
  the shared `LoadCommand` (so the unsaved-changes confirmation still applies). Re-ran the same
  simulated double-click after the fix: "Loaded profile 'tek108'".
  - **The TUI was already fine**: a one-off probe injecting a real `MouseFlags.LeftButtonDoubleClicked`

- **The HID "Detected devices" picker is filtered by the Vendor/Product ID fields** — requested as
  "if the vendor id or product id is not 0 then filter the list, like `Where VendorId in (0,
  vendorId) and ProductId in (0, productId)`". A non-zero id keeps only devices with that id; `0`
  means any; an id that isn't a number yet counts as 0. Live: `ConnectionEditorViewModel.HidDeviceOptions`
  is now a filtered view over everything detected, recomputed whenever `HidVendorId`/`HidProductId`
  change (typing, the hex display field, Load, or picking a device).
  - **Interpretation**: I read the pseudo-code as "0 is a wildcard on the *field*", so a device that
    itself reports vendor/product id 0 is not also matched by a non-zero filter.
  - **In-place updates, not a new list**: the list is an `ObservableCollection` edited in place, so
    the WPF combobox follows it live and keeps a selection that still matches (verified with a real
    bound `ComboBox`); exposed as `IReadOnlyList<HidDeviceOption>`, so nothing else changed for
    callers. New `HidDevicesHiddenByFilter` lets the TUI's empty-picker message say "No detected HID
    device matches the Vendor/Product ID entered (0 means any)" rather than "Nothing was detected."
    The TUI's Detect button now pushes its typed fields into the view model first (its fields only
    sync on button presses), then reads the filtered list.
  - **Side effect to be aware of**: picking a device fills in both ids, which narrows the list to just
    that device; to choose another one, set an id back to 0. Easy to change if that's annoying — e.g.
    only filter on ids the user typed rather than ones a pick filled in.
  - **Tests (+11)**: 10 view-model (no ids = everything, vendor only, product only, both must match,
    later edits widen/narrow in detection order, hex display field, non-numeric id doesn't filter,
    initial options filter from the start, in-place collection with exactly the expected change
    events, a pick is a real edit and stays in the list) and 1 WPF (a bound `ComboBox` follows the
    filter and keeps its selection). Configuration 185 (was 175), Wpf 31 (+2 skipped) excluding the
    screenshot tests. The TUI Detect handler change is a modal dialog, so it's covered structurally
