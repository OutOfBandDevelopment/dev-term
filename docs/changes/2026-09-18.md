## Completed

- **Multi-select Presenter picker and per-line send format ("parser") landed together** — two
  Connection Editor backlog items built as one change because they share a design question (with
  several display presenters active, which one encodes a typed line?). The answer: **display and
  send are separate concepts.** Presenters (`IPresenter`) decode incoming bytes for display, any
  number at once; the *parser* is the `IPresenterInput` that encodes typed text, chosen on its own.
  All six text presenters (ascii, utf8, hex, decimal, octal, binary) implement both.

  - **Config shape**: `CliOptions.Presenter` is now a `string[]` (a JSON array in a saved profile,
    `--presenter ascii,hex` on the command line) and a new `CliOptions.Parser` names the encoder.
    `EffectivePresenters` (trimmed, blanks dropped, case-insensitive distinct, `["hex"]` if none)
    and `EffectiveParser` (`Parser`, else the first effective presenter) are the read-side views.
    Chosen by the user over keeping a scalar plus a second list.
  - **Backward compatibility**: an old profile with `"Presenter": "hex"` and no `Parser` still loads
    and behaves as before. Two real .NET config-binder behaviours forced the shape, both verified
    with a throwaway test rather than assumed: the binder **appends** bound array items to a
    non-empty default (`["hex"]` + bound `["a"]` came out `hex|a`, so the property defaults to `[]`
    and the "hex" fallback lives in `EffectivePresenters`), and it **silently drops a scalar bound
    to an array property** (so a scalar `Presenter` from an old profile, a flag, or
    `DEVTERM_PRESENTER` would vanish). New `DevTermConfiguration.Bind(configuration, options)` runs
    the normal bind, then splits a scalar `Presenter` value on commas; `Program.cs`, `App.xaml.cs`,
    and `ConnectionProfileStore` all call it. A scalar comes from a higher-precedence source than a
    JSON array, so it wins. Saved profiles now write the array form plus an explicit `Parser`.
  - **Core/wiring**: `PresenterCatalog` gained `InputNames`/`TryGetInput`;
    `DevTermSessionBuilder.ResolvePresenters(catalog, options)` builds the ordered presenter list
    and throws `InvalidOperationException` for an unknown presenter or a parser that can't encode
    ("Unknown parser '…'. Available: …"); `DevTermSessionBuilder.Result` now carries the
    `PresenterCatalog`. All three front ends take a `PresenterCatalog` instead of one `IPresenter`,
    which is what lets the send format change per line and on a live profile switch.
    `ConnectionDescription.Formats` renders `ascii, hex; send as hex` for titles/banners.

  `serial://COM3:4800,8,n,1`, `hid://1915.AFDA[.serial]` (vendor/product in hex, the serial number

    edited fields), and a tracked name would go stale the moment a field was edited.

    subset) against each saved profile instead, so it also works at startup, ignores run-mode flags,
    treats an older profile with no `Parser` the same as one with its effective parser, skips an
    unreadable profile file, and picks the first alphabetically if two are identical. The cost is
    reading each saved profile on each title refresh, which only happens on a switch or a parser
    change.

- **"Replace All" zip import — delete every saved profile, then import the zip** — the last
  functional Connection Editor follow-up from the 2026-09-16 export/import work. Import's per-name
  Replace/Rename/Skip never removes a profile the zip doesn't mention; this is the "restore from a
  backup" alternative. New `ReplaceAllFromZipCommand` (WPF: button between Import and Export, TUI: on
  the Browse/Import/Export/Save As row) and a `ConfirmReplaceAllProfiles(savedCount, zipCount)` hook
  (native `MessageBox`/`MessageBox.Query`; skipped when nothing is saved — nothing to lose).
  - **Safety over cleverness**: the destructive step is split from the read.
    `ConnectionProfileStore.ReadZip` (static, side-effect free) reads every `*.json` entry and
    rejects invalid JSON naming the entry; only then does `ReplaceAll(profiles)` delete and write.
    So an unreadable/invalid/empty zip, or a declined confirmation, deletes nothing (each has its own
    status message ending "Nothing was deleted" where relevant). Only the JSON *syntax* is checked,
    matching `ImportZip`'s existing leniency. Not transactional once writing starts (an I/O error
    says "failed partway"); a temp-folder-and-swap was judged out of proportion. A `.json` path
    is refused ("Replace All needs a .zip file") rather than silently treated as a one-profile
    restore.

- **A device timeout is now reported instead of crashing** — reported as "if devices time out they

- **Fix: the TUI editor's fields couldn't take input at all** — reported as "I can't type in the TUI
  input fields on the editor panel anymore", then "the TUI inputs don't work". Real bug, found by
  driving the real TUI in a classic console (injected key events, `PrintWindow` screenshots) and
  bisecting with two throwaway worktrees: the build from just before `3743cdc` ("make the Connection
  Editor form scrollable") took typing and showed a focus highlight; `3743cdc` and everything after
  showed **no focus anywhere** — Tab did nothing visible, typed text went nowhere. Cause: that commit
  moved every control into a scrollable container that is a plain `View`, whose `CanFocus` defaults to
  `false`, and an unfocusable container stops focus reaching any child. So it has been broken since
  that commit (and not caught: no test asked whether a field could hold focus, and headless
  key-injection tests were already known to be unreliable). Two changes in `ConfigureMode`:
  - `formContent.CanFocus = true` — the fix. Verified live afterwards: the saved-profiles list is
    highlighted at startup, Tab walks the controls, and `hello` typed into Description appeared.
  - **Focusing a control scrolls it into view.** Making fields focusable exposed the next problem:
    the form is ~40 rows in a window of ~13, and Tab moved focus to controls below the fold without
    moving the viewport (34 Tabs and nothing visible was focused). Each direct child of the form now
    reveals itself in the viewport when it gains focus (`HasFocusChanged`). Verified live: the same 34
    Tabs now end with `Browse...` focused and scrolled into view.
  - **Behavior change worth knowing:** PageUp/PageDown scroll the form only when the saved-profiles
    list *doesn't* have focus (that carve-out already existed, since the list owns those keys). With
    focus now really starting on the list, PageDown at startup pages the list, not the form; Tab off
    it and PageDown/mouse wheel scroll the form, and Tab scrolls on its own anyway. The two existing
    PageDown tests (`PageDown_ScrollsToRevealControlsBelowTheFold`, the scrolled screenshot test) now
    move focus to the Description field first.
  - **Tests (+2)**: `FormFields_CanTakeFocus_SoTheUserCanTabToAndTypeIntoThem` (confirmed to fail
    with `CanFocus = false`) and `FocusingAControlBelowTheFold_ScrollsItIntoView` (confirmed to fail
    with the reveal call removed). They assert focus, not typed text — headless key injection stays
    unreliable. Console 58 (+3 skipped) on the normal path.
  - **Also seen, not changed:** in a classic Windows console the text fields render white-on-light-
    gray, so their contents (`COM3`, `4800`, anything typed) are low contrast. That's the driver's
    default color scheme, not new; worth a look if it bothers anyone.

- **Fix: closing the WPF window crashed** — a pasted stack trace: `InvalidOperationException` "Cannot
  set Visibility to Visible or call Show, ShowDialog, Close, or WindowInteropHelper.EnsureHandle while
  a Window is closing." at `MainWindow.OnClosing` (line 299). Very possibly what "if devices time out
  they throw an error and crash the app" was actually seeing. Cause: `OnClosing` cancels the close,
  awaits `Session.CloseAsync`/`DisposeAsync`, then calls `Close()` again — but when those awaits are
  already-completed tasks (a transport that closes instantly, or a session that never connected) the
  continuation runs *synchronously inside the first `Close()`*, so the second `Close()` fired while
  the window was still closing. Fix: `await Dispatcher.Yield()` before the second `Close()` so it
  runs after the first has unwound; also, a connection-type failure during that cleanup is now
  swallowed (`IsConnectionFailure`) rather than turning a close into a crash. This is the same
  reentrancy that CLAUDE.md recorded as a test-automation quirk ("don't call `Window.Close()` on a
  shown `MainWindow`") — it was a real app bug, not a test artifact; that note is corrected.
  **Tests (+3, `MainWindowTests.Close_*`)**, reproduced failing first, then passing.
  Not seen on a physical device (the reproduction is a fake transport).
