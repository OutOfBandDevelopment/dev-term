## Applied queued SystemUsbtmcDevice code-review findings

Applied the four `SystemUsbtmcDevice` code-review findings queued in commit `1897ce4` (filed in
`docs/design/usbtmc-transport.md`'s "Open questions" section, deliberately deferred pending the
USBTMC bulk-IN stall investigation which is still parked): endpoint selection now filters transfer
type (`Attributes & 0x03 == 0x02`, Bulk) in addition to direction, so an optional Interrupt-IN
endpoint (USB488 SRQ) can no longer be mistaken for bulk-IN; `SetRemote`'s `wValue` is now always
`0` per the USB488 subclass spec instead of `remote ? 1 : 0`; `TryGetSerialNumber`'s swallowed
exception is now logged via `Debug.WriteLine`; and `Open()`'s failure-path catch now explicitly
calls `ReleaseInterface` before `Close()`/`Dispose()`. No behavior change expected against real
hardware already working (Rigol DM3058E's bulk-IN endpoint was already sorting first in its
descriptor), verified via a clean full-solution build and a full passing `TestCategory=UNIT` run;
not re-verified against real hardware this pass, since the parked stall issue means the DM3058E
still can't complete a query round-trip to confirm end-to-end. See
[`docs/design/usbtmc-transport.md`](../design/usbtmc-transport.md) for the updated findings detail.

## Built and verified the Rigol DS1102E SCPI profile against real hardware

Built `src/DevTerm.Devices.Scpi/Profiles/rigol-ds1102e.json` from
`docs/devices/rigol-ds1102e/programming-manual.md`, replacing the wrong-model
`rigol-ds1105e.json`, then tested all 27 of its query commands plus `:WAV:DATA?` against the bench
unit over USBTMC — all now return correct data. Found and fixed three real bugs along the way: two
in `DevTerm.Transports.Usbtmc` that affect every USBTMC device (`UsbtmcTransport.IsQuery` only
checked an outgoing line's last character, silently dropping replies to any query with a trailing
parameter like `:MEAS:VPP? CHAN1`; LibUsbDotNet's string-descriptor properties come back
NUL-padded, breaking `--serialnumber` matching and `--listusbtmcdevices` output) plus a
`DevTerm.Configuration` gap (`--readtimeoutms`/`--writetimeoutms` were never wired into
`UsbtmcTransportOptions`, unlike the Serial branch); one in the profile itself (`:MEAS:VAVG?`/
`:MEAS:RISE?` used guessed-at full-name abbreviations instead of the SCPI short forms `VAV`/`RIS`,
which the device simply doesn't answer at all). Also set the profile's `Terminator` to `""`,
mirroring the Korad KA3005P/KA6003P profiles, since the DS1102E's USBTMC replies carry no CR/LF —
the EOM bit alone marks the message boundary. Full detail, the complete command/response table,
and remaining open notes (no `DevTerm.Transports.Usbtmc.Tests` project exists yet): see
[`docs/test/2026-09-24-09-54-39.md`](../test/2026-09-24-09-54-39.md).
