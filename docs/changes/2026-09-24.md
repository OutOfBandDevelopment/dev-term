## Merged the TCP flag into `--port`, shared with serial

`CliOptions.TcpPort` (`int`) is gone; the TCP transport now reads its port from the same `Port`
(`string?`) property serial already used for a COM port name, so both transports take `--port`
instead of the TCP side needing its own `--tcpport` — one less flag to remember, and consistent
with `CliOptions`' own rule that a property name doubles as its flag name. `CliOptionsValidator`
and `ServiceCollectionExtensions` now `int.TryParse(options.Port, ...)` for the TCP branch instead
of reading a pre-parsed int. `ConnectionEditorViewModel` keeps its own separate `Port`/`TcpPort`
UI-facing fields (bound to different Connection Editor controls depending on transport) unchanged
by name — both now read/write the single underlying `CliOptions.Port`, gated by `IsTcpTransport` at
save time, so no TUI/WPF UI-layer changes were needed beyond that. Updated everywhere `--tcpport`
was previously documented or invoked: both front ends' `launchSettings.json`, the `docs/user-guide/`
CLI walkthroughs, and every test file that built a `CliOptions`/JSON profile/CLI invocation string
with the old property. `docs/changes/2026-09-23.md`'s own `--tcpport` example is left as-is, since
it's a historical record of what was true on that date. Verified via a full clean
`dotnet build DevTerm.slnx` and a full `dotnet test DevTerm.slnx` pass (one test,
`ConnectionProfileStoreTests.Save_TcpTransport_OnlySavesTcpFields`, had its own stale assertion
fixed in the same pass — it asserted `loaded.Port` was simultaneously `"23"` and `null`, a leftover
from when `Port` was serial-only; it now checks `Baud` for that "no serial-specific fields on a TCP
profile" case instead).

## Fixed HID connection failure for serial-less devices (e.g. Velleman K8055) by splitting DevicePath out of SerialNumber

Connecting to a real K8055 (attached three-at-once on the bench, same VID/PID, no serial descriptor
at all) failed with `"No HID device found for VID 0x10CF PID 0x5500 serial '...'"` even though a
device was picked in the connection editor. Root cause: the `SerialNumber`/`DevicePath`-fallback
design landed on 2026-09-23 folded a serial-less device's `DevicePath` directly into the
`SerialNumber` field/property so every consumer only had one value to read — but
`SystemHidDevice.Open()` passed that value straight into HidSharp's own
`DeviceList.Local.GetHidDeviceOrNull(serialNumber:)`, which only ever matches a device's *real*
serial descriptor. A folded `DevicePath` string could never match a real (`null`) serial, so the
open always failed. Separately, since `SystemHidDevice.Open()` never actually looked at
`DevicePath` at all, picking a different one of the three K8055 boards in the UI had no effect on
which physical board actually got opened.

Fixed by splitting `SerialNumber` and `DevicePath` into two genuinely independent fields, carried in
parallel end-to-end: `CliOptions.DevicePath` (persisted alongside `SerialNumber` in a saved profile
whenever non-null), `ConnectionEditorViewModel.DevicePath` (populated from `SelectedHidDevice`/a
loaded profile — no visible control in either front end, since there's nothing to hand-type),
`HidTransportOptions.DevicePath`, wired through `ServiceCollectionExtensions`. Matching — both
`FindBestUsbDeviceMatch`'s UI auto-select and `SystemHidDevice.Open`'s real connection path — now
tries an exact `SerialNumber` match first (when non-blank), falls back to an exact `DevicePath`
match, and only then falls back to the first device found for the given VID/PID.
`SystemHidDevice.Open()` no longer calls HidSharp's serial-only `GetHidDeviceOrNull` at all; it
enumerates candidates via `DeviceList.Local.GetHidDevices(vendorId, productId, null, null)` (VID/PID
filter only) and applies the three-tier match itself. `HidDeviceOption.FromDescriptor` no longer
folds `DevicePath` into `SerialNumber` — a device with no real serial now reports `SerialNumber` as
`null`, with `DevicePath` as its own separate, always-populated field. `UsbtmcDeviceOption`/
`UsbtmcTransportOptions` are unaffected (no `DevicePath`-equivalent field exists there — see
`BACKLOG.md`'s Connection Editor section for that still-open gap). Verified via a full clean
`dotnet build DevTerm.slnx` and a full passing `TestCategory=UNIT` run, including a new regression
test (`ConnectionEditorViewModelTests.LoadIntoFields_ThreeIdenticalSerialLessHidDevices_SelectsTheOneMatchingDevicePath`)
covering three same-VID/PID, no-serial devices distinguished only by `DevicePath`; also verified
against the real bench, in both front ends: three simultaneously-attached Velleman K8055 boards,
previously indistinguishable and unopenable, now each connect correctly by their own `DevicePath`
via the console CLI, and the WPF front end's own connect flow was confirmed against the same
three-board setup too.

## Fixed the USBTMC bulk-IN reassembly bug causing communication lockups

Fixed the root cause behind field reports of USBTMC "communication locking up" against Rigol
DG1022/DS1102E/DM3058E: `UsbtmcTransport.ReadReply` was re-decoding a bulk-IN 12-byte header on
*every* physical transfer of a logical `DEV_DEP_MSG_IN` response, but per USBTMC 1.0 only the
**first** physical transfer of a multi-transfer reply carries a header — every later transfer is
raw continuation payload. Re-parsing those raw bytes as a header produced a bogus `TransferSize`
and hung forever waiting for bytes that were never coming; this only surfaced for a reply long
enough to span more than one physical transfer, which is why it read as intermittent. Fixed per
[`docs/design/features/usbtmc-bulk-in-reassembly-fix.md`](../design/features/usbtmc-bulk-in-reassembly-fix.md)
(moved there from `docs/design/proposals/` now that it's done — see below): the header is decoded
exactly once, then continuation reads are pure byte-counted payload against `TransferSize`
(matching libsigrok's `scpi_usbtmc_libusb.c`). Two compounding hardening gaps fixed alongside it:
`SendRequestDevDepMsgIn` now requests an effectively unlimited `int.MaxValue` instead of one
buffer's worth (`device.MaxTransferSize`), and `UsbtmcCodec.DecodeHeader` now validates MsgID/
bTag/`~bTag`/expected-tag before trusting a header, with a new `UsbtmcTransportOptions.MaxResponseSize`
(default 16 MB) capping a well-formed-but-implausible declared size. A previously-silent failure
mode is also closed: `ReadReply` now throws `IOException` instead of returning an empty
`List<byte[]>` when a read genuinely fails, so a failed query can no longer look identical to one
that legitimately returned nothing (see `BACKLOG.md`'s USBTMC entry — this was a general
reliability gap, not specific to the two "stuck" units).

Covered by 13 new unit tests in `tests/DevTerm.Transports.Usbtmc.Tests` (new project), including the
two the fix's own doc called out as "most likely to be skipped": a reply spanning two physical
transfers reassembling correctly, and proof that continuation bytes shaped to look like a valid
header are never re-parsed as one.

Re-verified against real hardware: DM3058E has no regression. DS1102E is now reliably correct —
chasing an intermittent "silent nothing" on it surfaced a *further*, Rigol-firmware-specific quirk
(a query right after `OpenAsync` sometimes gets back a fully valid, EOM-terminated, zero-byte
message before the real reply), fixed the same way as the existing stall-retry: re-issue
`REQUEST_DEV_DEP_MSG_IN` once, treat a second empty reply as legitimately empty. DG1022 remains
genuinely stuck at the device/USB level in this session's bench state — not something this fix
addresses — but the previously-silent-forever hang now surfaces as a clean, catchable
`IOException` instead. Full detail, including what's still open for the DG1022 and DG1062Z: see
`BACKLOG.md`'s USBTMC entry.

Also moved `docs/design/proposals/scpi-instrument-control.md` (already marked implemented) and this
fix's own task doc to a new `docs/design/features/` directory, so completed proposals stop mingling
with not-yet-started ones — `docs/design/README.md` now has a "Features" section pointing there.
