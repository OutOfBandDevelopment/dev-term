- **`RealHardwareCliTests` generalized further, per direct feedback**: the query text sent to each

- **Double-click a saved profile to load it, in both front ends** — the same `LoadCommand` a Load
  button press already uses, not a separate code path. WPF needed no code-behind at all: `ListBox`
  has no XAML way to bind a routed mouse event to a command directly, but does support
  `<ListBox.InputBindings><MouseBinding MouseAction="LeftDoubleClick" Command="{Binding LoadCommand}" />`.
  The TUI's `ListView` has no such binding concept — confirmed via reflection against the installed
  Terminal.Gui v2.5.0 package that a double-click maps to `Command.Accept` (a single click maps to a
  different command, `Activate` — the "OpenSelectedItem"/"Activated"-sounding members are a natural
  but wrong first guess here, this version renamed things), so `ConfigureMode` subscribes
  `profilesList.Accepting` to the same local function the Load button's own handler already calls.

- **Dirty-field confirmation landed** — the "if inputs are dirty should get an OK/Cancel dialog on
  load, close, connect" Architect Notes item, closed for the two actions that actually discard
  something (Connect doesn't discard anything, so it's excluded on purpose, not an oversight).
  `ConnectionEditorViewModel.IsDirty` flips true the moment any field changes — everything except
  transient UI state (`StatusMessage`, `SelectedProfileName`, the `Is*Transport` flags) — and clears
  on a successful Load, Save, Connect, or Import. A new `ConfirmDiscardChanges` hook (`Func<bool>?`,
  same "left null in tests, always proceeds" convention as the existing `ConfirmOverwrite`) backs a
  `ConfirmClose()` method both Close/Quit and Load now call before actually discarding whatever's
  unsaved. Freshly opening the editor is never dirty — `LoadIntoFields` in the constructor would
  otherwise flip it true immediately, so it's explicitly reset right after.

  Wired per front end the same way `ConfirmOverwrite` already is: WPF's `MessageBox.Show` in
  `DeviceProfilesWindow`'s constructor, backing a new `Window.Closing` handler (`e.Cancel = true` on
  decline) that covers both the Close button and pressing Escape — WPF triggers an `IsCancel`
  button's click for Escape by default, both paths end up at `Window.Close()`. Doesn't interfere
  with the Connect path: `Connect()` already clears `IsDirty` before raising `CloseRequested`, so by
  the time that handler sets `DialogResult = true` (itself triggering `Closing`), there's nothing
  left to confirm. The TUI's `ConfigureMode` wires the equivalent `Terminal.Gui.Views.MessageBox.Query`
  and pushes Terminal.Gui field values into the view model before checking dirty on Quit (the only
  point besides Save/Import/Export/Connect that already does this), since a value typed but never
  synced into the view model wouldn't otherwise register as an edit.

- **Coding standards infrastructure**: new `.editorconfig` (repo root), `Directory.Build.props`
  (references StyleCop.Analyzers solution-wide, sets `EnforceCodeStyleInBuild=true` so style rules
  actually surface as `dotnet build` warnings), and `docs/coding-standards.md` — a declared,
  enforced list of standards, not a style guide written in the abstract; a new rule gets written
  down there and turned on in `.editorconfig` in the same change.

  The baseline itself: file-scoped namespaces, Allman braces (required even for single-statement
  bodies), `var` where the type's obvious, expression-bodied simple members, no `this.`
  qualification, `System.*`-first `using` ordering, `_camelCase` private fields — all derived from
  what's *already* consistently true across the codebase (checked directly, file by file, not
  assumed), encoded via the built-in Roslyn `csharp_style_*`/`dotnet_style_*` keys.

  StyleCop.Analyzers is referenced but starts **completely silent** — every rule at
  `severity = none` by category, confirmed necessary by actually building against it first: with
  its out-of-the-box defaults, a full rebuild produced ~1,800 warnings, 1,396 of them `SA1101`
  ("prefix local calls with `this`") alone — a style this codebase has never used anywhere, and none
  of the ~1,800 reflecting an actual declared standard. Re-verified after silencing: 0 new warnings
  against the existing codebase, only the two pre-existing, already-accepted warning families
  (`CS0618` Terminal.Gui obsolete-API notices, `CS8602` nullable-dereference warnings already known
  about) remain. A specific `SAxxxx` rule turns on with one `.editorconfig` line once a standard is
  actually declared for it — see `docs/coding-standards.md`'s own "Adding a new standard" section.

  A custom `DevTerm.Analyzers` Roslyn project (for project-specific semantic rules no generic
  analyzer covers) is deliberately deferred to `TODO.md`'s backlog rather than scaffolded now — no
  such rule has come up yet that needs one.

- **Real file-watcher auto-refresh for the saved-profiles list**, the next Connection Editor
  Architect Notes item picked up. `ConnectionEditorViewModel` is now `IDisposable` and watches
  `ConnectionProfileStore.ProfilesDirectory` (new public property, exposing what was previously a
  private implementation detail) via a real `FileSystemWatcher`, raising a new
  `ProfilesChangedExternally` event on add/remove/rename. Each front end subscribes and marshals
  onto its own UI thread (`Dispatcher.BeginInvoke` in WPF, `Application.Invoke` in the TUI) before
  calling the same `RefreshCommand` the Refresh button already used — the button stays as a manual
  fallback, and construction tolerates the watcher failing to start at all (e.g. a permissions
  problem) by just not auto-refreshing rather than failing the whole editor.

  Found and fixed a real crash while landing this, confirmed by watching it actually happen, not
  hypothesized: the watcher fires on its own background thread, and the very first full test-suite
  run after adding it took down the entire `DevTerm.Console.Tests` process with an unhandled
  `Terminal.Gui.App.NotInitializedException` — a filesystem event (the test's own directory cleanup
  deleting a profile file) fired *after* `Application.Shutdown()` had already run for that test,
  and `Application.Invoke` doesn't no-op in that state, it throws, uncaught, on a background thread,
  which is fatal to the whole process rather than just that one test. Fixed with a targeted
  try/catch around the TUI's `Application.Invoke` call. Added a dedicated regression test that
  reproduces the exact sequence (build and tear down a real window, then trigger a genuine
  filesystem event afterward) and confirmed stable across three repeated full runs of the affected
  test class, then the whole solution.

  New tests: 2 in `ConnectionEditorViewModelTests` (a real watcher notices a save from a second,

- **TUI: a real Browse button and a scrollable form** — the two Connection Editor Open items marked
  "confirmed possible, not wired up." Investigated both properly before writing any code, same
  discipline as everything else Terminal.Gui-related in this project: a throwaway headless probe
  against the installed v2.5.0 package confirmed `OpenDialog`/`SaveDialog` show as a real
  `Application.Run(dialog)` modal (read `dialog.FilePaths`/`Canceled` afterward), and that setting a
  `View`'s content size plus `ViewportSettings |= AllowNegativeY | HasVerticalScrollBar` genuinely
  scrolls real content, verified by capturing the buffer before and after moving `Viewport.Y`
  programmatically. A second probe answered the follow-up question directly instead of assuming:
  `View` has *no* built-in handling for `Command.ScrollDown`/`PageDown` (invoking either did nothing
  to a real view's `Viewport`), so keyboard/wheel scrolling needed wiring by hand either way.

  `ConfigureMode`'s "Browse..." button mirrors WPF's `Browse_Click` exactly, limitation included —
  both use an open-style picker (an existing file only) for *both* Import and Export. The whole form
  now lives inside a new `formContent` container `View` instead of being added straight to the
  window, scrollable via PageUp/PageDown or the mouse wheel. The PageUp/PageDown binding is on the
  global `Application.KeyDown`, but checks `profilesList.HasFocus` first and backs off if so: a
  direct check (`ListView.KeyBindings.GetBindings()`) showed `ListView` already binds PageUp,
  PageDown, *and* the plain arrow keys for its own item navigation, so an unconditional global
  intercept would have silently broken scrolling within the saved-profiles list itself. (Arrow keys
  were dropped from the form-scroll bindings entirely for the same reason — PageUp/PageDown plus the
  wheel felt like enough without risking a similar collision somewhere else in the form.)

  Adding the Browse button surfaced a real, unrelated layout bug the same day it landed: crowding

  Investigated Terminal.Gui for a native combobox first, same discipline as every other
  Terminal.Gui-touching change this session: reflection against the installed v2.5.0 package found
  `TextFieldAutocomplete`/`SingleWordSuggestionGenerator` (a `TextField.Autocomplete` property
  backed by a simple `List<string>` of suggestions) as the closest built-in equivalent, but it has no

  was set aside in favor of composing already-proven pieces instead: a plain `Dialog`+`ListView`
