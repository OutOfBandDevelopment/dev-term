# 2026-09-16

## Completed

- **`RealHardwareCliTests` generalized further, per direct feedback**: the query text sent to each
  real device is now also a `.runsettings` parameter *name*, not a literal in the `DataRow` — the
  same treatment the expected-reply parameter already got yesterday. A fourth real device can be
  added later with only new `devterm.runsettings` entries plus one new `DataRow`, no code change.

- **Double-click a saved profile to load it, in both front ends** — the same `LoadCommand` a Load
  button press already uses, not a separate code path. WPF needed no code-behind at all: `ListBox`
  has no XAML way to bind a routed mouse event to a command directly, but does support
  `<ListBox.InputBindings><MouseBinding MouseAction="LeftDoubleClick" Command="{Binding LoadCommand}" />`.
  The TUI's `ListView` has no such binding concept — confirmed via reflection against the installed
  Terminal.Gui v2.5.0 package that a double-click maps to `Command.Accept` (a single click maps to a
  different command, `Activate` — the "OpenSelectedItem"/"Activated"-sounding members are a natural
  but wrong first guess here, this version renamed things), so `ConfigureMode` subscribes
  `profilesList.Accepting` to the same local function the Load button's own handler already calls.

- **Dirty-field confirmation landed** — the "if inputs are dirty should get an OK/Cancel dialog on
  load, close, connect" Architect Notes item, closed for the two actions that actually discard
  something (Connect doesn't discard anything, so it's excluded on purpose, not an oversight).
  `ConnectionEditorViewModel.IsDirty` flips true the moment any field changes — everything except
  transient UI state (`StatusMessage`, `SelectedProfileName`, the `Is*Transport` flags) — and clears
  on a successful Load, Save, Connect, or Import. A new `ConfirmDiscardChanges` hook (`Func<bool>?`,
  same "left null in tests, always proceeds" convention as the existing `ConfirmOverwrite`) backs a
  `ConfirmClose()` method both Close/Quit and Load now call before actually discarding whatever's
  unsaved. Freshly opening the editor is never dirty — `LoadIntoFields` in the constructor would
  otherwise flip it true immediately, so it's explicitly reset right after.

  Wired per front end the same way `ConfirmOverwrite` already is: WPF's `MessageBox.Show` in
  `DeviceProfilesWindow`'s constructor, backing a new `Window.Closing` handler (`e.Cancel = true` on
  decline) that covers both the Close button and pressing Escape — WPF triggers an `IsCancel`
  button's click for Escape by default, both paths end up at `Window.Close()`. Doesn't interfere
  with the Connect path: `Connect()` already clears `IsDirty` before raising `CloseRequested`, so by
  the time that handler sets `DialogResult = true` (itself triggering `Closing`), there's nothing
  left to confirm. The TUI's `ConfigureMode` wires the equivalent `Terminal.Gui.Views.MessageBox.Query`
  and pushes Terminal.Gui field values into the view model before checking dirty on Quit (the only
  point besides Save/Import/Export/Connect that already does this), since a value typed but never
  synced into the view model wouldn't otherwise register as an edit.

  Found and fixed a real self-inflicted test hang while landing this: `ConfigureModeTests.
  Quit_SetsResultToNull` edited a few fields before clicking Quit (incidental setup, not needed for
  what it actually asserts) — with dirty-checking now live, that made the view model dirty and
  Quit's real, blocking `MessageBox.Query` popped up with nothing able to click it in headless test
  mode, hanging the run. Confirmed by watching it happen (the background test process had to be
  killed manually), not assumed. Fixed by dropping the unnecessary field edits from that test and
  adding a dedicated one that stubs `ConfirmDiscardChanges` directly — exposed a `ViewModel` property
  on `ConfigureWindowParts` for exactly this, mirroring how `DeviceProfilesWindow.ViewModel` already
  lets WPF tests do the same. Same "verify the view-model-level dialog logic separately, never
  exercise the real blocking dialog from a headless/automated UI-level test" convention `ConfirmOverwrite`
  already established.

  New tests: 3 more in `ConnectionEditorViewModelTests` (dirty-marking, Load's confirmation, Load's
  confirmation being skippable), plus `ConfirmClose_*` coverage from the underlying method; 1 more in
  `ConfigureModeTests` (Quit's confirmation) plus the double-click test; 2 more in
  `DeviceProfilesWindowTests` (`Closing`'s confirmation, the double-click binding). 249 tests across
  the solution now (244 pass by default).

  `docs/specs/connection-editor.md` updated: Fields/Actions/States describe the new double-click and
