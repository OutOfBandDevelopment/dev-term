## Multi-session UI: WPF TabControl (Step 2) and TUI Tabs (Step 3)

Implements the next two steps of `docs/design/multi-session-ui.md` (Step 1, `SessionTab` extraction,
landed earlier — `0c006f8`): both front ends' main windows now hold a tab strip of independent
sessions instead of exactly one, per that design's recommended implementation order.

**WPF (`447ebab`)**: `MainWindow` now holds a list of `WindowTab` — a `SessionTab` plus its own
`TabItem`, output `ListBox`, header `TextBlock`, and event-handler delegates — instead of a single
session's worth of window-level fields. A `SessionTabs` (`TabControl`) replaces the old
window-level `OutputList`; each tab's `Session.Output`/`Disconnected` routes to that tab's own
output list, not "whichever tab is active." File > New Session adds a tab via
`DevTermSessionBuilder.Build`; File > Close Session (enabled only when more than one tab is open)
closes the active tab, its session, and any control panels it owns (tracked via `Window.Tag` — bug
016). `SendHistory` and the send-format picker are per-tab. `DarkControls.xaml` gained
`TabControl`/`TabItem` styles (the stock Aero2 chrome is hard-coded light, the same gap as every
other themed stock control).

**TUI (`618b869`)**: mirrors the WPF shape. `TuiMode` now holds a list of `TuiWindowTab` — a
`SessionTab` plus its own `Editor` output pane, `TextField` `SendField`, and per-tab `SendHistory` —
instead of one. A `Terminal.Gui.Views.Tabs` control (confirmed present in the installed 2.5.0
package via reflection; the design doc's draft had assumed a nonexistent "TabView") replaces the old
window-level `output` `Editor`. File > New Session... opens `ConfigureMode`'s nested dialog,
pre-filled from the active tab's own connection, and adds a tab via `SessionTab.Build`; File > Close
Session (enabled only with more than one tab open) closes the active tab, unsubscribes its
handlers, and reassigns `Tabs.Value` to a remaining tab. Shared chrome (status line, Device menu
items, connection state) rebinds to whichever tab is active via
`RefreshConnectionUi(TuiWindowTab)`/`ActiveTab()`. `TuiWindowParts` gained `TabsView`,
`NewSessionMenuItem`, `CloseSessionMenuItem`, and `AllSessions` (closes every open tab's session at
shutdown). New test coverage (`TuiModeMultiSessionTests`) drives the real menu actions end-to-end via
the same nested-modal-driving technique already established for the K8055 control panel's tests.

Both steps deliberately narrowed the same way and defer the same items to Step 4 (not yet started,
see `docs/design/multi-session-ui.md`'s Open questions): closing the last tab is a no-op (can't reach
zero tabs yet); session logging and the Stream Monitor both stay single, window-level instances that
follow "whichever tab was active when started/opened," not yet one-per-tab.

## TUI legacy-conhost 16-color readability: Dark theme's focus highlight fixed

Closes the last remaining bullet from `TODO.md`'s "TUI layout review follow-ups (from 2026-09-25)"
section: "The startup editor looks unthemed in legacy conhost (16-color downgrade of the truecolor
theme: invisible field backgrounds, faint focus)."

Investigated from Terminal.Gui v2.5.0's actual source (not the earlier, explicitly-caveated starter
palette from an unpublished draft) before writing any fix. Confirmed two things:

1. A legacy Windows conhost session (no VT processing enabled on the console handle at process start)
   gets permanently forced into Terminal.Gui's 16-color mode for its whole lifetime, with no way back:
   `WindowsOutput`'s constructor checks `GetConsoleMode` once and sets `IsLegacyConsole`, whose setter
   forces `Force16Colors = true`; `Force16Colors`'s own setter then refuses `false` while
   `IsLegacyConsole` is true (`Drivers/WindowsDriver/WindowsOutput.cs`, `Drivers/Output/OutputBase.cs`).
2. Every truecolor value then renders as `Color.GetClosestNamedColor16()`'s nearest of the 16 named
   ANSI colors, by plain Euclidean RGB distance with no perceptual weighting
   (`Drawing/Color/Color.cs`).

Ran the Dark theme's actual role colors through that same public API
(`Terminal.Gui.Drawing.Color.GetClosestNamedColor16()`, not a reimplementation) and found the real
collision: `selectionBackground` (`#264F78`, a VS-Code-style dark blue used for the TUI's
Focus/Active/HotFocus states — the highlight a focused field gets) and `fieldBackground`/
`controlHoverBackground` (`#3C3C3C`/`#3A3D41`) all snap to the same nearest named color, "DarkGray".
`selectionForeground` and the normal `foreground` both snap to "White". So under the legacy-conhost
downgrade, a focused editable field renders with the *identical* background as a merely-editable,
unfocused one — exactly "faint focus".

Fixed by brightening `dark`'s `selectionBackground` from `#264F78` to `#2A66C2`: still a clearly
blue selection highlight in truecolor, but its nearest named color is "BrightBlue" instead of
"DarkGray" (Euclidean distance to BrightBlue's anchor is roughly a third of the distance to
DarkGray's, not a near-tie), and it still clears the 4.5:1 text contrast `ReadablePairs` requires
against `selectionForeground` (white) with real margin (~5.6:1). `BuiltInThemes.Dark`'s doc comment
now records the rationale and the fixed date so a future palette edit doesn't reopen this by feel.

Regression test: `DevTerm.Console.Tests.LegacyConsole16ColorTests` — calls the real
`Terminal.Gui.Drawing.Color.GetClosestNamedColor16()` (not a reimplementation, so it can't drift from
Terminal.Gui's actual behavior) and asserts the Dark theme's focused-field background no longer
collapses onto the unfocused-field or hover-field background, or onto the window background itself.
Full-suite regression check: `DevTerm.Configuration.Tests` (32/32, including the existing WCAG
contrast checks), `DevTerm.Console.Tests` Unit category (367/367), `DevTerm.Wpf.Tests` Unit category
(197/197, since `selectionBackground` is a shared `ThemeRole` also used by WPF's `DynamicResource`
bindings) — no regressions from the hex change. Full solution build: 0 warnings, 0 errors.

Not fixed here: `light`'s equivalent roles have a similar, worse collision under the same
downgrade — `background`/`fieldBackground`/`selectionBackground` *all three* land on "White", since
`light`'s field/selection colors are deliberately much closer to white than `dark`'s are to black.
Fixing it would mean darkening those colors enough to change `light`'s look in the WPF app too, for a
narrower real-world case (a legacy black-background console running the *light* theme, rather than
`dark`, dev-term's default). Moved to `BACKLOG.md`'s new "TUI theming" section rather than folded into
this fix.

`docs/design/theming.md`'s TUI section now documents the legacy-conhost mechanism itself (the
irreversible `Force16Colors` forcing, the Euclidean nearest-16-color snap) alongside the fix, so a
future theme change has the real mechanism to check against instead of guessing.

## TUI Connection Editor: fixed the lone button-shadow row on a scrolled form

Closes `TODO.md`'s "TUI layout review follow-ups" item: "A scrolled form can show a lone
button-shadow row at the viewport's top edge."

`ConfigureMode.cs`'s ~19 buttons (Load/Delete/Refresh, Export Selected/Export All/Delete Selected,
the transport pickers, Save Profile, Browse/Import/Export/Save As/Replace All, Connect/Quit) never
set `ShadowStyle = ShadowStyles.None`, unlike every other button-heavy TUI screen in the codebase
(`PlaybackMode.cs`, `ManifestEditorMode.cs`'s `ToolButton`, `ControlPanelMode.cs`) — see CLAUDE.md's
existing constraint on this: a shadowed button's shadow is drawn on the next row, over whatever
sibling is there. On this screen's scrollable form, that meant a button's opaque shadow row could
scroll to sit right at the viewport's top edge with the button itself scrolled out, i.e. exactly a
stray shadow-only row with nothing above it.

Fixed by adding `ShadowStyle = ShadowStyles.None` to every button in `ConfigureMode.cs`, matching the
established convention. Confirmed via `tests/DevTerm.Console.Tests/TuiConfigureLayoutTests.cs`
(28/28 passing, `EachTransport_ScrolledToTheBottom` covers the exact scrolled scenario) and by
regenerating and pixel-diffing the six affected `docs/user-guide/images/tui-configure-*.png`
screenshots with `scripts/image-diff/image_diff.py` — every diff is confined to each button's own
frame (its shadow glyphs disappearing), nothing else moved.

## `scripts/image-diff/`: per-image mask sidecars, plus a `render-masks` preview command

Reworked the screenshot pixel-diff tool built earlier today (see this file's session context) from a
single shared `masks.json` to one mask sidecar per image (`<image-stem>.mask.json`, co-located next

subcommand. `main()` now inserts `diff` explicitly whenever the first argument isn't already a known
subcommand or `-h`/`--help`.

## RFC 2217 client transport

Implements `BACKLOG.md`'s "RFC 2217 client" item: a new `Rfc2217Transport : ITransport`
(`DevTerm.Transports.Rfc2217`) connects to a remote serial port over the network (e.g. `ser2net`,
pyserial's `rfc2217_server.py`) — baud rate, parity, data/stop bits, DTR, RTS, all controlled over
plain TCP via Telnet's COM-PORT-OPTION subnegotiation (RFC 2217), rather than the raw-byte-only
pass-through `DevTerm.Transports.Tcp` already provides. Selectable the same way as every other
transport: `--transport rfc2217 --host <h> --port <p>` on the CLI, or `rfc2217` in the Connection
Editor (TUI/WPF).

**Core transport** (`Rfc2217Codec`, `Rfc2217TelnetReadStream`, `Rfc2217Transport`,
`Rfc2217TransportOptions`): pure Telnet IAC escape/unescape and COM-PORT-OPTION subnegotiation
encode/decode (server replies recognized via RFC 2217's `command + 100` server-offset convention),
a resumable framing state machine wrapping the TCP stream so control sequences split across reads
still resolve correctly and a read that only consumed control bytes never returns 0 (which would
look like EOF to `StreamToPipePump`), and the transport itself reusing
`DevTerm.Transports.Tcp`'s `ITcpConnectionSource`/`ITcpConnection` for the actual socket connect
rather than re-deriving that logic. `OpenAsync` negotiates COM-PORT-OPTION with a bounded timeout:
an explicit `WONT`/`DONT` is a hard failure (the peer doesn't speak RFC 2217 at all), silence/timeout
falls back to tolerant plain-data mode with `ComPortControlNegotiated = false` (some vendor bridges
forward bytes with no real COM-port control), and an explicit `WILL`/`DO` sends the
SET-BAUDRATE/DATASIZE/PARITY/STOPSIZE/CONTROL(DTR)/CONTROL(RTS) commands to configure the remote
port. Covered by `Rfc2217CodecTests`, `Rfc2217TelnetReadStreamTests`, and `Rfc2217TransportTests`
(41 tests total) against a fake server — **no run against a real RFC 2217 server yet**; see the new
Status section in `docs/design/rfc2217.md`.

**Configuration wiring**: `CliOptionsValidator` (host/port/baud/data-bits validation),
`ServiceCollectionExtensions` (DI registration + options binding from `CliOptions`),
`ConnectionDescription` (both the detailed and compact connection-description strings),
`ConnectionErrorMessages` (a vendor-variant-aware hint instead of reusing serial's CTS hint, which
doesn't apply to a TCP-backed transport), `Program.cs`'s usage text, and
`ManifestEditorForms.TransportTypes`. `ConnectionEditorViewModel` adds `rfc2217` to
`TransportOptions` and retargets the Serial/TCP `[FormSection(VisibleWhen=...)]` attributes from
`IsSerialTransport`/`IsTcpTransport` to new `IsSerialLikeTransport`/`IsTcpLikeTransport` properties
(`... || IsTransport("rfc2217")`), so `rfc2217` reuses both existing field groups instead of adding
a third, mostly-duplicate one — "a serial port, reached over the network." Three fields
(Listen/Handshake text/Read timeout (ms)) get their own narrower field-level `VisibleWhen` so they
stay hidden under `rfc2217` even though their section is now shown for it too.

**Tests**: new parallel `rfc2217` cases in `CliOptionsValidatorTests`/`ServiceCollectionExtensionsTests`.
While re-verifying the whole solution's Unit suite after this work, found and fixed two
pre-existing, unrelated stale assertions in `ConnectionEditorFormTests` (left behind by an earlier
session's `ConnectionEditorViewModel`/`CliOptions` edits never having been propagated to this test
file) — not a regression introduced by this change, but caught by the same full-suite run.

**Docs**: `docs/design/rfc2217.md` (new Status section, client mode marked implemented),
`docs/design/README.md` (one-line summary), `docs/specs/connection-editor.md` (Fields table + States
section describing the shared-group visibility), `docs/user-guide/connecting.md` (CLI example +
Connection Editor note), `BACKLOG.md` (removed the now-done client bullet; server bullet stays, out
of scope here).

Verified: `dotnet build` (whole solution, 0 warnings/errors) and

## Fixed bug 062: WPF SendBox Up/Down history recall stops working after clicking "Send"

User report: "the up/down keys do not always work on the send message combo box." Root cause:
clicking the "Send" button (a plain focusable `Control`, no `Focusable="False"` override) moves WPF
keyboard focus to that button — standard framework behavior for any focusable control clicked with
the mouse — and nothing in `MainWindow.xaml.cs` ever returned focus to `SendBox` afterward (the only
existing `SendBox.Focus()` call was in `ConnectAsync`, after a successful connect). `SendBox`'s
Up/Down history recall is wired to `SendBox_PreviewKeyDown`, which only tunnels through `SendBox`'s
own ancestor chain — once focus moves elsewhere, Up/Down presses never reach it. Pressing Enter in
the box instead of clicking Send never triggers this (Enter doesn't move focus), which is why the
bug was intermittent rather than constant.

Fixed by wrapping `MainWindow.SendCurrentInputAsync`'s body in a `try`/`finally` with
`SendBox.Focus()` in `finally`, so focus returns to the send box after every exit path (empty input,
a rejected parse, not connected, a successful send, a send that throws). Two new regression tests in
`MainWindowSendBoxFocusTests` simulate the Send-button click's focus side effect
(`Keyboard.Focus(ParserBox)`) and assert focus returns to `SendBox` after `SendCurrentInputAsync`.
Along the way, found and documented a new WPF gotcha (now in CLAUDE.md's constraints list): an
editable `ComboBox`'s `IsKeyboardFocused` stays `false` even right after a successful `Focus()`
call, since WPF delegates actual keyboard focus to the control's internal text-box part — the tests
assert `IsKeyboardFocusWithin` instead.

Full bug report: `docs/bugs/fixed/062-sendbox-arrow-keys-lose-focus-after-send.md`. Verified:
`dotnet build` (0 warnings/errors) and `dotnet test tests/DevTerm.Wpf.Tests` (210/210, 2 skipped
real-hardware cases, no regressions).
