# 2026-09-30

## TUI legacy-conhost 16-color readability: Dark theme's focus highlight fixed

Closes the last remaining bullet from `TODO.md`'s "TUI layout review follow-ups (from 2026-09-25)"
section: "The startup editor looks unthemed in legacy conhost (16-color downgrade of the truecolor
theme: invisible field backgrounds, faint focus)."

Investigated from Terminal.Gui v2.5.0's actual source (not the earlier, explicitly-caveated starter
palette from an unpublished draft) before writing any fix. Confirmed two things:

1. A legacy Windows conhost session (no VT processing enabled on the console handle at process start)
   gets permanently forced into Terminal.Gui's 16-color mode for its whole lifetime, with no way back:
   `WindowsOutput`'s constructor checks `GetConsoleMode` once and sets `IsLegacyConsole`, whose setter
   forces `Force16Colors = true`; `Force16Colors`'s own setter then refuses `false` while
   `IsLegacyConsole` is true (`Drivers/WindowsDriver/WindowsOutput.cs`, `Drivers/Output/OutputBase.cs`).
2. Every truecolor value then renders as `Color.GetClosestNamedColor16()`'s nearest of the 16 named
   ANSI colors, by plain Euclidean RGB distance with no perceptual weighting
   (`Drawing/Color/Color.cs`).

Ran the Dark theme's actual role colors through that same public API
(`Terminal.Gui.Drawing.Color.GetClosestNamedColor16()`, not a reimplementation) and found the real
collision: `selectionBackground` (`#264F78`, a VS-Code-style dark blue used for the TUI's
Focus/Active/HotFocus states — the highlight a focused field gets) and `fieldBackground`/
`controlHoverBackground` (`#3C3C3C`/`#3A3D41`) all snap to the same nearest named color, "DarkGray".
`selectionForeground` and the normal `foreground` both snap to "White". So under the legacy-conhost
downgrade, a focused editable field renders with the *identical* background as a merely-editable,
unfocused one — exactly "faint focus".

Fixed by brightening `dark`'s `selectionBackground` from `#264F78` to `#2A66C2`: still a clearly
blue selection highlight in truecolor, but its nearest named color is "BrightBlue" instead of
"DarkGray" (Euclidean distance to BrightBlue's anchor is roughly a third of the distance to
DarkGray's, not a near-tie), and it still clears the 4.5:1 text contrast `ReadablePairs` requires
against `selectionForeground` (white) with real margin (~5.6:1). `BuiltInThemes.Dark`'s doc comment
now records the rationale and the fixed date so a future palette edit doesn't reopen this by feel.

Regression test: `DevTerm.Console.Tests.LegacyConsole16ColorTests` — calls the real
`Terminal.Gui.Drawing.Color.GetClosestNamedColor16()` (not a reimplementation, so it can't drift from
Terminal.Gui's actual behavior) and asserts the Dark theme's focused-field background no longer
collapses onto the unfocused-field or hover-field background, or onto the window background itself.
Full-suite regression check: `DevTerm.Configuration.Tests` (32/32, including the existing WCAG
contrast checks), `DevTerm.Console.Tests` Unit category (367/367), `DevTerm.Wpf.Tests` Unit category
(197/197, since `selectionBackground` is a shared `ThemeRole` also used by WPF's `DynamicResource`
bindings) — no regressions from the hex change. Full solution build: 0 warnings, 0 errors.

Not fixed here: `light`'s equivalent roles have a similar, worse collision under the same
downgrade — `background`/`fieldBackground`/`selectionBackground` *all three* land on "White", since
`light`'s field/selection colors are deliberately much closer to white than `dark`'s are to black.
Fixing it would mean darkening those colors enough to change `light`'s look in the WPF app too, for a
narrower real-world case (a legacy black-background console running the *light* theme, rather than
`dark`, dev-term's default). Moved to `BACKLOG.md`'s new "TUI theming" section rather than folded into
this fix.

`docs/design/theming.md`'s TUI section now documents the legacy-conhost mechanism itself (the
irreversible `Force16Colors` forcing, the Euclidean nearest-16-color snap) alongside the fix, so a
future theme change has the real mechanism to check against instead of guessing.
