# 2026-10-03

## Plugin loading

`DevTerm.Core.Plugins` adds `IPluginModule`, a `plugin.json` manifest (name, version, contract, assembly) and
`PluginLoader`, which loads each `<plugins>/<name>/` folder into its own `AssemblyLoadContext` (never a second copy of an
assembly the host already has, so the plugin's `IPresenter` is the host's) and lets the module register services. A bad
manifest, another contract version, an assembly outside the folder or a module that throws is skipped and reported, with
that module's registrations staged so nothing half-registered leaks. `--plugins <folder>` (`CliOptions.Plugins`; default a
`plugins` folder next to the app) is loaded from `AddDevTermPresenters`; the console prints skips to stderr.
`src/DevTerm.Plugins.Sample` is the template and test fixture. Tests: `PluginLoaderTests` (5). Checked end to end:
`dotnet run ... --transport loopback --presenter sample --plugins <folder>` rendered `sample: 20 bytes`. The loaded DLL
stays locked until exit (the context isn't collectible). Not done: moving the built-in decoders into plugin folders,
unloading, trust/signing, a loaded-plugins view in the TUI/WPF. Design: `docs/design/plugin-model.md`.

## LXI discovery (phase 1)

`DevTerm.Transports.Tcp.LxiDiscovery` finds LAN instruments by broadcasting an ONC-RPC portmapper `GETPORT` for the VXI-11 core
program to UDP 111 on each up IPv4 interface, keeping hosts that answer with a non-zero port, then probing 5025 and 5555 with
`*IDN?`. mDNS `_lxi._tcp` was tried against the real DG1062Z first and got no answer, so it isn't used. Real run:
`--listlxidevices true` -> `192.168.0.87:5555  Rigol Technologies,DG1062Z,DG1ZA232603118,03.01.12`; a second host (192.168.0.67)
whose portmapper replied port 0 was correctly ignored. Surfaces: `--listlxidevices`, `LxiDeviceScanner`/`LxiDeviceOption`,
`ConnectionEditorViewModel.SelectedLxiDevice` (fills Host and `TcpPort`, not the serial Port), a "Detect LXI..." button in the
TUI and WPF editors. Tests: `LxiDiscoveryTests` (4, including the captured DG1062Z reply) and a view-model test. Phase 2 (VXI-11
client) and a formal `docs/test/` pass remain. Proposal: `docs/design/proposals/lxi-support.md`.

## AMQP and STOMP transports

New `DevTerm.Transports.Brokers` (one project, `--transport amqp|stomp`), built from the MQTT transport: `BrokerTransport` over an `IBrokerConnection` (connect, subscribe, publish), each inbound message one `address<TAB>payload` line. `AmqpConnection` uses RabbitMQ.Client 7.2.2 (0-9-1; a private exclusive auto-delete queue bound to `amq.topic` per subscription). `StompConnection` is a hand-written STOMP 1.2 client over TCP with a pure `StompFrame` encoder/parser (header escaping, `content-length`, heart-beat newlines, CONNECT unescaped). Reuses `--subscribe`/`--publish`/`--username`/`--password`; wired through the validator, description, error hints, profile save, DI, the Connection Editor (shares the MQTT field group) and the manifest transport list.

Verified against the Docker RabbitMQ (`containers/`): Integration tests for both protocols plus a wrong-password STOMP failure, and a CLI round trip each. One real catch: RabbitMQ reads STOMP's `host` header as the virtual host, so the client sends `/` unless one is configured (sending the machine name gave "Bad CONNECT"). Git Bash also rewrites `--subscribe /topic/x` into a Windows path; set `MSYS_NO_PATHCONV=1` when running STOMP examples from it. Tests: `StompFrameTests`, `BrokerTransportTests`, `RabbitMqIntegrationTests`, plus validator cases. Not built: TLS, STOMP heart-beats/acks, AMQP 1.0.

## One Stream Monitor for every session; HP-GL no longer split

- **The Stream Monitor watches all open sessions.** `StreamMonitor` now tracks any number of sessions
  (`Track(key, session, deviceName, exportDirectory)` / `Untrack(key)`; `SetSession` stays as the
  single-session shorthand). TUI and WPF each hold one window-level monitor instead of one per tab; tabs opened
  or closed while it runs are tracked/untracked, a profile switch re-points that tab, and each capture's status
  line goes to the tab it came from (`StreamMonitorCapture.Source`). The state line lists every device; the folder
  line adds "(+N more)" when tabs export to different folders. Tests: `StreamMonitorTests` (two sessions, track
  while running/untrack, start/stop all). This reverses multi-session-ui.md Step 4's per-tab monitor.
- **HP-GL from the .108 at 4800 baud was one plot cut into several files.** The saved pieces broke mid-command
  (`...PD648,4` / `32;PU684,...`): the 2 s idle timer fired during a stall. HP-GL now ends at its own pen-stow
  `SP0;` (anything after, like `READY;`, is not part of it), and an HP-GL capture without it waits
  `HpglIdleTimeout` (10 s, never shorter than the general idle) before being cut. The general idle is
  configurable per profile/CLI as `StreamIdleTimeoutMs` (default 2000). Tests in `StreamContentWatcherTests`.
  Not verified against the .108 itself yet.
- **TDS2024 hardcopy leftover (text presenter kept the image's tail).** The user's `.scratchpad/tds2024_mw_bmptest.png`
  showed two extra lines of image bytes (`SSSS...` after the "Captured" line, `QQQ...` glued onto the next `*IDN?`
  reply). The session log (`~/.dev-term/logs/20261003-100604_...jsonl`) shows the BMP is exactly the 77,878 bytes its
  header declares (320x240, 8bpp: 54 + 1,024 palette + 76,800) and nothing but the next `*IDN?` reply follows, so
  the bytes were the scpi/ASCII presenter's line buffer: it saw the image as text and flushed its unterminated tail
  later. `Pipeline.Render` now runs content-capturing presenters first (`IContentCapturePresenter`, implemented by
  `StreamContentWatcher`) and withholds a chunk from every other presenter while a capture is in progress or ends
  in it. Trade-off: text arriving in the very read that finishes a capture is withheld too. Tests:
  `PipelineTests.Render_WithholdsCapturedContentFromTextPresenters_...`; the existing live-session watcher test now
  expects other presenters to see the text before the image but not the image. Two Console tests that relied on the
  HP-GL sample having no end marker now drop its trailing `SP0;`. Not yet re-checked on the real TDS2024.
- **PCX support (TDS2024 `HARDCopy:FORMAT PCX`).** `.scratchpad/tds2024_mw_pcxtest.png` showed a PCX hard copy
  printed as text and never captured: PCX wasn't a known kind. The session log
  (`~/.dev-term/logs/20261003-101724_...jsonl`) is a 128-byte header (v5, RLE, 8bpp, window 0,0-319,239, 320
  bytes/line), 9,287 bytes of run-length scanlines, then `0x0C` and a 768-byte palette, 10,184 bytes in all, followed
  only by the next `*IDN?` reply. Added `StreamContentKind.Pcx` (`.pcx`), a header-plausibility sniffer
  (0x0A is also LF, so version/encoding/bpp/window/reserved byte are all checked), and `PcxEndFinder`, which decodes
  the runs until the declared bytes are produced and then expects the palette. WPF can't decode PCX, so it isn't a
  "native image": the Stream Monitor saves it and a configured converter (ImageMagick) can turn it into a PNG. Tests:
  the PCX sample in the sniffer and end-finder tables. Not yet re-run on the real scope.
- **PCL raster hard copy (TDS2024 `HARDCopy:FORMat LASERJet`).** `.scratchpad/tds2024_mw_laserjet_test.png` showed the
  job printed as hundreds of `*b115W` lines. The log (`~/.dev-term/logs/20261003-101925_...jsonl`) is
  `ESC&l0O ESC*t150R ESC*r0A`, a run of `ESC*b<n>W` rows, then `ESC*rB ESC&l0H ESC E`, followed by the next `*IDN?`
  reply. The sniffer now treats `ESC&l<n>O` or `ESC*t<n>R` followed by another escape as a PCL job start, and
  `PclEndFinder` ends a job that isn't UEL-wrapped at `ESC*rB`/`ESC*rC`, plus any form feed (`ESC&l<n>H`/FF) and
  reset (`ESC E`) that follows. Saved as `.pcl`; no preview (needs a PCL raster decoder). Tests: `PclRaster` sample in
  the sniffer and end-finder tables. Not yet re-run on the real scope.
