## Plugin loading

`DevTerm.Core.Plugins` adds `IPluginModule`, a `plugin.json` manifest (name, version, contract, assembly) and
`PluginLoader`, which loads each `<plugins>/<name>/` folder into its own `AssemblyLoadContext` (never a second copy of an
assembly the host already has, so the plugin's `IPresenter` is the host's) and lets the module register services. A bad
manifest, another contract version, an assembly outside the folder or a module that throws is skipped and reported, with
that module's registrations staged so nothing half-registered leaks. `--plugins <folder>` (`CliOptions.Plugins`; default a
`plugins` folder next to the app) is loaded from `AddDevTermPresenters`; the console prints skips to stderr.
`src/DevTerm.Plugins.Sample` is the template and test fixture. Tests: `PluginLoaderTests` (5). Checked end to end:
`dotnet run ... --transport loopback --presenter sample --plugins <folder>` rendered `sample: 20 bytes`. The loaded DLL
stays locked until exit (the context isn't collectible). Not done: moving the built-in decoders into plugin folders,
unloading, trust/signing, a loaded-plugins view in the TUI/WPF. Design: `docs/design/plugin-model.md`.
