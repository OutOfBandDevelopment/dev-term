# 2026-10-03

## Plugin loading

`DevTerm.Core.Plugins` adds `IPluginModule`, a `plugin.json` manifest (name, version, contract, assembly) and
`PluginLoader`, which loads each `<plugins>/<name>/` folder into its own `AssemblyLoadContext` (never a second copy of an
assembly the host already has, so the plugin's `IPresenter` is the host's) and lets the module register services. A bad
manifest, another contract version, an assembly outside the folder or a module that throws is skipped and reported, with
that module's registrations staged so nothing half-registered leaks. `--plugins <folder>` (`CliOptions.Plugins`; default a
`plugins` folder next to the app) is loaded from `AddDevTermPresenters`; the console prints skips to stderr.
`src/DevTerm.Plugins.Sample` is the template and test fixture. Tests: `PluginLoaderTests` (5). Checked end to end:
`dotnet run ... --transport loopback --presenter sample --plugins <folder>` rendered `sample: 20 bytes`. The loaded DLL
stays locked until exit (the context isn't collectible). Not done: moving the built-in decoders into plugin folders,
unloading, trust/signing, a loaded-plugins view in the TUI/WPF. Design: `docs/design/plugin-model.md`.

## LXI discovery (phase 1)

`DevTerm.Transports.Tcp.LxiDiscovery` finds LAN instruments by broadcasting an ONC-RPC portmapper `GETPORT` for the VXI-11 core
program to UDP 111 on each up IPv4 interface, keeping hosts that answer with a non-zero port, then probing 5025 and 5555 with
`*IDN?`. mDNS `_lxi._tcp` was tried against the real DG1062Z first and got no answer, so it isn't used. Real run:
`--listlxidevices true` -> `192.168.0.87:5555  Rigol Technologies,DG1062Z,DG1ZA232603118,03.01.12`; a second host (192.168.0.67)
whose portmapper replied port 0 was correctly ignored. Surfaces: `--listlxidevices`, `LxiDeviceScanner`/`LxiDeviceOption`,
`ConnectionEditorViewModel.SelectedLxiDevice` (fills Host and `TcpPort`, not the serial Port), a "Detect LXI..." button in the
TUI and WPF editors. Tests: `LxiDiscoveryTests` (4, including the captured DG1062Z reply) and a view-model test. Phase 2 (VXI-11
client) and a formal `docs/test/` pass remain. Proposal: `docs/design/proposals/lxi-support.md`.

## Manifest editor: frame length and checksum forms

The Frame form now edits `LengthField`, `LengthAdjust` and `Checksum` (kind, start, byte order) instead of leaving them JSON-only.
Length adjust shows only with a length field, checksum start/byte order only with a checksum (byte order only for 16-bit kinds);
"none" clears the checksum. Test: `ManifestEditorTests.FrameForm_LengthAndChecksumFields_WriteThroughToTheSchema`. Spec: `docs/specs/manifest-editor.md`.

`TelemetryExporter` sets the OTLP metric reader interval to 10 s (the SDK default is 60 s, so a short interactive session exported nothing until exit). Not yet viewed in the Aspire dashboard.

## Web host: read-only viewers and a control panel

`Web:ReadOnlyToken` admits viewers who can watch but not send: `AccessTokenMiddleware` flags the request, the `/ws` tunnel answers `! read-only viewer` instead of sending, and `POST /api/invoke` returns 403. `Web:Panel` (`k8055`/`busylight`) serves the device's `UiDefinition` at `/api/panel` and the page renders it generically, invoking `IControlSurface` through `/api/invoke`. Chose JSON plus a small script over a Blazor circuit (no Razor/SignalR for this). `AccessPolicy.Validate` rejects an equal read-only token or an unknown panel. 6 new tests in `WebRolesTests`, including an https round trip with a generated self-signed certificate; the 19 web tests pass. Not verified: a CA-issued certificate, a real device through the page, a real browser.

## AMQP and STOMP transports

New `DevTerm.Transports.Brokers` (one project, `--transport amqp|stomp`), built from the MQTT transport: `BrokerTransport` over an `IBrokerConnection` (connect, subscribe, publish), each inbound message one `address<TAB>payload` line. `AmqpConnection` uses RabbitMQ.Client 7.2.2 (0-9-1; a private exclusive auto-delete queue bound to `amq.topic` per subscription). `StompConnection` is a hand-written STOMP 1.2 client over TCP with a pure `StompFrame` encoder/parser (header escaping, `content-length`, heart-beat newlines, CONNECT unescaped). Reuses `--subscribe`/`--publish`/`--username`/`--password`; wired through the validator, description, error hints, profile save, DI, the Connection Editor (shares the MQTT field group) and the manifest transport list.

Verified against the Docker RabbitMQ (`containers/`): Integration tests for both protocols plus a wrong-password STOMP failure, and a CLI round trip each. One real catch: RabbitMQ reads STOMP's `host` header as the virtual host, so the client sends `/` unless one is configured (sending the machine name gave "Bad CONNECT"). Git Bash also rewrites `--subscribe /topic/x` into a Windows path; set `MSYS_NO_PATHCONV=1` when running STOMP examples from it. Tests: `StompFrameTests`, `BrokerTransportTests`, `RabbitMqIntegrationTests`, plus validator cases. Not built: TLS, STOMP heart-beats/acks, AMQP 1.0.
