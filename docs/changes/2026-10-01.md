## TCP software flow control is now a live, runtime-settable toggle

`TcpTransportOptions.SoftwareFlowControl` previously only set XON/XOFF stripping/write-pausing at
construction time. It's now also a live property, `TcpTransport.SoftwareFlowControl`, backed by a
new `XonXoffFlowControlGate` (pause/resume state, written by `XonXoffReadStream` as it scans inbound
bytes, read by `WriteAsync` before every write) — a front end can flip it on or off without
reconnecting, since a serial-to-Ethernet bridge's actual XON/XOFF behavior often can't be confirmed
until a connection is already open. Disabling it releases any write currently paused on a stale
XOFF rather than leaving it stuck. `Session` grew a `Transport` property so front ends can reach a
transport's own capabilities (here, via a `TcpTransport` pattern match) without the session itself
knowing about transport-specific features. See `docs/design/transports.md`'s TCP section.

## WPF and TUI: View > Echo Sent Commands, Software Flow Control, Clear Output

Both front ends' View menu gained three items alongside Theme:

- **Echo Sent Commands** — appends `Out> {line}` to the active tab's output right after a typed
  line is successfully encoded, before it's actually sent. A window-level toggle, off by default.
- **Software Flow Control (XON/XOFF)** — a checkable item wired to the new
  `TcpTransport.SoftwareFlowControl` toggle above (see that section). Enabled/checked only when the
  active tab's `Session.Transport` is a `TcpTransport`, re-synced by each front end's
  `RefreshConnectionUi` on every tab switch, profile switch, and connect/disconnect, since the
  setting lives per-transport-instance.
- **Clear Output** — empties the active tab's output pane/list; other tabs are untouched.

The TUI's `_View` menu was restructured to hold these as four sibling items (`_Theme`, Echo Sent
Commands, Software Flow Control, Clear Output) instead of `_Theme` owning the whole top-level menu;
`TuiThemeMenu` now exposes just its `MenuItem` (`ThemeMenuItem`) rather than the whole
`MenuBarItem`. Both front ends' marker convention (`●`/blank prefix for the TUI, `IsCheckable` for
WPF) and `RefreshConnectionUi` gating already existed for Theme and Device menu items respectively;
this reuses both rather than inventing new patterns. See `docs/specs/tui-main-screen.md` and
`docs/specs/wpf-main-window.md`.

"TestCategory=Unit"` (all projects green, including `DevTerm.Console.Tests` 372/372 and
`DevTerm.Wpf.Tests` 203/203). Not yet verified: a live manual run against a real or loopback TCP

**Addendum**: Echo Sent Commands' `{line}` now shows the full text of what was actually sent, not
just the typed line — the appended line ending's own bytes are included, and every non-printable

`TypedInputEchoTests`. See `docs/specs/tui-main-screen.md`, `docs/specs/wpf-main-window.md`, and
`docs/user-guide/sending-and-receiving.md`.

## Write pacing (inter-byte delay) for Serial, TCP, and RFC 2217

New `WriteDelayStream` (`DevTerm.Core.Transports`) — a write-only `Stream` decorator for slow
devices without FIFO buffers that can't absorb a burst write. Writes one byte at a time with an
explicit `FlushAsync` after each, delaying `WriteByteDelayMs` milliseconds between bytes (never
after the last one). Three-way sentinel: `-1` (default) disables pacing entirely — an unpaced write,
exactly as before; `0` paces with no delay (still one write-and-flush per byte); a positive value
adds that many milliseconds between bytes. Write-only — has no effect on how a transport reads.

`WriteByteDelayMs` was added to `SerialTransportOptions`, `TcpTransportOptions`, and
`Rfc2217TransportOptions` — the three transports whose write path is a single stream
`WriteDelayStream` can wrap; not offered for HID/USBTMC (one atomic device-framed report/message per
write call — splitting it would break framing, not pace it) or BLE/Loopback. Wired through
`CliOptions.WriteByteDelayMs` (`--writebytedelayms`), `CliOptionsValidator` (must be -1 or greater),
and `ServiceCollectionExtensions.AddDevTermFrontEnd`.

`ConnectionEditorViewModel` grew a new "Timing" form section (`SupportsWriteByteDelay =
IsSerialTransport || IsTcpTransport || IsRfc2217Transport`) holding the one field, shown in both
front ends alongside Serial/TCP/RFC 2217's own groups rather than nested inside any one of them,
since the field applies across all three.

See `docs/design/transports.md`'s new "Write pacing" section, `docs/specs/connection-editor.md`'s
Fields/States entries, and `docs/user-guide/connecting.md`'s Connection Editor walkthrough.

## Manifest editor expression builder

Per `docs/design/proposals/manifest-editor-expression-builder.md` (sourced from `BACKLOG.md`'s
"Proposed Ideas" section, added 2026-09-30). A device manifest's display controls and button
parameters previously bound a raw decoder value or sibling field value verbatim; they can now derive
one instead.

New `Expression` (`DevTerm.UiDefinitions`) — a hand-rolled recursive-descent parser/evaluator: numeric
literals, `{id}` variable refs, `+ - * /`, unary `-`/`+`, parens, `round(x[,n])`, `min`/`max`
(variadic), `abs(x)`, comparisons, `&&`/`||` (short-circuiting), `if(cond,a,b)`. `Parse`/`TryParse` can
fail; `Evaluate` never throws. `IndicatorControl.Expression` and `ChartChannel.Expression` (the fourth,
optional `id:label:color:expression` segment, which is why chart channels are semicolon- not
comma-separated — an expression can itself contain commas) drive live display via `IndicatorState`
and `BarGraphState`/`StripChartState` (`LiveDisplayState.cs`), evaluated against the live
published-values dictionary. `ButtonControl.ParameterExpressions` (semicolon-separated, positionally
parallel to `ParameterFieldIds`) drives outbound parameter composition instead, evaluated per field
against every sibling control's current numeric value (a new `SiblingValues()` helper in both front
ends) — a non-blank, successfully-parsed entry replaces that field's raw value at send time; blank
keeps it as-is.

`DeviceManifestValidator` parses every expression-bearing property at load and reports every failure
(never silently ignored, matching `ValueConstraint`'s convention); at runtime a bad/unresolvable
expression never throws — an indicator's `Text` just stays null until its referenced id arrives, and a
chart channel without a resolvable expression falls back to reading its own id directly.

Wired into the manifest editor's form (`ControlForm.ParameterExpressions`/`IndicatorExpression`/
`Channels`) and both front ends' live control panel (`ControlPanelMode.cs`'s
`IndicatorStates`/`TryReadParameters`, `ControlPanelWindow.xaml.cs`'s mirror), plus the manifest
editor's own live preview (same panel-building path). See `docs/specs/manifest-editor.md`'s Fields
table and `docs/user-guide/manifest-editor.md`.

Verified: whole-solution `dotnet build` (0 warnings/errors) and `dotnet test --filter
"TestCategory=Unit"` — every project green, including the newly-added `ExpressionTests`,
`IndicatorStateTests`, `ChartControlsTests` (`DevTerm.UiDefinitions.Tests`), `DeviceManifestTests`/
`ManifestEditorTests` (`DevTerm.DeviceManifests.Tests`), and TUI/WPF wiring tests in
`ControlPanelModeTests`/`ControlPanelWindowTests`. Not yet verified against real hardware — this is a
pure UI/manifest-model feature with no device-side behavior to exercise, so that gap is expected
rather than a coverage hole.

## Theme builder: in-app theme creation/editing (View > Theme > Build/Edit Theme...)

Per `docs/design/proposals/theme-builder.md` (sourced from `BACKLOG.md`'s "Proposed Ideas"
section). Creating a `ThemeFile` previously meant hand-writing JSON with no live preview; both front
ends now have a builder screen that edits a `DevTermTheme` directly, with the whole app re-skinning
live on every change.

Shared model (`DevTerm.Configuration`): `ThemeFile.Save` (the inverse of `Parse`'s `colors`

## Loopback sample rate control

Per `docs/design/proposals/loopback-sample-rate.md` (sourced from `BACKLOG.md`'s "Proposed Ideas"
section, added 2026-09-30). The Loopback transport previously pushed every line of a scripted
response back-to-back with no delay, so a streaming reply (`Samples: N`, `Send Events: N`) arrived
all at once instead of at a believable device cadence.

`LoopbackTransportOptions.SampleIntervalMs` (default `0`, preserving today's instant delivery) is
now the extension point that doc already anticipated. `LoopbackRule` gained a `Streaming` flag (set
on the `Samples:`/`Send Events:` rules in `LoopbackScript.Default()`); `LoopbackTransport.WriteAsync`
awaits `Task.Delay(SampleIntervalMs, cancellationToken)` between each pushed line of a streaming
rule's response — never before the first line, never after the last, and never for a single-line
reply like `hello`.

Wired through the full Configuration stack: `CliOptions.LoopbackSampleIntervalMs`
(`--loopbacksampleintervalms`) → `CliOptionsValidator` (must be 0 or greater) →
`ServiceCollectionExtensions.AddDevTermFrontEnd` (configures `IOptions<LoopbackTransportOptions>`) →
`ConnectionEditorViewModel`'s existing "Loopback" form section (a new "Sample interval (ms)" numeric
field) → `DevTermConfiguration.ToProfileJson` (persisted only when non-zero) →
`ConnectionDescription.For()` (`Loopback (N ms/sample)` in the status bar/window title when set).

Also fixed a pre-existing gap found while wiring profile persistence: `ToProfileJson` had no
`loopback` branch at all, so a saved Loopback profile silently fell into the catch-all serial branch
and persisted irrelevant serial-only fields (Baud, DataBits, Parity, ...) into its JSON. It now has
its own branch.

See `docs/design/proposals/loopback-sample-rate.md` (Status flipped to Implemented, with a
`@startuml` sequence diagram), `docs/design/README.md`'s one-line summary,
`docs/specs/connection-editor.md`'s Fields table, and `docs/user-guide/connecting.md`'s Loopback
walkthrough. The "Loopback sample rate control" bullet is removed from `BACKLOG.md`'s "Proposed
Ideas" section.

Verified: whole-solution `dotnet build` (0 warnings/errors) and `dotnet test --filter
"TestCategory=Unit"` — every project green, including `DevTerm.Transports.Loopback.Tests` (17/17)
and `DevTerm.Configuration.Tests` (403/403). Not yet verified against real hardware — the Loopback
transport has none by design; this is a pure in-process scripted-device feature.

## Stream Monitor raster/convert tool integration

Per `docs/design/proposals/stream-content-detection.md`'s "Raster/convert tool integration" section
(proposed 2026-09-30). The Stream Monitor could capture and auto-save an HP-GL/image/PostScript/PCL
reply but had no way to convert one to something else; both front ends' Stream Monitor windows now
have a "Convert..." action next to Start/Stop Monitoring.

New `DevTerm.Configuration.StreamCaptureConverter` wraps the proposal's three mechanisms behind one
`ConvertAsync(StreamMonitorCapture)` call, picked by a single `StreamConversionMode` (offered as
alternatives, never all three at once): external tool invocation (`System.Diagnostics.Process`,
`UseShellExecute = false`), web-service conversion (`IHttpClientFactory`, optional — falls back to
an owned, per-call `HttpClient` when constructed outside DI, the same accommodation `StreamMonitor`
itself needs for ad-hoc TUI/WPF construction), and the already-built, unmodified
`HpglToSvgConverter.ConvertToSvg` for HP-GL captures. Never throws — every failure path (nothing
configured, a never-saved capture, a process that won't start or exits non-zero, a failed HTTP
request) returns a `StreamConversionResult(Success, OutputPath, Error)`, matching `StreamMonitor`'s
own tolerant, result-object file-I/O convention. The converted file always lands next to the
capture's own saved file (same folder and name stem), never a separately configured output
directory.

The external-tool argument template is split on whitespace *before* `{input}`/`{output}`/`{dpi}`
substitution, with each resulting token added individually to `ProcessStartInfo.ArgumentList` —
never a shell-parsed command string — so a substituted path containing spaces (or a device-supplied
value) can't break out of its argument boundary.

Seven new `CliOptions` properties (`StreamConvertMode`, `StreamConvertExternalToolPath`,
`StreamConvertExternalToolArguments`, `StreamConvertDpi`, `StreamConvertWebServiceUrl`,
`StreamConvertWebServiceMethod`, `StreamConvertOutputExtension`), all `[Category("Stream Monitor")]`,
carried per-connection-profile like every other `CliOptions` setting and automatically surfaced as a
new "Stream Monitor" section in the Connection Editor's generated form
(`FormDefinitionGenerator.Generate<CliOptions>()`) in both front ends — `ConnectionEditorFormTests`'
section-list assertion updated to match. Bound via `StreamCaptureConverterOptions.FromCliOptions`/
`CopyFrom`: the ad-hoc path for TUI/WPF's own `StreamMonitorMode.BuildWindow`/`StreamMonitorWindow`
construction (which don't go through DI), and `ServiceCollectionExtensions.AddDevTermFrontEnd`'s
`IOptions<StreamCaptureConverterOptions>` registration for DI.

Both front ends' Stream Monitor windows gained a "Convert..." button beside Start/Stop Monitoring,
enabled only when a capture is selected: `StreamMonitorMode`'s button reports "Converting..." then
the result in the detail label (TUI); `StreamMonitorWindow`'s `ConvertSelectedAsync` (internal,
directly callable from tests) reports success in the detail text and failure via `MessageBox.Show`
(matching the existing, already-untested `ExportAs_Click` failure-path convention — a real modal,
deliberately left untested, per CLAUDE.md's WPF-modal-testing note).

Not built this pass: live preview of the converted output in either window (the file is written but
not shown — still gated on the HP-GL/PostScript/PCL rendering presenter from `presenters.md` §3), and
no CLI-mode conversion command (Stream Monitor still has no CLI-mode support at all, unchanged by
this work). See `docs/design/proposals/stream-content-detection.md`'s updated Status section,
`docs/design/README.md`'s one-line summary, `docs/specs/stream-monitor.md`'s new Convert... row and
"Converting a capture" section, and `docs/user-guide/stream-monitor.md`'s new walkthrough section.
The "Stream monitor raster tool integration" bullet is removed from `BACKLOG.md`'s "Proposed Ideas"
section.

Verified: whole-solution `dotnet build` (0 warnings/errors) and `dotnet test --filter
"TestCategory=Unit"` — every project green, including the new `StreamCaptureConverterTests` (23
tests covering all three mechanisms, placeholder-substitution safety, a fake-`HttpMessageHandler`-
backed web-service round trip, and failure paths) and the new TUI/WPF wiring tests in
`StreamMonitorModeTests`/`StreamMonitorWindowTests`. Not yet verified against real hardware, a real
external tool (Ghostscript), or a real web conversion service.
