## TCP software flow control is now a live, runtime-settable toggle

`TcpTransportOptions.SoftwareFlowControl` previously only set XON/XOFF stripping/write-pausing at
construction time. It's now also a live property, `TcpTransport.SoftwareFlowControl`, backed by a
new `XonXoffFlowControlGate` (pause/resume state, written by `XonXoffReadStream` as it scans inbound
bytes, read by `WriteAsync` before every write) — a front end can flip it on or off without
reconnecting, since a serial-to-Ethernet bridge's actual XON/XOFF behavior often can't be confirmed
until a connection is already open. Disabling it releases any write currently paused on a stale
XOFF rather than leaving it stuck. `Session` grew a `Transport` property so front ends can reach a
transport's own capabilities (here, via a `TcpTransport` pattern match) without the session itself
knowing about transport-specific features. See `docs/design/transports.md`'s TCP section.

## WPF and TUI: View > Echo Sent Commands, Software Flow Control, Clear Output

Both front ends' View menu gained three items alongside Theme:

- **Echo Sent Commands** — appends `Out> {line}` to the active tab's output right after a typed
  line is successfully encoded, before it's actually sent. A window-level toggle, off by default.
- **Software Flow Control (XON/XOFF)** — a checkable item wired to the new
  `TcpTransport.SoftwareFlowControl` toggle above (see that section). Enabled/checked only when the
  active tab's `Session.Transport` is a `TcpTransport`, re-synced by each front end's
  `RefreshConnectionUi` on every tab switch, profile switch, and connect/disconnect, since the
  setting lives per-transport-instance.
- **Clear Output** — empties the active tab's output pane/list; other tabs are untouched.

The TUI's `_View` menu was restructured to hold these as four sibling items (`_Theme`, Echo Sent
Commands, Software Flow Control, Clear Output) instead of `_Theme` owning the whole top-level menu;
`TuiThemeMenu` now exposes just its `MenuItem` (`ThemeMenuItem`) rather than the whole
`MenuBarItem`. Both front ends' marker convention (`●`/blank prefix for the TUI, `IsCheckable` for
WPF) and `RefreshConnectionUi` gating already existed for Theme and Device menu items respectively;
this reuses both rather than inventing new patterns. See `docs/specs/tui-main-screen.md` and
`docs/specs/wpf-main-window.md`.

## Write pacing (inter-byte delay) for Serial, TCP, and RFC 2217

New `WriteDelayStream` (`DevTerm.Core.Transports`) — a write-only `Stream` decorator for slow
devices without FIFO buffers that can't absorb a burst write. Writes one byte at a time with an
explicit `FlushAsync` after each, delaying `WriteByteDelayMs` milliseconds between bytes (never
after the last one). Three-way sentinel: `-1` (default) disables pacing entirely — an unpaced write,
exactly as before; `0` paces with no delay (still one write-and-flush per byte); a positive value
adds that many milliseconds between bytes. Write-only — has no effect on how a transport reads.

`WriteByteDelayMs` was added to `SerialTransportOptions`, `TcpTransportOptions`, and
`Rfc2217TransportOptions` — the three transports whose write path is a single stream
`WriteDelayStream` can wrap; not offered for HID/USBTMC (one atomic device-framed report/message per
write call — splitting it would break framing, not pace it) or BLE/Loopback. Wired through
`CliOptions.WriteByteDelayMs` (`--writebytedelayms`), `CliOptionsValidator` (must be -1 or greater),
and `ServiceCollectionExtensions.AddDevTermFrontEnd`.

`ConnectionEditorViewModel` grew a new "Timing" form section (`SupportsWriteByteDelay =
IsSerialTransport || IsTcpTransport || IsRfc2217Transport`) holding the one field, shown in both
front ends alongside Serial/TCP/RFC 2217's own groups rather than nested inside any one of them,
since the field applies across all three.

See `docs/design/transports.md`'s new "Write pacing" section, `docs/specs/connection-editor.md`'s
Fields/States entries, and `docs/user-guide/connecting.md`'s Connection Editor walkthrough.
