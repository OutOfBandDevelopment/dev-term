## Migrated off Terminal.Gui's obsolete static `Application`/`TextView` APIs, elevated CS0618 to error

Terminal.Gui v2.5.0 marks its static `Application.*` surface and `TextView` `[Obsolete]`; both were
still in use across `DevTerm.Console`/`DevTerm.Console.Tests`. Migrated every call site to the
instance-based `IApplication` API, and migrated `TuiMode.cs`'s output pane from `TextView` to the
`Terminal.Gui.Editor` NuGet package's `Editor` class (`Editor.Text` is a direct `string` property
like the old `TextView.Text`; `Editor.CaretOffset`'s setter scrolls the viewport to keep the caret
visible — the correct, doc-confirmed replacement for `TextView.MoveEnd()`). With both migrations
done, `dotnet_diagnostic.CS0618.severity = error` is now set in `.editorconfig`, so a future obsolete-
API usage fails the build instead of accumulating as a warning. Verified via a full clean
`dotnet build` (0 `CS0618` warnings) and a full passing `TestCategory=Unit` run.

## Fixed a hanging USBTMC unit test

`UsbtmcTransportTests.WriteAsync_TwoConsecutiveValidZeroLengthMessages_ReturnsAnEmptyReplyWithoutThrowing`
hung indefinitely rather than failing. Root cause was the test's own technique, not the transport:
every other test in the file reads the reply via a blocking `PipeReader.ReadAsync`, but a genuinely
empty USBTMC reply never advances bytes into the pipe and never completes it — there's no signal path
from "confirmed empty" to an awaiting reader, so `ReadAsync` blocks forever. Fixed by asserting via
the non-blocking `PipeReader.TryRead` instead (see the new `CLAUDE.md` constraint on this), plus an
`Assert.HasCount(3, device.WrittenFrames)` check to actually prove the retry-once path consumed and
tag-validated the *second* queued empty header, not just that the first one alone produced nothing.
Production `UsbtmcTransport.ReadReply`/`WriteAsync` logic was traced through in full and confirmed
already correct.

## Fixed a real bug in `Session.OpenAsync` found during a pre-merge branch review

A prior CA2016/MA0040 "forward the CancellationToken parameter" cleanup pass had changed
`Session.OpenAsync`'s `Task.Run(() => PumpAsync(_readLoopCts.Token))` into
`Task.Run(() => PumpAsync(_readLoopCts.Token), cancellationToken)` — forwarding `OpenAsync`'s own
token into `Task.Run`'s scheduling-cancellation parameter, not the token actually passed to
`PumpAsync`. If that token were cancelled before the thread pool started the delegate, `Task.Run`
would yield an already-`Canceled` task without ever running `PumpAsync`: the read loop would silently
never start (no exception out of `OpenAsync`, since it doesn't await `_readLoopTask`), and a later
`StopAsync`'s `await _readLoopTask` would throw `TaskCanceledException` uncaught out of
`CloseAsync`/`DisposeAsync`. Fixed by passing `CancellationToken.None` explicitly, with a comment
explaining why — see the new `CLAUDE.md` constraint. Caught by a review pass across the whole
`dev/code-cleanup` branch before merging to `main`, not a live symptom; verified via a full clean
build and a full passing `TestCategory=Unit` run (including `DevTerm.Core.Tests.Sessions.SessionTests`).

## USBTMC transport protocol-conformance rework; root-caused the DG1022 "no reply" failures

Branch `dev/usbtmc-fix`. The full write-up is in
[`docs/design/features/usbtmc-protocol-conformance.md`](../design/features/usbtmc-protocol-conformance.md). I reviewed
`DevTerm.Transports.Usbtmc` against `docs/protocols/usbtmc/` and fixed eleven problems.

**Read path:**
- Replies were cut short: EOM was ignored, and a short packet didn't end the transfer.
- The bulk-IN buffer (65548 bytes) wasn't a whole number of packets, so libusb overflowed on large replies. WinUSB instead carries the surplus into the next read.
- A declared TransferSize above 2³¹ wrapped negative.

**Recovery:**
- There was no abort or clear, so one timeout left every later query off by one.

**Control requests and writes:**
- REN_CONTROL sent wValue=0, which de-asserts REN. An earlier "spec nit" change had introduced this, and `usbtmc-transport.md` now marks it reverted.
- A zero-length DEV_DEP_MSG_OUT could be sent.

**Device lifetime and concurrency:**
- `SystemUsbtmcDevice.Open` leaked every device listed after the match.
- Nothing serialized I/O or close.
- Disposing twice threw.

**Query detection:**
- It missed several shapes of query.

New pieces:
- `UsbtmcCodec.BulkInBufferSize`
- `IUsbtmcDevice.MaxPacketSize`/`AbortBulkIn`/`AbortBulkOut`/`Clear`
- GET_CAPABILITIES-gated remote/local
- `UsbtmcDeviceQuirks`
- Options `ClearOnOpen` (off), `RemoteOnOpen`, `RequestDelayMs`

Unit tests: 39 in `DevTerm.Transports.Usbtmc.Tests`, up from 24. Two existing tests had encoded a
spec-violating assumption (EOM clear across physical reads of one transfer) and were corrected.

Bench tested against a real DG1022 (`docs/test/2026-09-25-18-03-06.md`). A raw probe showed the device
**never** answers a REQUEST_DEV_DEP_MSG_IN sent back-to-back with the query, reproducibly across 3 runs.
Any gap of about 1 ms or more fixes it. That is the real cause of the "intermittent" DG1022 failures `BACKLOG.md` tracked: the
open-time control requests happened to supply the gap for `*IDN?` only. There are two fixes:
- `UsbtmcDeviceQuirks` gives 0x1AB1:0x0588 a 20 ms delay.
- It also skips REN, because the DG1022 timed out GO_TO_LOCAL and libsigrok blacklists RL1 for this PID.

After both fixes, `RealHardwareUsbtmcTests.CliMode_AgainstRigolDg1022...` passed 3 of 3 runs, and 7 unpaced CLI queries all
answered. I removed the DG1022 entry from `BACKLOG.md` and added follow-ups:
- Re-verify the DS1102E/DG1062Z/DM3058E.
- DS1102E `:WAV:DATA?` framing quirks (from the literature).
- A/B test the open-time ClearHalt.
- A hex-parser crash on non-hex input, which is unrelated to USBTMC.

## All four Rigols verified; root-caused the DG1062Z "2-byte first read" (data-toggle desync)

With all four bench Rigols attached, the first run of the 13 USBTMC hardware tests failed both new DG1062Z tests.
A bulk-IN read came back as 2 bytes, too short for a header. The raw probe showed those 2 bytes (`\n+`) were the
*tail* of the device's 66-byte `*IDN?` transfer: its first 64-byte packet was lost, on the first query after open only.

**Cause:** `SystemUsbtmcDevice.Open`'s unconditional CLEAR_FEATURE(ENDPOINT_HALT) on both bulk endpoints.
- It resets the host's data toggle (USB 2.0 §9.4.5).
- The DG1062Z doesn't reset its own toggle to match, so the host drops the device's next packet as a retransmission.
- A/B test over 12 opens: broken on 12 of 12 with the clear, intact on 12 of 12 without it.

**Fix:** a new `ClearHaltOnOpen` option, default off, pinned by a unit test together with `ClearOnOpen`. A real STALL is
still cleared and retried per transfer, which covers the DM3000 first-write STALL the open-time clear was originally
added for. This resolves the BACKLOG DG1062Z entry. It also resolves the "A/B test the open-time ClearHalt" and
"re-verify DG1062Z/DM3058E" entries, which were removed.

After the fix, all 13 USBTMC hardware tests pass on all four devices across three runs. `devterm.runsettings` now has
the DM3058E's real serial (`DM3R232301438`) and `*IDN?` substring (`DM3058E`), and its stale "left blank" comments are
fixed. Details are in `docs/test/2026-09-25-18-03-06.md`, follow-up 2.

## Detected serial port descriptions on Linux and macOS

The Linux/macOS half of the Connection Editor's long/short serial port name (the Windows half landed
2026-09-18, see `docs/changes/2026-09-18.md`) — the last item on the Connection Editor's requested
list, removed from `BACKLOG.md` and the spec's Open items. The "Detected ports" picker (WPF dropdown,
TUI "Detect..." list) now shows e.g. `/dev/ttyUSB0 — FTDI FT232R USB UART (0403:6001, serial
A50285BI)`; picking one still writes only `/dev/ttyUSB0`, and the profile format is unchanged.

- **Shape**: nothing outside `DevTerm.Transports.Serial` changed. `SystemSerialPortDiscovery.GetPortDescriptions()`
  now picks by `OperatingSystem.IsWindows()`/`IsLinux()`/`IsMacOS()` (anything else still reports no
  descriptions). Keys are the full paths `SerialPort.GetPortNames()` reports on those OSes
  (`/dev/ttyUSB0`, `/dev/cu.usbserial-…`), so `SerialPortOption.From`'s lookup matches unchanged.
  Linux and macOS share one format (`SerialPortDescriptionFormat`): `<manufacturer> <product>
  (<vid>:<pid>, serial <serial>)`, the manufacturer dropped when the product already starts with it,
  `USB device <vid>:<pid>` when the device reports no strings, null when there's nothing at all. The
  serial number is included (unlike Windows' friendly name) because it's what tells two identical
  adapters apart.
- **Linux (`LinuxSerialPortDescriptions`) reads sysfs directly** — the same USB string descriptors
  udev's `ID_VENDOR`/`ID_MODEL`/`ID_SERIAL_SHORT` and `/dev/serial/by-id/` names come from, with no
  libudev dependency. For every `/sys/class/tty/<name>` it resolves `device` with a physical realpath
  (built on a single-level `readlink`; relative targets are resolved against the directory the link
  really lives in, since `/sys/class/tty/<name>` is itself a link; bounded at 40 hops like the
  kernel's ELOOP), then walks up at most 12 levels, staying under `/sys`, to the nearest directory
  with an `idVendor` file — the USB device, not the interface (`1-2:1.0`) or an upstream hub/root hub
  — and reads `manufacturer`/`product`/`serial`/`idVendor`/`idProduct`. Covers both usb-serial
  (`ttyUSB*`: `device` → the port dir, two levels below the device) and `cdc_acm` (`ttyACM*`:
  `device` → the interface, one level below). Non-USB ports (`ttyS*`, platform UARTs), ttys with no
  `device` link, and unreadable files get no entry. `/dev/serial/by-id/` was not used — it's derived
  from the same attributes and adds nothing sysfs doesn't already give.
- **macOS (`MacSerialPortDescriptions`) shells out to `ioreg`** rather than P/Invoking
  IOKit/CoreFoundation: `/usr/sbin/ioreg -a -l -r -c IOUSBHostDevice` (every USB device's subtree as
  an XML plist), parsed with `System.Xml.Linq` (DTD processing ignored — the plist has a
  `<!DOCTYPE>` the default reader rejects). Each `IOSerialBSDClient`'s `IOCalloutDevice` and
  `IODialinDevice` (`cu.*` and `tty.*` — `GetPortNames()` lists both) is mapped to its nearest
  `IOUSBHostDevice`/`IOUSBDevice` ancestor's `USB Vendor Name`/`USB Product Name`/`USB Serial Number`
  (falling back to `kUSBVendorString`/`kUSBProductString`/`kUSBSerialNumberString`) and
  `idVendor`/`idProduct`. The intermediate `IOUSBHostInterface` also carries `idVendor`/`idProduct`
  but not the strings, so only the device node counts as the ancestor. The process run is bounded:
  3 s, both pipes drained concurrently, killed (whole tree) on timeout; a missing `ioreg`, non-zero
  exit, timeout, or unparseable output all mean no descriptions, never an exception or a hang.
- **Tests (+38 in `DevTerm.Transports.Serial.Tests`, 19 → 57)**: `LinuxSerialPortDescriptionsTests`
  (11, Unit) builds a fake sysfs tree in a temp dir laid out like the real one (FTDI `ttyUSB0`,
  Raspberry Pi Pico `ttyACM0`, CP2102 behind a hub, a string-less CH340, `ttyS0` under `pnp0`, a
  virtual `tty`, a symlink loop, a missing root) — the symlinks are supplied as data through the
  injected `readlink` (creating real symlinks on Windows needs a privilege tests can't count on), and
  sysfs's `:` separators are written as `_` since NTFS forbids `:` in names.
  `MacSerialPortDescriptionsTests` (10 incl. data rows, Unit) parses a sample `ioreg -a` plist whose
  FTDI entry's property names/values (`idVendor` 1027, `idProduct` 24577, `IOCalloutDevice`
  `/dev/cu.usbserial-AE01EB7D`, `IODialinDevice`, `IOTTYDevice`) follow ioreg output posted in
  pololu/libusbp issue #8, plus a CDC-ACM Pico, a non-serial USB receiver, the `kUSB*String`
  fallback, a Bluetooth-style port with no USB parent, and malformed output.
  `SerialPortDescriptionFormatTests` (13 rows, Unit). `MacSerialPortDescriptionsProcessTests` (4,
  **Integration** — real processes) drives the bounded runner with this OS's stand-ins: missing
  executable, stdout returned, non-zero exit, and a 60 s `ping`/`sleep` killed at 500 ms. Full
  `dotnet build` 0 warnings; `dotnet test --filter TestCategory=Unit` all passing.
- **Not verified on a real Linux or macOS machine.** This environment is Windows only; both
  implementations are exercised solely through the unit tests' sample sysfs trees and sample `ioreg`
  output, and the macOS sample is a trimmed, hand-assembled plist rather than a capture. Worth
  checking on real machines: that .NET's `FileInfo.LinkTarget` returns sysfs's relative link text as
  assumed, `ioreg -a -l -r -c IOUSBHostDevice`'s actual nesting on current macOS (Apple Silicon /
  DriverKit `AppleUSBFTDI`, `AppleUSBACMData`), and the picker's appearance with a real adapter.

## Front ends never crash on errors; the 2026-09-23 TODO bugs; presenter lifetime; USBTMC DevicePath

Branch `dev/error-handling-and-todo`. I reviewed the CLI, TUI and WPF for crash/exit paths against the
rule "show the error, disconnect, let the user resume; reject invalid input". What changed:

**Core: `Session.Disconnected`.**
- The read loop used to die silently on a read failure (an unplugged cable, a reset socket, a
  presenter throwing), and its exception resurfaced from `CloseAsync`/`DisposeAsync`, crashing on close.
- A peer hang-up also ended the loop with no notice.
- Now the session closes itself on a read failure, a peer close, or a failed send, and raises
  `Disconnected` once. For a failed send it does this before the send rethrows.
- `CloseAsync` never throws for a transport-close failure. Open/close/fault are serialized, and each
  fault carries a generation so a stale fault can't hit a newer connection.
- 7 new `SessionTests`.

**Shared (`DevTerm.Configuration`).**
- `TypedInput.TryEncode` rejects input the parser can't encode with a message.
  - This was the CLI crash: non-hex text with `--parser hex` threw an unhandled `FormatException`.
  - A decimal value over 255 is rejected the same way.
- `ConnectionErrorMessages.ForDisconnect` gives the CTS/`--handshake` hint only for a serial timeout.
  Before, a USBTMC timeout told the user to check hardware flow control.

**CLI.**
- Invalid lines are rejected and the connection is left alone.
- A lost connection is reported once, and the next line reconnects first, then sends. A failed
  reconnect is reported and the next line retries.
- Only a failed first connect still exits (code 1).
- 4 tests drive the real loop through scripted stdin. A real capture (a local TCP stand-in hangs up,
  then the next line reconnects and gets a reply) is in `docs/user-guide/sending-and-receiving.md`.

**TUI.**
- A failed startup connect opens the TUI disconnected with the error (it used to exit to the shell).
- `Disconnected` flips the menu and send field, and is re-subscribed on a profile switch.
- Every menu action is guarded, with an error dialog instead of an exception escaping `Application.Run`,
  which only swallows it in RELEASE builds.
- Every fire-and-forget task (connect, send, switch, SCPI auto-detect) is observed.
- 4 new tests.

**WPF.**
- A failed startup connect, reconnect or profile switch is shown in the output list and the window
  stays open, disconnected. It used to show a modal and close the whole app.
- `Disconnected` handling and observed fire-and-forget tasks match the TUI.
- 4 new tests.

**Control panels (both).** Every command goes through one helper, so a rejected value or a device
failure is shown instead of vanishing as an unobserved task: an error dialog in the TUI (the modal
panel hides the main output), the red status line in WPF. There's a WPF test for a failing command.

## Fixed: real Radex One on COM8 never replied — two protocol bugs, both checksum-verified

The Radex One module built earlier this session (see "Built the Radex One geiger counter device
module" below) never got a reply from the real device once one turned up attached on COM8. The
device is a plain serial port (2400 8-N-1, no handshake) — real-hardware confirmed — not a USB HID
device as that earlier build wrongly assumed; `RadexOneHidFraming` is deleted, and the module now
uses `DevTerm.Transports.Serial` directly, no report wrapping involved.

Beyond the transport, re-deriving the source reverse-engineering doc's raw trace examples by hand
(not just trusting its prose field list) found the implemented framing itself was wrong in two
ways:

- The outer header's `Type` field was implemented as a per-command code. It's actually a **constant
  marker** (`0x0020` outbound, `0x8020` inbound) on every command — the real command code is the
  *first word of the Extension field itself*. A new `RadexOneExtensionCodec` now builds/parses each
  command's own extension shape (query/ack: 6 bytes; Write Settings request: 16 bytes; Read Data
  reply: 22 bytes; Read Settings reply: 16 bytes), each verified byte-for-byte against a real trace.
- The checksum was a byte-sum. It's actually a **word-sum**: read the covered range as consecutive
  little-endian 16-bit words, sum them, then `0xFFFF - (sum % 0xFFFF)`. The `% 0xFFFF` looked like a
  no-op under a byte-sum's much smaller max total, but isn't — confirmed against a real reply trace
  whose outer-header word-sum exceeds `0xFFFF` and only matches the trace's actual checksum bytes
  once the modulo is applied. The same formula covers both the outer header's checksum and each
  extension's own trailing checksum.

The Read Serial/Version reply's exact reserved-byte layout past its first 4 bytes didn't fully
reconcile against the source doc's own worked checksum example (off by 10 decimal) — likely a
transcription error in the source notes, which have visible typos elsewhere. Rather than guess,

## Stream Monitor (stream content detection, phase 1)

Built phase 1 of [docs/design/proposals/stream-content-detection.md](../design/proposals/stream-content-detection.md).
**Device > Stream Monitor...** in the TUI and WPF:
- watches the live session for images (PNG/JPEG/GIF/BMP/TIFF), HP-GL, PostScript and PCL;
- captures each one whole;
- auto-saves it to the connection's export folder (`~/.dev-term/exports` by default) as
  `{device}_{yyyyMMdd-HHmmss}.{ext}`.

WPF also previews native image formats and has Open Folder and Export As.... Spec:
[docs/specs/stream-monitor.md](../specs/stream-monitor.md); guide:
[docs/user-guide/stream-monitor.md](../user-guide/stream-monitor.md).

- **Detection** (`DevTerm.Core.StreamContent`, pure and unit-tested):
  - `StreamContentSniffer` matches signatures, including SCPI `#<n><len>` blocks.
  - `StreamContentEndFinder` finds structural ends: PNG `IEND`, JPEG EOI (by walking segments), the GIF
    trailer, BMP/EPS header sizes, `%%EOF`/Ctrl-D and the PJL UEL. Formats without one end after 2 s of
    silence, and there's a 64 MiB cap.
  - False-positive guards: HP-GL only counts at a reply boundary, and a lone `ESC E` isn't PCL.
  - `StreamContentWatcher` is an `IPresenter` that emits no text and raises `ContentDetected`. `Render`
    never throws. Timing goes through `TimeProvider`, so the tests use a fake clock.
- **Declared hint:** `ScpiCommandDefinition.ExpectedResponseFormat`. `ScpiControlSurface` calls
  `IStreamContentHintSink.ExpectResponse` on sinks in `Session.Presenters` before sending. The DG1062Z's
  `HCOPy:SDUMp:DATA?` declares `Image`.
- **Tap:** `StreamMonitor` (`DevTerm.Configuration`) binds a fresh watcher per session with
  `Session.AddPresenter`; the new `Session.RemovePresenter`/`Pipeline.RemovePresenter` unbind it.
  - It isn't a `--presenter`: it emits no text, and binding it in place lets monitoring be turned on and
    off mid-connection without touching any other presenter's output.
  - It follows profile switches (`SetSession`): a capture in progress on the old session is flushed and
    saved first.
  - Monitoring continues after the window closes (the TUI window is modal), and each capture adds a
    status line to the main output.
- **Not verified against real hardware yet** (DG1062Z screen capture, TDS2024 hardcopy); unit tests only.

Built in a parallel worktree and merged, with no conflicts. The full unit suite passes.

## Logger mode and log playback (CLI, TUI, WPF)

- **New `DevTerm.Logging` project** (references only Core): a versioned JSON Lines session-log format, a
  header plus one record per event.
  - `tx`/`rx` store the raw chunk as base64, so playback is lossless, chunk boundaries included.
  - Records carry sequence numbers and monotonic UTC timestamps.
  - Unknown fields are ignored, unknown record types are kept verbatim, newer versions are refused, and a
    torn final line is tolerated.
  - See `docs/design/session-logging.md`.
- **`Session.AddObserver(ISessionObserver)`:** a passive tap on the session. It sees each received chunk
  before rendering, each send before the write, opens, and closes (a requested close versus a
  self-disconnect). It sits outside the pipeline, and an observer that throws is ignored. `SessionLogger`
  records through it and follows a live profile switch (writing a `session` record).
- **`PlaybackEngine`/`PlaybackController`:** pull-driven playback with an injectable `TimeProvider`.
  - Controls: 0.25x–10x and Max, step, rewind, seek, +10 s, and changing presenters.
  - Trim to a new log (`trimmedFrom`, original sequence numbers kept), and notes saved into the log.
  - `PlaybackPresenters` composes presenters with no transport (`AddDevTermPresenters`), so playback cannot
    reach a device.
- **CLI:** `--log <path>` or `--log true`, defaulting to
  `~/.dev-term/logs/{yyyyMMdd-HHmmss}_{profile|connection}.jsonl`. `--playback <log> [--presenter ..]
  [--playbackspeed n]` replays a log (0 = as fast as possible) and never connects.
- **TUI/WPF:** File > Start Logging... / Stop Logging (with `● REC` in the status line/bar) and File > Open Log
  for Playback.... The TUI's `PlaybackMode` is modal; WPF's `PlaybackWindow` is non-modal, with a seek slider
  and presenter check boxes. Specs: `docs/specs/playback-window.md`, `tui-main-screen.md`,
  `wpf-main-window.md`. User guide: `docs/user-guide/logging-and-playback.md`.
- **Verified** with the loopback transport and test fakes: the real CLI recorded a loopback session with
  `--log` and replayed it with `--playback`, including `--presenter hex --playbackspeed 4`. Not verified
  against real hardware yet.

Built in a parallel worktree. On merge it conflicted in `DevTerm.Configuration.csproj`, where this branch and
the panels branch each added a project reference (both kept), and in the TUI spec's status-line row (combined).
The full unit suite passes, 17 projects including the new 44-test `DevTerm.Logging.Tests`.

Known limits:
- A note can't be added to a log the same process is still recording.
- Logs load fully into memory, and backward seeks replay from the start.
- No skip-silence option, and notes can't be edited.
- The TUI has no seek slider.
- Quitting the TUI ends the log without a final `close` record; WPF records it.

With this, **Phase 1 of the UI batch is complete** (Stream Monitor, panels, logger/playback).

## Theming: light/dark/system and user themes (TUI + WPF)

- **Investigated first** (details in `docs/design/theming.md`):
  - **WPF Fluent `ThemeMode`: not used.** It works on net10.0-windows per window, but it's still experimental
    (WPF0001 on every use, which fails the build under TreatWarningsAsErrors). It re-templates every control
    with much larger metrics (a 60 px ListBox went from two rows to one). And Dark's window background is
    transparent (Mica), so RenderTargetBitmap screenshots come out white on white.
  - **Terminal.Gui v2.5.0's built-in themes: not used either.** There's no ConfigurationManager, and its
    Dark/Light themes leave the Base background as the terminal's own (`None`), so Dark is unreadable on a
    light terminal. `SchemeManager.AddScheme` does override a scheme live and process-wide, surviving
    Application.Init and ThemeManager switches.

  - `DevTermTheme`: a WCAG contrast check and IsDark.

    Windows, `COLORFGBG` elsewhere).
  - `ThemeFile`: JSON user themes in `~/.dev-term/themes`, validated. Every problem is reported, and loading
    never throws.
  - `ThemeCatalog`, and `ActiveTheme` (the process-wide current theme and a `Changed` event).
- **Where the choice lives:** it's an app preference in the new `~/.dev-term/preferences.json`

## UI batch Phase 2: forms from one definition, and a device manifest editor

**Forms engine** (`DevTerm.UiDefinitions.Forms`). `[FormField]`/`[FormSection]` plus the
`System.ComponentModel` attributes a model already carries (`[Category]` → section, `[DisplayName]` →
label, `[Description]` → help, `[Browsable(false)]` → left out) declare a form on the model itself.
`FormDefinitionGenerator` turns it into an ordinary `UiDefinition`: the control id is the property name,
and it's opt-in once any property has `[FormField]`, otherwise every browsable editable property
(`CliOptions` generates this way). `FormBinding` binds a rendered form to the model: validated,
type-converted writes (a string property keeps what was typed), condition evaluation, and change relay
(or its own change notice for a plain model). New model pieces: `UiCondition` (`VisibleWhen` on sections
and controls: an id plus values, none meaning "is true", a collection matching on any item),
`UiControl.Description`, `ChoiceStyle.CheckList` (now written by name in JSON; numbers still read), and
`IndicatorStyle`. Form renderers in both front ends (`DevTerm.Console.FormRenderer`,
`DevTerm.Wpf.FormRenderer`) are siblings of the control-panel renderers. TUI choices are a one-line
`OptionSelector`, wrapped radio check boxes (up to 3 lines), or a text field plus a Pick... list; the TUI
form reflows on every change and aligns each section to its longest *shown* label.

**Connection Editor fields are generated** in both front ends from `ConnectionEditorViewModel`'s own
annotations (`FormDefinition`). The view model stays underneath as the binding/validation layer, and one
level of grouping plus visibility conditions covers the transport-conditional groups (the two open scope
questions). Generated: every connection field, the not-found hints, the loopback note, presenters
(`PresentersText`), SCPI profile, Send as, Line ending. The three detected-device pickers are hand-built
widgets in generated rows; the profile list, save/import/export and Connect/Close/Quit stay hand-built.
This fixes the TUI's blank gap under a hidden transport group
(`ConfigureModeTests.SwitchingTransport_ReflowsTheForm_…`). Both front ends bind live now (the TUI's
push/pull and its `TransportChoice`/`PresenterChoice` enums are gone), and typed numbers get an inline
validation message. WPF output is pixel-identical; the TUI screenshots were regenerated.

**Manifest validation and writing.** `DeviceManifestValidator` errors now fail
`DeviceManifestLoader.Load` with `DeviceManifestValidationException`: a blank name, a command without a
name or template, a duplicate command id, a blank or duplicate parameter name, a pattern without a name or
regex (or with a regex that doesn't compile), a control without an id. Warnings don't block a load: a
button or field whose command no command declares, a missing parameter field, an unfilled template
placeholder. The editor uses `Load(path, validate: false, out file)`. `DeviceManifestWriter.Save` writes
camelCase with nulls omitted, keeps a package's separate UI file, and copies a referenced Kaitai file.
`ManifestControlSurface.ForPreview` has no session and raises `PreviewInvoked` instead of sending.

**Device manifest editor** (**Device > Edit Device Manifest...**; TUI `ManifestEditorMode`, WPF
`ManifestEditorWindow`, shared `ManifestEditorViewModel`). An outline of identity, commands, parameters,
reply patterns, panel sections and controls; each part's form is generated from an annotated facade
(`DevTerm.DeviceManifests.Editing`), including a control form whose fields follow its kind and a pattern
tester. Add, remove and reorder; create a panel from the commands; a live preview through the real
control-panel renderers that sends nothing and shows what it would send. Save validates first, then
writes to `~/.dev-term/manifests/<folder>/device.json` (for an installed, zipped or new manifest) or in
place. The bundled Loopback Sensor Demo round-trips unchanged (tested). Specs:
docs/specs/manifest-editor.md; guide: docs/user-guide/manifest-editor.md; design:
docs/design/ui-definitions.md#forms-from-one-definition.

Merged after the theming branch: the forms renderer's warning text and the Device Profiles status line
now use the theme's `DevTerm.Error` brush (a dynamic resource) instead of the `DarkRed` literal the
branch was written against, and the color picker's owner (`GetWindow(SectionsPanel) ?? this`, so it works
from the editor's preview) went into the Custom-radio refactor's `TryPickColor`. Follow-ups
