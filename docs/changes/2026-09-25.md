# 2026-09-25

## Migrated off Terminal.Gui's obsolete static `Application`/`TextView` APIs, elevated CS0618 to error

Terminal.Gui v2.5.0 marks its static `Application.*` surface and `TextView` `[Obsolete]`; both were
still in use across `DevTerm.Console`/`DevTerm.Console.Tests`. Migrated every call site to the
instance-based `IApplication` API, and migrated `TuiMode.cs`'s output pane from `TextView` to the
`Terminal.Gui.Editor` NuGet package's `Editor` class (`Editor.Text` is a direct `string` property
like the old `TextView.Text`; `Editor.CaretOffset`'s setter scrolls the viewport to keep the caret
visible — the correct, doc-confirmed replacement for `TextView.MoveEnd()`). With both migrations
done, `dotnet_diagnostic.CS0618.severity = error` is now set in `.editorconfig`, so a future obsolete-
API usage fails the build instead of accumulating as a warning. Verified via a full clean
`dotnet build` (0 `CS0618` warnings) and a full passing `TestCategory=Unit` run.

## Fixed a hanging USBTMC unit test

`UsbtmcTransportTests.WriteAsync_TwoConsecutiveValidZeroLengthMessages_ReturnsAnEmptyReplyWithoutThrowing`
hung indefinitely rather than failing. Root cause was the test's own technique, not the transport:
every other test in the file reads the reply via a blocking `PipeReader.ReadAsync`, but a genuinely
empty USBTMC reply never advances bytes into the pipe and never completes it — there's no signal path
from "confirmed empty" to an awaiting reader, so `ReadAsync` blocks forever. Fixed by asserting via
the non-blocking `PipeReader.TryRead` instead (see the new `CLAUDE.md` constraint on this), plus an
`Assert.HasCount(3, device.WrittenFrames)` check to actually prove the retry-once path consumed and
tag-validated the *second* queued empty header, not just that the first one alone produced nothing.
Production `UsbtmcTransport.ReadReply`/`WriteAsync` logic was traced through in full and confirmed
already correct.

## Reworked the build's warning policy: every warning is now a build-breaking error

`Directory.Build.props` now sets `TreatWarningsAsErrors` (previously an empty `WarningsAsErrors`, a
narrower per-ID list). The solution was already sitting at a clean 0-warning baseline, so this makes
that state enforced going forward instead of just currently-true — any new analyzer finding or
compiler warning now fails `dotnet build` rather than silently accumulating until someone notices and
hand-elevates it in `.editorconfig`. Also:

- Fixed the real suppression mechanism for the `AD0001` warnings StyleCop.Analyzers throws on a
  `record struct` declaration (`SA1201`'s member-order table has no entry for that syntax kind) and
  on `DevTerm.Transports.Tcp.Tests`'s `SocketExceptionStub` class layout (`SA1500`/`SA1502`/`SA1508`,
  all `NullReferenceException` in the same internal helper). An `.editorconfig`
  `dotnet_diagnostic.AD0001.severity` line does nothing — confirmed empirically (build-server
  shutdown + `obj`/`bin` deleted + clean rebuild still showed identical warnings) — because AD0001 is
  Roslyn's `NotConfigurable` diagnostic tag, which ignores `.editorconfig` severity overrides
  entirely. The working fix is `Directory.Build.props`'s `<NoWarn>$(NoWarn);AD0001</NoWarn>`, a
  compiler-option-level filter.
- Set `csharp_style_prefer_primary_constructors = false:silent` so `IDE0290` stops suggesting a
  primary constructor, without retroactively flagging the handful of files that already use one for
  removal.
- Suppressed `CA1859` (prefer concrete types for performance) and `IDE0021` (expression-bodied
  constructor) as not-a-fit for this codebase's conventions.

See `docs/coding-standards.md`'s "How this is enforced" and "A known StyleCop quirk" sections for the
updated detail. Verified via a full clean `dotnet build --no-incremental` (0 warnings, 0 errors) and
a full passing `TestCategory=Unit` run after each change.

## Fixed a real bug in `Session.OpenAsync` found during a pre-merge branch review

A prior CA2016/MA0040 "forward the CancellationToken parameter" cleanup pass had changed
`Session.OpenAsync`'s `Task.Run(() => PumpAsync(_readLoopCts.Token))` into
`Task.Run(() => PumpAsync(_readLoopCts.Token), cancellationToken)` — forwarding `OpenAsync`'s own
token into `Task.Run`'s scheduling-cancellation parameter, not the token actually passed to
`PumpAsync`. If that token were cancelled before the thread pool started the delegate, `Task.Run`
would yield an already-`Canceled` task without ever running `PumpAsync`: the read loop would silently
never start (no exception out of `OpenAsync`, since it doesn't await `_readLoopTask`), and a later
`StopAsync`'s `await _readLoopTask` would throw `TaskCanceledException` uncaught out of
`CloseAsync`/`DisposeAsync`. Fixed by passing `CancellationToken.None` explicitly, with a comment
explaining why — see the new `CLAUDE.md` constraint. Caught by a review pass across the whole
`dev/code-cleanup` branch before merging to `main`, not a live symptom; verified via a full clean
build and a full passing `TestCategory=Unit` run (including `DevTerm.Core.Tests.Sessions.SessionTests`).

## Added a `Hardware` test category, plus real-hardware Integration tests for three more Rigol profiles

Added `TestCategories.Hardware` (whitelisted in `TestCategoryStandardsTests`) and applied it across
every existing real-hardware test class, so `TestCategory=Hardware` alone selects the full
real-device suite regardless of transport. Added `tests/DevTerm.Console.Tests/RealHardwareUsbtmcTests.cs`
covering the Rigol DM3058E, DS1102E, and DG1062Z over USBTMC — same in-process construction pattern
(no DI container, no subprocess) as the existing `RealHardwareSerialTests`, with `TestContext`
logging of connection info and each sent/received value, `Assert.Inconclusive` preflight via a new
`RealDeviceReachability.IsUsbtmcDeviceAvailable` (disambiguating the DS1102E from a DG1022 sharing
its exact VID:PID via `SerialNumber`, per `BACKLOG.md`'s existing USBTMC entry), and identity plus
1-2 safe read-only queries per device. The `RawPresenter` used for terminatorless replies (previously
private to `RealHardwareSerialTests`) is now shared via `DevTerm.Test.Utilities`. New
`devterm.runsettings` parameters hold each device's VendorId/ProductId/SerialNumber/ExpectedIdnReply.

First real-hardware run (`docs/test/2026-09-25-15-02-44.md`) found two new, real issues, both left
for a deliberate follow-up rather than fixed blind: the DG1062Z's `*IDN?` bulk-IN reply fails USBTMC
header decoding (a 2-byte transfer where 12 bytes are required), and `RealHardwareSerialTests`'s
shared `RunAsync` helper misreads a multi-chunk serial reply (confirmed against the HP 34401A) because
it only consumes one `Session.Output` item per command. Both tracked in `BACKLOG.md`. The DM3058E's
previously-parked USBTMC bulk-IN stall (docs/changes/2026-09-23.md) did not reproduce — likely
resolved as a side effect of this session's `Session.OpenAsync`/`Task.Run` fix above. Everything else
(both Korads, both Tektronix scopes over TCP, the DS1102E, two of four K8055 boards, the Busylight)
passed with no regressions.

Later the same session, added a Rigol DG1022 test too (`*IDN?`/`OUTPut?`/`FREQuency?`) with
`RealUsbtmcDg1022SerialNumber` set to its real, previously-confirmed serial (`DG1D125306284`, see
`docs/test/2026-09-24-17-39-35.md`) to disambiguate it from the DS1102E sharing its exact VID:PID.
Running it against real hardware found the DG1022's previously-documented "stuck at the device/USB
level" zero-byte-reply behavior (docs/changes/2026-09-24.md) is intermittent rather than permanent:
`*IDN?` succeeded twice in a row with a real reply, but the very next query (`OUTPut?`) both times
hit the already-fixed empty-reply retry's terminal `IOException`. Updated `BACKLOG.md`'s existing
USBTMC entry rather than filing a new one — see `docs/test/2026-09-25-15-02-44.md`'s follow-up
section for the full transcript. No production code changed.

Later still, a re-run of the Rigol DG1062Z test (which had earlier failed in this same session's
results matrix with a USBTMC header-decode error on `*IDN?`) passed cleanly against real hardware —
`*IDN?`/`SOURce1:APPLy?`/`SOURce1:FREQuency?` all answered correctly. That framing failure is
therefore also intermittent, not permanent, matching the DG1022's pattern above. `devterm.runsettings`
now has the DG1062Z's real, confirmed serial number (`DG1ZA232603118`) and `*IDN?` reply substring
(`DG1062Z`). `BACKLOG.md`'s USBTMC entry updated accordingly. No production code changed.

With this, every device profile (both Korads, the HP/Agilent/Keysight 34401A, both Tektronix scopes,
and all four Rigol USBTMC instruments) has now been confirmed against real hardware via the automated
`RealHardware*Tests` suite — removed the "Remaining real-hardware verification opportunity" note from
`TODO.md`'s in-progress list accordingly. The two remaining open issues from this pass (the DG1062Z/
DG1022's intermittent USBTMC failures, and `RealHardwareSerialTests`'s multi-chunk-reply harness bug
on the HP 34401A) stay tracked in `BACKLOG.md`'s USBTMC entry rather than `TODO.md`, since neither is
being actively worked yet.
